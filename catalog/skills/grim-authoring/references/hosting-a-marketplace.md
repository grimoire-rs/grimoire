# Hosting a Plugin Marketplace

You loaded this file because you are creating or maintaining a **plugin
marketplace**: a git repository that Claude Code, Copilot, Codex, Qoder and
Cursor users add with their own tool, no grim needed. This is the curator
half. The people who add the repository, and the grim-side commands for
operating one, are in the consumer reference of the `grim-usage` skill
(see [Consumer Side](#consumer-side)).

Everything here needs **grim 0.15.0 or later**. An older grim rejects a
manifest carrying `[marketplace]` with exit 65 on every command that reads
it.

## Pick the Route

Three ways to hand artifacts to people, in order of reach:

- **OCI artifacts** (`grim release`/`publish`) for people who run grim.
- **`grim export plugin`** for a one-off file handoff, a zip someone
  uploads once ([Hand a team a plugin][team-plugin]).
- **`grim export marketplace`** for a standing git address that clients
  add and update from, with no grim on their side.

Pick the marketplace when the audience is a team or the public and a
repository address is the right unit. Confirm flags with
`grim export marketplace --help`.

## Who Owns What {#ownership}

The curator owns the manifest and the automation. grim owns everything it
generates.

| Path | Owner | What |
|---|---|---|
| `marketplace.toml` | curator | The `[marketplace]` table and the plugins |
| `.github/workflows/marketplace.yml` | curator | Regenerate, deliver, keepalive |
| `.github/workflows/verify.yml` | curator | The required check |
| `scripts/` | curator | The gate, the verifier, the pull request body |
| `.github/CODEOWNERS` | curator | Review on what a verifier trusts |
| `marketplace.lock` | grim | Pins, written by `grim update --marketplace` and `grim export marketplace` |
| each client's marketplace file and `./<client>/<plugin>/` trees | grim | See the table below |
| root `README.md` | grim, only while its first line is `<!-- generated by grim export marketplace; edit marketplace.toml instead -->` | A README without that line is yours and is left alone |

The client-to-file table is a frozen contract ([Stability](#stability)), so
it is safe to rely on:

| Client | Marketplace file | Tree | Default set |
|---|---|---|---|
| `claude` | `.claude-plugin/marketplace.json` | `./claude/<plugin>` | yes |
| `copilot` | `.github/plugin/marketplace.json` | `./copilot/<plugin>` | yes |
| `codex` | `.agents/plugins/marketplace.json` | `./codex/<plugin>` | yes |
| `qoder` | `.qoder-plugin/marketplace.json` | `./qoder/<plugin>` | yes |
| `cursor` | `.cursor-plugin/marketplace.json` | `./cursor/<plugin>` | opt-in only |

Add `.grim-export*` to `.gitignore`: grim stages output in a hidden
directory and keeps a `.grim-export.lock` sidecar in the root. If anyone
edits on Windows, add `.gitattributes` with `* -text`. grim writes `\n`
line endings, and `core.autocrlf` would rewrite the owned files and fail
verification.

## Declare It {#declare}

Minimal manifest:

```toml
[marketplace]
name = "acme-tools"
owner = { name = "Acme Platform Team" }
repository = "https://git.example.com/acme/marketplace.git"

[plugins.team-kit]
include = ["registry.example.com/team/team-kit:1"]
description = "The platform team's skills and rules"
```

- `name` and `owner.name` are required. Optional: `description`,
  `clients`, `repository`.
- Each `[plugins.<name>]` takes **exactly one** of `include = [...]`
  (registry references) or `project = "<dir>"` (a local project's locked
  set). Both or neither exits 65.
- `repository` must be an https clone URL without credentials. It is
  written **only** into the generated README, never into a marketplace
  file. Omitted, the README carries a placeholder.
- `clients` defaults to claude, copilot, codex, qoder. Naming `junie`,
  `openclaw` or `droid` exits 65 (they read Claude's file, so select
  `claude`), and so does an empty list.
- `name` may not contain `anthropic`, `claude`, `official` or `qoder`, and
  a reserved-name list applies. Exact limits and the full key table:
  [the `[marketplace]` table][marketplace-table]. Do not copy them here.

Generate once by hand, then commit the result:

```sh
grim export marketplace
git add -A && git commit -m "feat: add the marketplace"
```

## What a Tree Can Carry {#tree-contents}

A plugin tree is rendered per client. **Skills reach every client. MCP
servers reach every client unless the descriptor uses `oauth`, `ws`, or a
`${...}` reference in `command`, `url`, an env key or a header** (the
Agent Plugins clients omit such a server; see
[mcp-spec.md](mcp-spec.md)). **Agents go only to the Claude family
(`claude`, `qoder`). Rules and hooks never go** (a hook needs grim at run
time). Decide what to bundle into a plugin with that in mind.

A plugin with nothing a client can carry is reported `empty` for that
client and **leaves that client's marketplace file**. An existing
`./<client>/<plugin>` tree for it is **deleted**. Exit 65 happens only
when no selected client can carry the plugin. Details:
[what each client admits][admission].

## Plugin Metadata {#metadata}

Optional per-plugin keys (author, homepage, license, keywords, category,
`readme`, `changelog`, `rename.strip_prefix`, `logo`) are in
[plugin metadata][plugin-metadata]. The rules and per-client mapping
live there, so link them rather than copying. What the table does not
make obvious:

- `readme` and `changelog` name size-capped UTF-8 Markdown files relative
  to the manifest (the cap is in [plugin metadata][plugin-metadata]).
  `readme` replaces the generated title and description; `changelog` is
  copied to `CHANGELOG.md`.
- A `[plugin]` table in `grimoire.toml` supplies the same fields for
  `grim export plugin --project` and as a field-by-field fallback for a
  `project = "<dir>"` plugin. Several `plugin.*` keys are `grim config`
  keys at project scope only.
- Each harness gets only the fields its format defines (Codex gets
  `category` plus an `interface` block, and no author or homepage in the
  entry). A declared plugin reads no OCI annotations; an ad-hoc
  single-ref `export plugin` does.
- Adding metadata changes no lock bytes but does change the rendered
  files, so the `+<12 hex>` version moves once.
- `rename.strip_prefix` removes a common member-name prefix. A collision
  or a stale reference left behind is refused (65).
- A `project` plugin records nothing in `marketplace.lock`, and
  `grim update --marketplace` leaves it alone (naming it exits 64).

## Ownership Edge Cases {#edge-cases}

grim keeps no state file. It decides from the repository itself:

- A foreign marketplace file, or a non-empty `./<client>/` with no file,
  exits 65 `untracked-destination` unless `--force`.
- `--force` adopts them **and deletes every stray in `./<client>/`**. Read
  the refusal's path list first.
- A hand-written root README is left alone with a warning, even under
  `--force`.
- **Shadowing.** Droid reads `.factory-plugin/marketplace.json` first, and
  Qoder reads `.qoder-plugin/marketplace.json` before Claude's, even when
  the repo does not select `qoder`. grim warns for both. Delete the
  foreign copy, or select `qoder` and let grim own the file.
- **Rename is breaking.** Changing `[marketplace].name` makes every file
  look foreign, so grim warns then refuses. `--force` adopts under the new
  name and **every consumer must re-add the marketplace**. Do not rename
  casually.

## Change Flow {#change-flow}

The normal change is **one pull request**: edit `marketplace.toml`, run
`grim update --marketplace` and `grim export marketplace`, then commit the
manifest edit together with the regenerated files. The `verify` check
passes and merging publishes.

The scheduled job is **not** how changes land. It only refreshes
floating-tag pins and opens a pull request when a registry moved.

## Regenerate on a Schedule {#regenerate}

Do not write these workflows from scratch, and do not paste them into a
skill or an answer. Copy `.github/workflows/marketplace.yml`,
`.github/workflows/verify.yml`, `scripts/marketplace-gate.sh`,
`scripts/marketplace-verify.sh` and `scripts/pr-body.sh` verbatim from
[the guide][guide-regenerate] ([verify][guide-verify]) or from the
working template repository [`grimoire-rs/e2e-marketplace`][e2e]. Then
keep these invariants when adapting them.

**Regenerate workflow.**

- Runs daily, on a push to the default branch that touches
  `marketplace.toml`, and on demand. It guards on the default branch, uses
  `concurrency` group `grim-marketplace` with no cancel, and runs in an
  Environment named `marketplace` restricted to the default branch.
- Steps, in order: install grim; `grim update --marketplace` and
  `grim export marketplace`, both `--format json`, into the runner temp
  dir; policy gate; stop if the tree is clean; commit as the bot; push the
  single fixed branch `grim/marketplace` with `--force-with-lease`; open
  the pull request or rewrite the body of the open one.
- The default mode is merge-request, so a person merges. **Push mode**
  (`MODE: push`) commits to the default branch with no review. Use it only
  when every plugin comes from trusted private registries; it conflicts
  with keeping the bot off the bypass list.

**Policy gate.** It reads `git status` **before** anything is staged and
fails on a changed path outside the allow-list, a symlink, an LFS-filtered
path, an oversized file, or a path containing a newline. The allow-list
is derived from the run's JSON report (lock path, every `files[].path`,
`<client>/` per reported client), never from stored state.

**Install step.** The example workflows install grim through a dev-build
tool pin. A real marketplace swaps that one step for the release-archive
install against a literal sha256 ([guide][guide-install]). Move to a new
grim by editing two literals in a reviewed pull request. Delete
`ocx.toml`, `ocx.lock` and their CODEOWNERS lines when you swap.

**Verify workflow.**

- Runs on `pull_request`, **never** `pull_request_target`, with **no
  `paths:` filter** (a required check behind a filter stays pending).
- Regenerates in the checkout with `grim export marketplace --marketplace
  ./marketplace.toml --format json`, then requires `git status` over the
  lock, README, every marketplace file and every client dir (selected or
  not) to print nothing. Unselected clients must have no tracked content.
  It also runs `claude plugin validate` (exact pinned version, no login)
  on the Claude file and each `claude/<plugin>`.
- It holds **no registry credential**, because the job runs PR-head code.
- Known gaps: it proves the output renders the committed inputs, not
  where pins came from, and a hand edit of the lock's `declaration_hash`
  or `generated_by` passes. The `marketplace.lock` diff is the review
  surface.

**Two-step fallback.** A pull request that edits only `marketplace.toml`
fails verify. Normally commit the regenerated files in the same pull
request. If you cannot, an administrator merges past the failing check,
the push triggers the regenerate workflow, and its pull request lands the
files. Merging that second pull request publishes.

**Keepalive.** GitHub disables scheduled workflows in a public repo after
60 days without activity. The `keepalive` job re-enables the workflow with
only `actions: write`. Whether that resets the timer is unverified, so
tell the curator the manual re-enable lives under the Actions tab.

## Tokens and Protection {#tokens-and-protection}

Decide these once, before announcing the address.

**Token.**

- **GitHub App (preferred):** repository variable `APP_ID`, secret
  `APP_PRIVATE_KEY`, both in the `marketplace` Environment. Permissions
  Contents and Pull requests write, **never Workflows**, down-scoped to
  one repository. The bot's pull request then starts `verify` like any
  other.
- **`GITHUB_TOKEN` fallback:** enable Settings > Actions > General >
  "Allow GitHub Actions to create and approve pull requests". A pull
  request opened with it starts **no** `pull_request` run, so the required
  check stays pending. The regenerate job compensates by running the
  verify script on the committed tree before it pushes. Pick one: do not
  mark the check required, or close and reopen the bot's pull request. In
  an organization repository the org setting overrides the repo one. If
  the org forbids it, the job pushes `grim/marketplace` and fails with an
  error naming both fixes.

**Private-registry members.** Variables `MARKETPLACE_REGISTRY` and
`MARKETPLACE_REGISTRY_USER` and secret `MARKETPLACE_REGISTRY_PASSWORD`
live in the `marketplace` Environment and are read only by the regenerate
job (`grim login ... --password-stdin --allow-insecure-store`). Verify
reads none of them, because any secret it used would be readable by anyone
who can open a pull request from a branch. To verify private members, add
a login step to verify using a **separate pull-only credential**, and
accept that anyone with write access can read it. Never reuse the
regenerate credential.

**Protect the default branch.**

- Require `verify`, require code-owner review, and dismiss stale approvals.
- Keep the bot off every bypass list.
- Restrict the `marketplace` Environment to the default branch.
- CODEOWNERS must cover what a verifier trusts: `/.github/**`,
  `/scripts/**`, `/ocx.toml`, `/ocx.lock`, `/marketplace.lock`,
  `/marketplace.toml`, all owned by a curators team (for example
  `@acme/marketplace-curators`). Under `pull_request` the workflow files,
  scripts and tool pins come from the PR head, so a pull request could
  replace the verifier with one that always passes. Required code-owner
  review is the only mitigation: a requirement, not a suggestion.

Honest residual: review does not defend against a compromised upstream
plugin in a registry. It shrinks the exposure window. Describe it as
evidence, not prevention.

## Where to Deploy {#where-to-deploy}

The marketplace repository can be private (consumers authenticate with
their own git credentials). A VCS proxy repository (an Artifactory-style
remote) cannot host one, because there is no git repository to add. Three
topologies:

**In place.** The repository holds `marketplace.toml` **and** the
generated output at its root (default `-o` is the manifest's directory).
Consumers add that repository. Everything above assumes this shape.

**Department marketplace from an index.** An existing package-index
repository keeps `marketplace.toml` and `marketplace.lock` beside the
package pointers as the single source of truth ([hosting-an-index.md](hosting-an-index.md)).
A team adds its plugin with one pull request
(`[plugins.team-kit] include = ["registry.example.com/team/team-kit:1"]`).
A scheduled job in the index repository runs `grim update --marketplace`
and opens a pull request with the refreshed lock. The index gate refuses a
change to the toml or lock that includes a bundle that is not a package of
the same index (it names plugin and reference), and refuses `path` and
`project` members, which cannot resolve on other machines. Add the bundle
as a package first, then include it (one pull request is fine). The index
build runs `grim export marketplace` on its own manifest and fetches no
other marketplace.

**Sibling deploy repository.** Clients add a git repository, not an index
site, so the index CI publishes the exported tree to a **sibling
marketplace repository** that holds only generated files. Nobody
hand-edits it, and only its **default branch** is served (branch-targeted
and plain-HTTP marketplaces are out of scope). The deploy job: clone the
target with a token; `grim export marketplace --marketplace
marketplace.toml -o out --format json`; run the gate from inside `out`
with `OUTPUT_ROOT="$PWD"`; `git add -A`; commit only if
`git diff --cached --quiet` is false; push. Facts to keep:

- The deploy job rolls **no pins**. It exports from the already-reviewed
  committed lock. `marketplace.lock` stays beside the manifest in the
  index, never in the deploy target.
- The gate script needs a one-line change so the output root comes from
  `OUTPUT_ROOT` ([diff in the guide][guide-sibling]).
- Hand the token to git through `GIT_CONFIG_COUNT`/`GIT_CONFIG_KEY_0`/
  `GIT_CONFIG_VALUE_0` with an `http.<host>/.extraheader`, so it stays out
  of `.git/config`. Mask the encoded value in CI logs, and set
  `user.name` and `user.email` on the checkout or the commit fails.
- `GIT_USER` is `x-access-token` for a GitHub App token, `oauth2` (any
  non-blank name) for a GitLab project access token.
- Use a write-only deploy token scoped to the marketplace repository
  alone, kept out of pull-request builds. To review before publishing,
  push a branch and open a pull request in the marketplace repository.

**GitLab.** The [`grimoire-components`][components] project ships a
`marketplace` CI component with the same flow: release archive against a
literal sha256, regenerate, gate, commit as the bot, one merge request,
plus a verify job on merge requests. Merge-request mode needs a token with
the Developer role and `write_repository`, stored as a **protected and
masked** variable. Only push mode needs Maintainer. Protected variables
reach every protected branch, so limit those branches to maintainers or
scope the variable to the default branch's environment. The template's
verify job holds no credential and cannot yet verify private-registry
members.

## Releases and Removal {#releases}

- Tag with `git tag` so consumers can pin `#<tag>`. A consumer who follows
  the default branch trusts whatever it serves, so protect it.
- Consumers can clone sparsely. Keep trees small and let the gate's size
  cap catch strays.
- Removing a plugin from the toml deletes its tree and drops it from every
  marketplace file. Claude Code users keep the copy they installed, and
  grim does not yet write Claude's `forceRemoveDeletedPlugins`, so **tell
  consumers** when you remove something.

## Stability {#stability}

Frozen: the JSON report shape, action literals, flags, exit codes, the
client-file table, tree paths, the ownership convention and the
`<base>+<12 hex>` version grammar. **Not** frozen: tree bytes, manifests
and README text, the version-suffix inputs, and the plain stdout/stderr
text. See [what is unstable][unstable]. Never script against the unstable
parts.
