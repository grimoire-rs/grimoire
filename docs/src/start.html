run your own index

Stand up a package index in about ten minutes.

An index is the phone book grim browses — pointers into the OCI registries you already have, compiled to a static site your forge serves. No index server, no database, no account. Follow the steps; each one is a few commands.

first, where does it live

Everything below switches with this. One repository runs on one forge, so the scaffolder renders one pipeline, not both.

Open grimoire-rs/index-template, press Use this template → Create a new repository, and name it. The name shows up in the published URL.

your repository 
$ git clone <the URL GitHub gave you> && cd <repo>
Private repository?

It works, but GitHub only serves a private repo's Pages site on Enterprise Cloud. Without it, hand consumers the clone URL and skip Pages entirely — grim reads an index straight over git.

GitLab has no "use this template" button for a repository on another forge. Create an ordinary blank project and clone it; the scaffolder writes into it next.

your project 
$ git clone <the URL GitLab gave you> && cd <project>
Self-hosted instance?

Same command with your own host. Nothing in the scaffold reaches out to gitlab.com.

The template ships one script. It installs the toolchain, then runs the scaffolder in place:

$ npm install && npm run setup

Run the scaffolder in the clone. It ships on npm as @grimoire-rs/indexer and needs Node.js 22.14 or newer — nothing installed globally:

$ npx @grimoire-rs/indexer init .

It reads the origin remote, so the two hard questions — which forge, and where the site is served — already have the right answer waiting. Most of the rest is Enter.

The registry host is the one answer worth reading. It is the committed allowlist the contribution gate bounds every entry by, so widening it later is a reviewed commit rather than a CI variable.

Publish your own skills from this repository too?

One question decides the layout. Answer yes and you get a skills/ tree, a publish.toml, and a release pipeline — one repository holding the packages, the catalog that lists them, and the CI that ships both. Then it asks when a release happens.

TriggerFires on
tagA v* tag. Cutting a release is a deliberate act
default-branchEvery push to the trunk. Bumping the version in publish.toml is the release

Either way the job publishes and then announces into the index beside it, and grim publish skips versions the registry already has — which makes the every-push option reasonable rather than reckless. Change your mind later by editing ci.publish and re-rendering.

Say no if other people will publish into this index. In the combined layout this repository's own announce is opened by its CI token — which triggers no workflows on GitHub, so that one pull request arrives past the gate and wants a human. It also needs Settings → Actions → General → "Allow GitHub Actions to create and approve pull requests", off by default.
What it writes →

The same renderer CI runs, on your machine, with hot reload:

$ npm run dev

An empty catalog is the correct answer — you have not added entries yet. What you are checking is the branding: title, logo, and the "add this index" block that hands visitors the command to consume you.

Branding keys →

In the repository, open Settings → Pages and set Source to GitHub Actions.

Do it now, before the first push. Until the source is set, the pages workflow runs green and deploys nothing — a failure mode that looks like success.

Any credentials to set up?

None. No deploy key, no gh-pages branch, no personal access token — the workflow uses the built-in GITHUB_TOKEN.

Nothing to enable. The pages job publishes public/, and GitLab serves it at https://<group>.gitlab.io/<project> as soon as the job succeeds.

Private instance that refuses remote CI includes?

No change needed — the pipeline is committed in this repository and includes nothing from elsewhere.

Deploy notes →

Commit everything the scaffolder wrote — including package-lock.json. CI installs from it, so it is not optional.

$ git add -A && git commit -m "chore: bootstrap the index" && git push

That is the deploy. The pipeline enriches from the registry, builds, and publishes; your index is live at the base URL the scaffolder printed.

Never hand-edit the workflow files

The pipeline is committed here, not fetched — rendered from the ci block of index.config.json. Change that block and re-run npm run ci. A generated check re-renders and diffs on every push, so a hand-edit fails loudly instead of quietly forking your pipeline.

Changing the CI →

An index other people publish into has to answer one question mechanically: is this author allowed to write this entry? The validate job is that answer. Exit 0 means eligible to merge; anything else means a human looks.

It refuses a change that:

  • touches any path other than index/<host>/<ns>/<pkg>/metadata.json,
  • claims a namespace whose forge owner is not the author — checked against the numeric account id, so a recycled login cannot inherit it,
  • fails the metadata schema,
  • points at a registry host outside index-policy.json, or
  • names an OCI reference the registry cannot actually serve.

It judges all of that against the committed state of your repository, never the state the change proposes — so a pull request cannot allowlist its own registry host in the same commit.

That rests on one assumption: registry namespace equals forge namespace. True for ghcr.io/<github-owner>, which is why the gate can be trusted to auto-merge there. If your registry's namespaces are not your forge's — a self-hosted registry, a shared vendor account, a mirror — leave auto-merge off and review by hand.
How does someone claim a namespace?

They do not — there is no claim step. The <namespace> segment of the path is looked up on your forge as a real account, organisation or group, every run. A first contribution is judged exactly like the hundredth; nothing is granted by an earlier merge, and nothing is stored. Names you never want claimed go in reservedNamespaces.

Nothing merges itself unless you ask. Auto-merge is off in a fresh scaffold; the gate reports, and you decide.

Require the check, or let it merge on its own

Require it: Settings → Rules (or branch protection) → require the status check named validate.

Add the check and the rule together. Requiring a context that never reports blocks every pull request forever, and looks exactly like the gate rejecting the contribution.

To let passing contributions land by themselves, set "autoMerge": true in the ci block and re-render with npm run ci.

On GitLab the gate is advisory, and that is structural. A merge request supplies its own .gitlab-ci.yml, so a contributor can delete the job that judges them; and a fork's pipeline runs in the fork. Enforce it instance-side — a required merge check, protected-branch approval rules, or a compliance pipeline — or review merge requests by hand.
Why is auto-merge GitHub-only?

Merging an unreviewed contribution unattended needs a gate a contribution cannot edit, and GitLab has no equivalent of pull_request_target.

How the gate works →

Point grim at the published URL. From then on it is a browse source like any other, alongside the public index rather than instead of it:

alias and URL are yours 
$ grim config registry add <alias> --index <your Pages URL>

You do not have to assemble that by hand — your published index renders the finished line on its own front page. That is what you hand to anyone who asks how to use your index.

$ grim search review

Then put something in it. Publishers announce into your index by pointing their publish.toml at it and running:

$ grim publish --announce

That pushes the packages to the registry and opens a pull request against your index with the pointers — forking automatically when the publisher has no push access. For an index you curate yourself, write the metadata.json by hand; the shape is four fields and an owner.

three things people ask

Every package says "No README available"

That is an index that has not run enrich. An index stores pointers only; the pipeline reads the registry for READMEs, versions and logos before each build. Set "enrich": false in the ci block for a pointers-only site that never leaves the runner.

Can I add an index to a repository that already exists?

Not in a subdirectory. index/ is resolved from the repository root by both the gate and the generated pipeline, so an index tucked below it builds locally and then rejects every contribution. Give it its own repository — that is the supported shape, and it costs nothing on either forge.

Do I need the scaffolder at all?

No. A git repository containing index/<host>/<ns>/<pkg>/metadata.json already is an index — grim walks the tree over git, no build and no CI. Reach for the scaffolder when you want the browsable catalog, the contribution gate, or both.
