# Grimoire CLI Commands — Quick Reference

Concise index of `grim` CLI commands. Implementation lives under
`src/command/` — read the source for return types, call sites, and report
column formats.

Index of shipped `grim` subcommands — keep in sync with `src/command/`
(one file per subcommand) and `docs/src/content/docs/commands.md`.

## Command Surface

| Command | Purpose |
|---------|---------|
| `grim init` | Write a fresh `grimoire.toml` in the current directory; `--registry <ref>` seeds the default `[[registries]]` entry |
| `grim add [--kind …] [--name …] [--no-install] [--force] [--[no-]trust-workspace] <ref>` | Declare a skill/rule/agent/mcp/hook/settings/bundle in `grimoire.toml`, pin it in the lock immediately, and (by default) materialize just that entry into the detected clients; the relock is `Refresh::Nothing` with its proof against the pre-edit declaration (`Prior::edited`), so every other pin carries, every path source re-packs, and the target resolves unless the lock holds a pin that answers its reference, as under `grim lock` (owner decision OD-2). An add that kept the target's pin, a re-declared reference, a new key whose held pin answers it, or a tagless pin the edges onto it stamp with the typed tag, its tag read or not (`stamped_unread`), still reports `added`, and one stderr note says the pin was kept and names `grim update -- <name>`, which moves the pin to what its tag names now or says why it cannot, or declaring a reference that exists if that tag is gone, with the run's `Invocation` (`grim --global` or `grim --config <path>`). A pin kept over a refusal (`ExpandedGraph::kept_over_refusal`: a cycle back at another digest or a gone tag below the moved manifest, each kept at exit 0 since RF8; an unreachable registry, a refused credential, a timeout or a graph cap keeps its exit) gets the note that says that manifest does not resolve and that the update says why. Plain output prints one stderr line naming each pin the run moved, the target included, as it does for `pulled in`; a moved `[[bundle]]` pin has no `moved` row and gets `warn_moved_bundle_pins`' line on either format; `dropped` pins keep their files, and the line names `grim uninstall` before the bare update that also moves every pin. An unreadable lock refuses before the config is written, and a failed relock or lock write restores it. `--no-install` stops at declare + lock; `--force` overwrites a locally modified artifact / untracked destination with `grim install --force` semantics (inert with `--no-install`), scoped by `lock::closure::force_nodes` to the target or a bundle's members (nested bundles' via the lock's snapshots), never a dependency it merely requires — refused dependencies are named in the error. A hook declares and locks normally even with the feature flag off — the install half skips with a warning and `status` reads `gated`; the kind-inference path deliberately carries **no** flag check, so flipping the flag never requires re-running `add`. A settings package does the same under `[options.experimental] settings`; with that flag on and settings in the lock, `add` refuses a conflict among armed packages (78) before it saves the lock. **`add` is one of exactly three write seams for the workspace consent record** (with `grim hook allow` and an accepted prompt): typing a ref *is* the declaration gesture (`adr_artifact_trust_model.md` decision 1), and a bundle records the **resolved** hook member set so a later-added member drifts rather than arming silently. **Proposed, awaiting the owner:** the timing and reach that follow are goal-loop decisions RD-3, RD3-6 and "TUI consent" of the lock-pin plan. The Proposed blocks after `adr_hook_workspace_consent.md` decision 4 record them, and the shipped code follows them. The write happens ahead of the install for both kinds (`hook_consent::gesture`), and covers only the target and the hooks and settings packages it newly reaches over edges the relock resolved: a child that is not carried, is not a pre-edit direct key, and settled at the repository the edge names (`resolved_reach`, `Added::consents_to`). A lock row may inform a report, never a consent record. A carried target is its own whole reach, and a carried typed hook or settings package consents only while the tag its pin records still names its digest, one tag read within 10 s, or for a tagless pin while its repository serves the digest (`kept_pin_check` in `consentable_keys`, each key gated by its own kind's flag); a moved tag warns that the tag now names another digest than the pin the add kept, naming `grim update <name>`, which moves the pin or says why it cannot, then `grim hook allow`, or `grim consent allow` for a settings package, which takes the lock as it stands (over a refusal the warning says that manifest does not resolve; `PinCheck::MovedUnresolved`). Offline an edge counts only when the parent's stored manifest lists it, or the parent is a path this run re-packed (`stored_reach`). An add that consents to no new hook adopts the record as it stands for hooks (`gesture`), so it never disarms a hook the record covers; settings keep their per-package answer. A failed install keeps the declaration, the lock and the consent, so the next non-interactive `grim install` reads no drift. A relock or lock write that fails rolls the declaration back and records nothing, and a record write that fails arms hooks on the record as it stands. `--no-install` records the same hook set (`record_without_install`; a settings package is not recorded there and is asked about on the next `grim install`) and resolves no policy, so it adds no exit. A hook the gesture does not cover stays outside the record, which is drift until `grim hook allow`. `--trust-workspace` writes nothing itself, the gesture still records, and only `--no-trust-workspace` keeps the record out. `dropped` lists pins the add took out of the lock, and a rollback leaves a config someone else saved during the run and warns |
| `grim lock` | Bring `grimoire.lock` in line with `grimoire.toml` (after hand-edits; `add` locks what it declares) **without moving a pin**: `Refresh::Nothing` through `target_lock`, so a node resolves only if it is new or its request no longer matches the pin, and every path source re-packs. `lock::pin_rule` owns what a pin answers (`adr_lock_pin_stability.md`, § The pin rule). Under a proof every recorded edge of a key no declaration holds answers, in any repository, and an unrecorded edge never carries a pin into a new one. On a stale lock a pin naming a recorded edge carries every recorded edge; a pin naming none resolves once, and on `Refresh::Nothing` `unvouched_warning` names what moved. Nothing writes an empty `declaration_hash`; one read from disk is plain stale. A hand-deleted direct line, or a `grim remove` of a direct line that held a conflicting edge off, stays at exit 0 where a fresh resolve exits 78 (a consequence of owner decision OD-1), `update` exits 78, and `status --check` does not see a shadowed edge at a tag the pin never held. `pinned` records the resolving tag (`[[bundle]]` keeps its sibling `tag`); a clean pre-change lock is stamped with zero tag resolves; under a proof a tagless pin on a key no declaration holds also answers an edge in its repository from a parent read as the proof shows it (`Graph::read_as_proven`, `pin_rule::answers_listed_edge`) whose row records that edge at the digest read (`pin_rule::WalkedEdges`): a bundle with no `[[bundle]]` row keeps the pin, and a row that records no edge, as grim 0.15.1 writes for every dependent, lists none, so its edges settle as a fresh resolve does; a tagless pin nothing vouches for resolves once with a warning. Reach for a ghost edge comes from `effective_set::reached_rows`, where a key new to the proof is a leaf, so a new key leaves the walk known and a key the proof still declares with no row leaves it unknown. A carried node still reads its manifest by digest, store first; a kept pin is not re-verified against its tag, which is `status --check`'s and `update`'s job. Rows carry `action` (`locked`/`unchanged`/`dropped`, the last for a pin no longer in the lock) and `disposition` (`added`/`carried`/`moved`/`dropped`); a stamp is `carried`. An unreadable lock refuses (78/77/74) naming the recovery that keeps the pins, since deleting it moves every pin; a carried pin whose manifest neither the registry nor the store holds exits 79 naming `grim update <name>`, and a reference that exists plus `grim lock` when the tag is gone too or a digest names the pin, each with the run's `Invocation` (`grim --global` or `grim --config <path>`). A moved `[[bundle]]` pin gets one stderr line after the save, `bundle '<name>' moved its pin from <old> to <new>`. Offline, a carried bundle the store lacks reads its members from its lock row, and a run that moved a pin through the tag cache warns from `target_lock`, so on every relock path, a moved `[[bundle]]` row named too. A marketplace export stage warns per part, naming the plugin and every row below a followed bundle, nested ones included. A part keeps its bundles' pins in `bundle_tag` (owner decision OD-3), and only a run that selects the bundle records one (a whole update, a `<plugin>` pick, a `<plugin>:<bundle>` pick of it, the export stage; a pick of a bundle that nests one moves it only where the part records no digest for it, and otherwise keeps the nested bundle and the bundle's members at their pins at exit 0, ratified by the owner on 2026-11-08 (the nested bundle keeps its recorded digest); a nested bundle a row stamps with no digest is held and records none. The picked bundle's digest lands on each row that carries its stamp, as a whole update does, and a bundle no row stamps passes its stamp to every row below it, a direct include's held row too, its pin unchanged. A recorded nested bundle keeps its digest below an unrecorded parent too, so `grim export` no longer moves it (H2 closed). A pick that would keep a dependent beside another version of a row or bundle it requires exits 78 (`ResolveErrorKind::HeldRequirement`, owner 2026-11-08, deviation row 25), on proof from the pin rule's evidence or a manifest or tag read that succeeded; a failed read refuses nothing by itself, and a held bundle requirement counts with every bundle its list nests, each binding it is listed under, and every row it lists where the pick reaches no bundle of that list's repository; a held edge is matched to the run's bundle by binding name, else by the one bundle of its repository the pick reaches, and a tag that fails to read or reads as the run's own digest falls to the part's record of the move; `HeldRequirement` and `MarketplacePinGone` name the whole-plugin update only with its cost, that it moves every pin of the plugin whose tag moved), so a part pick reads the part's bundles from their stamps (`TargetLock::part`, `PartBundles`, `lock::part_stamps`, `resolve::part_bundles::sort_part_bundles`), holds every row outside its selection's closure and the requirement of a held row, and writes one digest for each bundle pair (`PartBundles::write_stamps`, `settle_digests`; the member check still reads every bundle the run read); a `<plugin>:<member>` pick keeps every row outside its selection byte for byte and warns on a kept tagless row in a part that records a digest; offline, a recorded digest the store lacks exits 81; an include the part already holds reads no tag. With `[options.experimental] settings` on and settings in the lock, it exits **78** on a conflict among **armed** settings packages before it saves — consent from `settings_policy(.., None)`, so it asks nothing and records nothing, and only a package the record covers loads a layer (a fresh clone locks as before). That branch reads install state, so a damaged state file then exits 74; with the flag off it reads none. `adr_lock_pin_stability.md` |
| `grim config get\|set [--dry-run]\|unset\|list <key>` | Read and write `grimoire.toml` settings (`[options]`, `[options.tui]`, `[options.vendors.<name>]`) and registry fields via dotted keys; `list` dumps explicitly-set values for the active scope (never merged across scopes); `list [--all]` lists every supported key incl. unset, with JSON items carrying type/title/description/default metadata. `set --dry-run` validates and reports (report gains always-present `dry_run`) without acquiring the write lock or touching the file — same 64/65/79 error envelopes as a real `set`; no `unset --dry-run`. Exit codes: unset `get` → 1, unknown key → 64, bad value → 65. |
| `grim config registry add\|set\|rm\|use\|show\|list\|fields` | Registry lifecycle for `[[registries]]` entries: `add <alias> --oci\|--index <url> [--include <glob>]… [--exclude <glob>]… [--default] [--insecure]`, `set <alias>` (edit in place — same flags as `add` plus `--clear-include`/`--clear-exclude`/`--no-insecure`; applies only the flags given, keeps the entry's position, `--oci`/`--index` swaps the kind clearing the other side, `--default` cannot unset, `--insecure`/`--no-insecure` can; naming no field → 64), `rm <alias>`, `use <alias>` (at-most-one-default, clears prior), `show <alias>`, `list`. Alias not found (`set`/`rm`/`use`/`show`) or dup on `add` → 64. `--include`/`--exclude` are repeatable and **never comma-split** (a comma is glob alternation) — `add`/`set` are the only CLI paths writing a multi-pattern browse filter; `config set registry.<alias>.include` stores exactly one pattern, and `get` comma-joins for display and is not round-trippable. Clearing a list has two supported routes, both silent at any list length and both writing the emptied list as an absent key: `registry set --clear-include`/`--clear-exclude` (conflicts with its own list flag → 64) and `config unset registry.<alias>.include`. `registry set`'s write report carries the always-present `fields` array — one element per field written, in `RegistryField::ALL` order, `{field, action: set, value}` or `{field, action: cleared}` (no `value` key); `[]` on every other write verb. `show`/`list` carry always-present `include`/`exclude` arrays (`[]` unfiltered; plain cell is counts, `—` unfiltered). **No per-registry field answers hook arming** — that question is workspace-scoped (`grim hook allow`, a record under `$GRIM_HOME/hooks/consent/`), never a registry field: the branch's `trust_hooks` tri-state and its emit-only-when-true serializer hazard are **gone**, along with the scope-precedence table and the bare-host/`insecure`/`index` matching rules that keyed a *name* on the publisher side. `fields` lists the 6 addressable per-registry field names (`oci`, `index`, `default`, `include`, `exclude`, `insecure` — **append-only**, positions frozen; `RegistryField::ALL` is back to the six shipped names in their shipped order) and their static type/title/description metadata — no `Context`, no scope resolve, no lock, works with no `grimoire.toml` present (unlike every other `registry` verb) |
| `grim install [<path> [--kind skill\|rule\|agent]] [--[no-]trust-workspace]` | Materialize every locked artifact into the configured AI client(s); scope clients via `--client`. The optional positional is a **dev-install** path only (`./`, `../` or absolute; a registry reference → 64, declare it via `add`): it packs a local skill, rule or agent and renders it without touching `grimoire.toml` or `grimoire.lock` or requiring a fresh lock, recording a `dev`-marked install (listed by `status`, refreshed by `update`, never pruned, removed only by `uninstall`); a `(kind, name)` that collides with a declared binding → 64. Refuses to overwrite an untracked pre-existing destination (65) unless `--force`; adopts identical content into the record. **Hooks are the one kind declined on policy rather than capability**: a locked hook arms only past the `[options.experimental] hooks` flag *and* the resolved workspace's consent record, otherwise `InstallOutcome::Skipped` + one warning naming the single cause, exit stays 0. **`install` never writes a consent record** — it converges what is already declared, and a cloned repo's `grimoire.toml` is not the user's gesture; that negative is the T3 control and is asserted by an acceptance test, not by visibility. Global scope is always consented and carries no record. A hook whose pinned registry host is non-loopback and reached over plain HTTP does not arm at all (`insecure-transport`), independent of consent and unescapable from any file. On Windows only Claude arms; every other client gets `platform-unsupported`: install registers nothing for it and warns once per client when the flag is on and a hook is recorded. `--trust-workspace` / `--no-trust-workspace` (visible aliases `--trust-hooks` / `--no-trust-hooks`; also on `update`/`add`) is a clap `overrides_with` pair resolving to one tri-state (`HookTrustOpts`); it arms hooks and applies settings, or refuses both, **per invocation**, writes no record, and does **not** enable either feature flag. Settings take the same gates (flag, then consent at project scope; global always consented): a gated package writes and removes nothing, exit 0. **The pair beats the consent record in both directions** — owner decision 2026-08-28, N4: a flag typed on this run is the most explicit answer there is, and no file can type one. Convergence derives its own client set from the hook-capable roster and ignores the caller's, so every command is idempotent and self-healing regardless of what it was asked to do — do **not** narrow it to the clients a command happened to touch |
| `grim status` | Report each declared artifact's state (installed, outdated, modified, plus `gated`/`not-armed` on hook and settings rows and the hook-only `untrusted`) with bundle provenance; a hook or settings row carries the always-present `arming` array (`{client, cause, message, transient}`, sorted by client, `[]` = armed everywhere) whose `cause` is the closed kebab-case `HookArmingCause` set and is the field consumers branch on — never `message`. A hook armed via `--trust-hooks` reports `installed`, not `not-armed`: `hook_arming` consults the **dispatch table first** (`armed_rows`, via `existing_root_token` so no key material is ever minted on a read path), because the table is the machine-local arming authority and is derived rather than recorded. The consent record alone would under-claim for every `--trust-hooks` run, which is the state every CI run is in. Consent contributes two `gated` causes — `workspace-not-consented` (no record) and `consent-drifted` (a record that no longer covers what the scope declares — a new binding or a new repository; a *version bump* is deliberately not drift) — keeping the state token the registry-scoped cause they replace already shipped with, because both are deliberate policy answers rather than something grim failed at. The relocated plain-HTTP gate is `insecure-transport`, orthogonal to consent and `not-armed`: grim will not work around it, so it groups with `grim-home-relative` rather than with the two consent causes. `platform-unsupported` (a client not yet verified on Windows, `not-armed`) is the same kind of host-level refusal, ranked after the flag and consent gates, so a Windows user sees the gate's cause until those clear. A settings row reuses `HookArming` through `settings_arming` (`hook_arming` untouched) with the same flag, consent, `GRIM_HOME` and `not-registered` causes plus five of its own: `no-applicable-settings` (`gated` only when nothing applies to any selected client, else a note), `client-config-absent` (a per-client note), `local-file-tracked` (advisory, never moves the row), and the global root fence's `settings-root-relative` and `settings-root-in-workspace` (`not-armed`: a global settings file whose config directory is relative, or lies inside the repository the command runs in); its `outputs` carry an always-present `element`, and its `outputs_pending` stays `[]`. The split closes issue #92 on the axis that turned out to matter — never-consented vs consented-then-drifted, rather than never-granted vs explicitly-opted-out; JSON items carry always-present `direct` (declared in the manifest) and `required_by` (the declared artifacts that reach it; `null` = the lock graph cannot be computed offline, `[]` = none), whose `source` literals now include the dependency-reached ones; JSON items also carry always-present `clients_missing`/`clients_extra` (configured-vs-recorded client drift, local only) and always-present `outputs_pending` (`[{client, path}]`, sorted by client; materialization drift: what `grim install` would write now that the record does not cover — two causes, a new client or a layout move; a deleted file is **not** one of them, it reads `state: missing`; reported under autodetect too, since it asks what install would do rather than what was configured; never moves `state`, never affects the exit code; derived from `install::expected_outputs`, the same seam the installer's no-op check uses). `--check` (network, opt-in) adds a live catalog load populating `deprecated`/`replaced_by`, plus a fresh per-artifact re-resolution populating `update_available`, which a dependency row answers by a digest-bearing edge if one holds it, else the tag its pin carries, else the smallest recorded edge (`dependency_reference`); it answers for the recorded reference, so a moved parent that switches or drops the edge, or a diverging diamond, is not predicted, and `null` means no readable edge or a failed resolve; a dependency row answers only when each parent recording an edge onto it is in the local store at its pin and its stored manifest lists the same edges (`rows_the_store_does_not_confirm`, store-only access), else `null`, while a bundle member row still reads the lock's `[[bundle]]` snapshot id; a nested bundle has no row and never flips `update_available`, which answers for the row's own pin alone: `moved_nested_bundles`, the last item key, lists the moved bundles a row reaches through nodes with no row, `[]` when none, `null` when a reached bundle has no answer and none moved, or when the graph is incomputable or the walk passes its budget, and plain output prints one stderr note per row with an update and per moved nested bundle, naming the run's `Invocation` (`grim --global` or `grim --config <path>`), `grim lock` first on a stale lock, and no command for a key the lock records under more than one reference. Such a key re-resolves every recorded reference (`row_references`); references naming different digests, or one vanished beside one that resolves, read `null` in any listing order, with a note that `grim update` exits 78 until `grimoire.toml` declares one (`split_note`). One re-resolve has a 30 s deadline, a run sends at most 2048, rows first, and stops re-resolving at 300 s (`CheckLimits::run`, one warning counting the rows and nested bundles left unanswered), and a tag outside the OCI grammar sends no request, each reading `null`; top-level `checked` gates all four — `false` forces them `null` on every item |
| `grim context` | Read-only introspection of the resolved invocation context: scope, config/lock/state paths (+ existence), effective client set (names only), registry browse set, default registry, offline (+ source). `registries[]` carries always-present `include`/`exclude` browse-filter patterns (`[]` unfiltered, and `[]` for every entry under `--registry`) plus an always-present `insecure` bool — the **authored** `[[registries]]` field, not the effective transport (a host reached over HTTP via the loopback default or `GRIM_INSECURE_REGISTRIES` still reports `false`), so it and `config get registry.<alias>.insecure` always agree **except under `--registry`**, whose synthesized entries carry no authored fields and report `false` for every row — a statement about the browse set only, since `--registry` never narrows the plain-HTTP transport set; `registries[].catalog` is always present, the source's sync state read from the sidecar alone with no request (`null` when no readable sidecar of this version exists for the source); plain row appends `, insecure` only when set, then `, N include, M exclude` counts, both omitted entirely when unset/unfiltered. Exits 79 outside a project without `--global` |
| `grim search [query]` | Searches the registry catalog: the artifact name (repo leaf) and keywords match fuzzy subsequence (skim score ≥ 12/char, with an exact/whole-word name bonus); summary, description, and the namespace path match by word prefix (a term matches the start of a word; a term carrying a separator like `-`/`.`/`/` must appear contiguously); the registry host is not searched by a plain word, but a term containing `/`, `.`, or `:` matches the full reference including host. Shared with the TUI `/` filter and MCP `grim_search`; empty query lists all. Results are ranked by relevance and cut below `options.search_min_relevance` percent of the best (default 50, `0` off, max 100 — measured against the best remaining hit when nothing matches by name); hidden rows are reported on stderr (`N weaker matches hidden; set options.search_min_relevance to 0 to list all`). `--sort <name\|updated\|rating\|downloads>` (also on `grim tui`) reorders only the kept set — never widening what the cutoff dropped — applying the shared `catalog::browse_sort` comparator: `name` ascending case-insensitive · `updated` date descending, undated last · `rating` upvotes descending then date descending, **unrated last, never as 0** · `downloads` total descending then date descending, **uncounted last, never as 0**. Every mode is total within one source — the final tiebreak is the fully-qualified ref — and `grim search` adds the source's declaration position as the last key, since two sources can serve one ref. Given with a query it **replaces** relevance ranking; omitted, ordering is unchanged (relevance when queried, registry order otherwise), so the flag is additive. JSON items carry `rating` as always-present `{up, url}`-or-null (`target` deliberately **not** emitted — opaque forge node id, and no consumer can act on it) and `downloads` as always-present `{total, as_of, versions}`-or-null (an object, never a bare number, so `as_of`/`versions` could land at all; `as_of` may itself be null; `versions` is the per-release breakdown as an ORDERED array, highest release first — grim sorts by semver so no consumer compares tags — and `[]` when the producer published none; `total` is never the sum of `versions`, since a channel tag carries traffic naming no release; null means **unknown**, never 0, and is the common case — only an Artifactory-backed index publishes a per-artifact counter at all). The two sidecar signals are independent: rated-and-uncounted and counted-and-unrated are both normal. Each source's `include`/`exclude` browse filter narrows the rendered rows at read time (`CatalogScope::Browse`) — the shared catalog cache is never narrowed, `--registry` browses unfiltered, and `grim status --check` uses `Complete` and is never filtered. A mis-aimed-pattern warning logs `registry '<name>': filter admitted <M> of <N> repositories; patterns match either the repository path or the fully-qualified reference, and anchor at the candidate's first segment — see https://grimoire.rs/configuration.html#browse-filters` (warn only, exit stays 0) when a non-empty `include` admits nothing from a group that had rows — **only on the unqueried browse**: `<N>` is post-query rows, so under `grim search <query>` the warning is silent (indistinguishable from a deliberate search for a hidden term). A non-empty `exclude` that removes nothing, and an exclude-only filter that empties a source, both stay silent. An `oci` source lists **every** repository (the `_catalog` walk follows `Link` `rel="next"`, else `last=`, to the end; only a repeated cursor, a mid-walk failure or 128 MiB of names ends it early); an index source is never truncated either (an index over 128 MiB decoded or 100,000 entries fails its fetch with `ok: false` and a warning naming the source). The listing is built before the filter runs, so a filter never widens or narrows it, and `truncated` keeps reporting build-time listing incompleteness verbatim. A long `oci` build is a checkpointed, resumable background job: the process holding the build lock writes partial progress to the cache (first at 64 rows, then on each doubling; rows are served only with full metadata, so an unfetched repository is absent, not bare), every other grim serves the newest checkpoint at once (online or `--offline`) flagged `capped`, an interrupted build resumes without refetching rows younger than the TTL, and a refresh reuses a row whose tag and manifest digest (`OciMeta.digest`, ignored by older grim) are unchanged. `--limit <N>` (`NonZeroUsize`, `0` is a usage error) cuts the printed rows **after** ranking and `--sort`; `--offset <N>` (`usize`, default 0, negative/non-integer is a usage error) skips rows first, so the page is `ordered[offset..offset+limit]` (`apply_page`); MCP `grim_search` takes the same optional `limit` and `offset`. Equal relevance scores tie-break on source declaration order, then the fully-qualified `registry/repository` (the order the catalog hands over, multi-host index sources included), so pages from separate invocations slice one list. The JSON envelope always carries `total` (every match after filter, deprecated visibility, query and cutoff, before `--offset`/`--limit`) and `truncated` (`--offset` or `--limit` removed rows, or a source's listing is incomplete so `total` is a lower bound) beside `items` and `sources` (each `sources[]` entry is `{alias, locator, ok, error, capped}`; `capped` is the per-source answer to "incomplete or just paged", `true` on every page for a listing whose `_catalog` walk could not finish, or whose build is still running or was interrupted — `total` is then a lower bound); no field echoes the offset (`has_more` = `offset + items.len() < total`). A partial page in plain output adds one stderr hint (`showing 101-200 of 600; next page: --offset 200`, emitted from `app.rs`, never under `--format json`); an offset past the end is `items: []`, exit 0. Ordinary scope-resolving `Printable` single-object report (`{workspace, action, hooks}`), wired like `hook list`. `--global` (or a resolved global scope) exits **64**: the global toolchain is always consented and carries no record, so the ask has no meaning — a usage error, not a failed write. | `grim hook revoke [path]` (alias `deny`) | Remove the resolved workspace's consent record. The alias exists because `direnv` — the precedent `adr_hook_workspace_consent.md` cites — calls this operation `deny`, with `revoke` as its own alias for it; the report's `action` stays `revoked`/`not-consented` whichever word is typed, since it names the operation and consumers branch on it. **The alias adds no fourth state**: consent is absent, granted or drifted, and *denied* is deliberately the same state as never-answered — the default is already deny, so a recorded refusal buys silence rather than safety and would leave arming withheld with no cause to report. **Idempotent**: `Removed` / `Absent`, both exit **0** — revoking what was never granted leaves exactly the state asked for, and erroring on the command's most ordinary outcome would be the defect. `--global` needs no refusal, unlike `allow`: global scope never writes a consent record, so there is nothing to remove and the answer is `Absent` (exit 0, `not-consented`) by construction. Global flags (`src/cli/options.rs` `GlobalOptions`): `--format`,
`--color <auto|always|never>` (default `auto`; styles clap help/errors and
`--format json`; `auto` is TTY-gated and honors `NO_COLOR`/`CLICOLOR`/
`CLICOLOR_FORCE`/`TERM=dumb`, `always` overrides `NO_COLOR`),
`--progress <auto|json|none>` (experimental; NDJSON events on stderr),
`--offline`, `--log-level <off|error|warn|info|debug|trace>` (wins over `GRIM_LOG`, whose directives it does not take; an invalid value prints one stderr line and the run continues at `GRIM_LOG` or `warn`, exit unchanged), `--config <path>`, `--global`,
`--registry <ref>` (repeatable / comma-separated).

`login`/`logout` resolve the registry from the positional argument when
given: an argument matching a `[[registries]]` alias substitutes that
entry's locator, anything else is taken as a literal hostname. With no
argument, the resolved scope's registry set supplies the primary —
`--registry` flag > `[[registries]]` default > `GRIM_DEFAULT_REGISTRY` >
project then global `[options].default_registry` — the same
`resolve_registries` chain `add`/`search` use, with `--config`/`--global`
selecting the scope as they do for every other command. Config **is**
consulted on this path; `Context::default_registry()` is a superseded
accessor with no production caller, so do not cite it as evidence
otherwise. The built-in `ghcr.io/grimoire-rs` fallback is deliberately not
substituted here — storing or erasing a credential for a registry the user
never named is a silent surprise — so an otherwise-unresolved set exits 78.
A global config that fails to load is fatal for `login` (78) and degrades
for `logout`, which still recovers the alias map when the file parsed and
only validation failed.
They read and write the docker config at `$DOCKER_CONFIG/config.json`
(default `~/.docker/config.json`) — the same file the credential read path
consults — so credentials round-trip with `docker login`.

## Conventions (apply as commands land)

- **One file per subcommand** under `src/command/`.
- **Typed identifiers**: parse user-supplied references into domain types
  early; the rest of the command works on typed values, not raw strings.
- **Report actual results**: a command reports what happened, not an echo
  of its input. Operations return enough data to build accurate output.
- **Exit codes**: follow `quality-rust-exit_codes.md` — usage errors,
  data errors, and I/O errors map to distinct, documented codes.
- **Output**: structured data goes through the shared output trait so
  `--format json` and the plain table render from one source.
