# Research: grimoire ↔ ocx reuse recon

## Metadata

**Date:** 2026-11-16
**Domain:** packaging | security
**Triggered by:** `.agents/discussions/ocx-adoption-and-signing.md` (owner asks how far grimoire could adopt ocx code, and how to get artifact signing; `.agents/adr/adr_artifact_trust_model.md` § "When signatures arrive")
**Expires:** 2027-02-16 (ocx is at 0.6.8 and moves weekly; crate map and tiers are recent)

Method: read-only recon of both working trees. Nothing was built, `cargo tree` was not run, nothing was run on Windows. ocx paths are `ocx:<path>`; ocx HEAD is `36ce3ca6` (release v0.6.8), grimoire HEAD is `22efb882` (0.15.1). Findings only; no recommendation.

## Direct Answer

No `ocx_*` crate is a published library: every one has `publish = false`, and ocx's own `AGENTS.md` says no crate is published and the binary is the only consumer (`ocx:AGENTS.md:14`). Ten crates, including `ocx_oci`, `ocx_trust`, `ocx_sign`, `ocx_index`, are tiered "ecosystem": linkable by a lockstep submodule consumer, breaking changes allowed if the consumer is upgraded in the same series, enforced by a CI job against an `ocx-mirror` satellite (`ocx:AGENTS.md:16`, `ocx:.claude/artifacts/adr_crate_split_workspace.md:416-440`). ocx's mechanism for that is full-tree git-submodule vendoring plus a re-declared `[patch.crates-io]`; ocx documents that a satellite may link its OCI client, index, signing stack and trust engine (same ADR, 455-495). Signing/verification is real and large (about 34k lines across `ocx_sign` + `ocx_trust`, Sigstore keyless and key-based, cosign bundle v0.3 over OCI referrers, ANY-of identity policy), but `ocx_sign` is typed against ocx's own `ocx_oci::Client`, not against grimoire's `OciAccess`, so linking it means running ocx's OCI client beside or in place of grimoire's. Grimoire's own OCI/identifier/lock/resolve code was originally copied-and-adapted from ocx (18 files carry "Adapted from OCX"), and the two data layouts, index formats, exit-code tables and artifact media types have since diverged.

2. **Signing and trust as built.**
   - Storage: cosign v3-style Sigstore bundle `application/vnd.dev.sigstore.bundle.v0.3+json` pushed as an OCI 1.1 referrer; discovery via Referrers API, then the `sha256-<hex>` fallback tag, then cosign `.sig`/`.att`/`.sbom` sidecar tags (`ocx:crates/ocx_oci/src/referrer/media_types.rs:9`, `ocx:crates/ocx_oci/src/referrer/discovery.rs:11-21`; ADR `ocx:.claude/artifacts/adr_oci_referrers_signing_v1.md`). Capability cache lives under a `state/` tier (same ADR, Amendment 3).
   - Sign: keyless via Fulcio with hand-rolled request flow (sigstore's `SigningSession` mandates SCT, which the self-hosted test stack cannot supply), ambient OIDC inline, browser OIDC, key backend (`ocx:crates/ocx_sign/src/sign/{fulcio,key_signer,key_backend,oidc_ambient_inline}.rs`; spike `ocx:.claude/artifacts/research_sigstore_rs_spike.md`). DSSE/in-toto attest and CycloneDX SBOM referrers also exist (`ocx:crates/ocx_sign/src/attest/`, `sbom/`).
   - Verify: `VerifyPipeline::run(&Client, VerifyContext)` (`ocx:crates/ocx_sign/src/verify/pipeline.rs:300`); context carries policies, trust root, Rekor URL, offline flag, `VerificationMode::{Demand,Permissive}`, `Transparency` handling (`pipeline.rs:88-172`). Rekor SET and Merkle inclusion are owned by ocx in `verify/tlog.rs` because sigstore 0.14 leaves them `TODO` (`pipeline.rs:7`; sigstore-rs#285). Trust roots: embedded or TUF-fetched public-good root, or `--tuf-root`/`OCX_SIGSTORE_TRUSTED_ROOT` file, with an offline trust cache (`verify/trust_resolve.rs`, `trust_cache.rs`, `adr_offline_verify_trust_cache.md`).
   - Policy: ocx_trust holds ANY-of identity-pinned `[[trust.policy]]` entries with scope globs, locked system tier, key or keyless identity, plus index-declared publisher claims (ADR `ocx:.claude/artifacts/adr_trust_policy.md`, `adr_publisher_trust_distribution.md`, accepted 2026-11-13).
   - Hook into fetch: `auto_verify.rs` runs "after resolve and before any layer download, so a fail-closed abort leaves no package or symlink state", fired from `setup_impl` at the metadata-first pull seam (`ocx:crates/ocx_package_manager/src/tasks/auto_verify.rs:1-6`, call at `tasks/pull.rs:255`). It is policy-gated: a package no policy covers installs with an INFO line (`adr_publisher_trust_distribution.md` Context). Strictness is per-registry `signatures = if_declared|required|off` plus `--no-verify`, refused when a system config locks `required` (`ocx:CHANGELOG.md:19`). This matches the shape in `.agents/adr/adr_artifact_trust_model.md:155-160` (uniform gate, strictness policy).
   - Completeness: the crate has no `experimental` markers and no TODOs of its own in non-test source (grep of `ocx:crates/ocx_sign/src`, `ocx_trust/src`); Rekor v2 is not supported (blocked on sigstore-rs, issue #107 per spike); an acceptance suite runs against a seven-service self-hosted Sigstore stack (`ocx:test/sigstore`, `ocx:test/tests/test_sigstore_stack_smoke.py`); ocx's own releases are being moved to signed-by-default (`ocx:.agents/goals/release-signing-trust-default-2026-11-12.md`).
   - `external/sigstore-rs` fork: branch `ocx/integration` on tag v0.14.0, one purpose recorded: adds `SigstoreTrustRoot::new_with_client(cache_dir, client)` so the TUF fetch uses the caller's `reqwest::Client` (CA roots, proxy, timeouts) (commit `d80c2e8e` message; `ocx:.gitmodules`; patch line `ocx:Cargo.toml:25`). Upstream visibility walls (`Keyring`, `verify_bundle`, TUF constants `pub(crate)`) are worked around in ocx code, not patched (`ocx:.claude/artifacts/research_sigstore_rs_visibility_and_capabilities.md`; ADR `adr_real_sigstore_stack_and_delegation.md` D2 rejected forking for the TODOs). The submodule is **not checked out** in the local ocx clone, so the fork's diff itself was not inspected.
   - Known supply-chain wart: sigstore pulls `openidconnect` -> `rsa 0.9.10` (RUSTSEC-2023-0071, no fix); ocx carries a documented `deny.toml` ignore (`ocx:deny.toml:16-28`). Any bundle-capable sigstore build carries it.

5. **Mechanics.**
   - Existing wiring: two path patches into submodules, `docker_credential = { path = "external/docker_credential" }`, `oci-client = { path = "external/rust-oci-client" }` under `[patch.crates-io]` (`Cargo.toml:165-167`); `.gitmodules` pins branches `feat/store-erase-list` and `ocx/integration`. ocx declares the same two plus `sigstore` (`ocx:Cargo.toml:23-26`) and also lists submodules in `[workspace] exclude`.
   - Consuming ocx crates the same way means a submodule of the **whole** ocx repo with path deps into `crates/*` (ocx documents "full-tree git-submodule vendoring is a hard requirement", cargo#14946, `ocx:.claude/artifacts/adr_crate_split_workspace.md:455-475`); the consumer must re-declare `[patch.crates-io]` for `oci-client`, `docker_credential`, `sigstore` (it does not travel) and the named feature lines `serde_json/raw_value` and `serde_json/preserve_order` (same ADR). ocx's own satellite is `ocx-mirror`, built in a `satellite:verify` deep job. A nested submodule would put ocx's submodules (`external/*`) under grimoire's `external/`, so grimoire's existing two forks and ocx's three would need to be reconciled to one set of pins. No git dependency or crates.io route exists (publish false).
   - Toolchain: both Rust 2024, resolver 3, grimoire toolchain 1.95.0 (`rust-toolchain.toml`), ocx `rust-version = 1.95.0` pinned equal to its toolchain (`ocx:Cargo.toml:17`). Grimoire sets no `rust-version`. Both `Apache-2.0`. Both forbid unsafe? grimoire does (`Cargo.toml` lints); ocx's lint set was not checked.
   - Shared-dep versions already unify in the two `Cargo.lock`s: tokio 1.53.3, reqwest 0.13.5, rustls 0.23.46, oci-client 0.17.0, serde 1.0.229, serde_json 1.0.154, chrono 0.4.45, hex 0.4.3, clap 4.6.7, docker_credential 1.3.3, schemars 1.2.3, thiserror 2.0.21 (both carry 1.0.69). Small drift: toml 1.1.8 vs 1.1.6, aws-lc-rs 1.18.2 vs 1.18.1, aws-lc-sys 0.46.0 vs 0.45.0. ocx's `sha2` is 0.10 for p256 beside 0.11; grimoire already has both lines. `sha2` 0.11 + `hmac` 0.13 in grimoire vs ocx's `base64` 0.23 present in both.
   - Dependency weight: grimoire lock 442 packages, ocx lock 762, 517 `name+version` pairs present in ocx but not grimoire (that number is the whole ocx CLI, not the signing closure). `sigstore` 0.14.0 direct deps include `tough`, `openidconnect`, `p256`/`ecdsa`, `x509-cert`, `scrypt`, `crypto_secretbox`, `webbrowser`, `tls_codec`, `sigstore_protobuf_specs`, `rustls-webpki`, `aws-lc-rs` (grimoire already has aws-lc-rs and ring); `rsa` and `ed25519-dalek` are in ocx's lock and absent from grimoire's. Size impact was not measured. ocx's own size tuning: `dist` profile `opt-level="s"`, fat LTO, measured 33.4 MB to 18.6 MB for the full ocx binary (`ocx:Cargo.toml:30-37`); grimoire `dist` uses thin LTO.
   - Telemetry/other: `ocx_oci` pulls `ocx_console` and `ocx_env`, so a signing link brings the `OCX_*` environment registry (e.g. `OCX_KEY_PASSWORD`, ambient OIDC sources, `OCX_SIGSTORE_TRUSTED_ROOT`) and ocx's `error.detail` slugs into a binary whose env contract is `GRIM_*` (`AGENTS.md` env table).
   - The grim-hook launcher crates are constrained to `serde`, `serde_json` and an allowlist (`.claude/rules/product-tech-strategy.md`), so signing cannot enter them regardless.

   - ocx uses grim as a tool only: root `grimoire.toml` pulls bundles from `ghcr.io/ocx-sh/lore` and `ghcr.io/michael-herwig/arcana`, lock generated by "grim 0.14.3", installed via `ocx exec -g lint -- grim install` (`ocx:grimoire.toml`, `ocx:grimoire.lock:1-12`, `ocx:taskfiles/baseline.taskfile.yml:16-97`).    - Grimoire depends on ocx at distribution level: grim is released to `ocx.sh/grimoire/cli` and installed with ocx (`docs/src/content/docs/installation.md`); grimoire's own acceptance runs may use an ocx-pinned toolchain (`git log`: "add uv to the project ocx toolchain", `5c39226e`/`52379ceb`). A source-level grimoire -> ocx edge would add a cycle at the process level: ocx builds depend on grim-installed rule files and grim is shipped through ocx, though neither is a Cargo edge.
   - The satellite rule forbids a satellite from naming `ocx_store`, `ocx_announce`, `ocx_package_manager`, `ocx_project` and others, while allowing the ecosystem tier and `ocx_exit` (`adr_crate_split_workspace.md:480-492`). Ecosystem crates may break at any time, with the consumer upgraded in the same series: a grimoire consumer would be a satellite outside the ocx CI job unless ocx adds it to `satellite:verify`.

- Signing without ocx crates — cosign/notation interop and a `sigstore`-direct (or `cosign verify` subprocess) option, to compare against the link options; adjacent lane for the owner's decision.
