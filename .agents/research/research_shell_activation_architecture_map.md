### B2. Output contract and the script-to-stdout precedent

- `Printable` has two methods, `print_plain` (exactly one `print_table`) and `print_json`: `src/cli/printer.rs:42-55`, single-table rule `:6-8`, `print_table` `:100`. `render` in `src/app.rs:228-245` picks by `--format` and wraps every stdout write with `tag_stdout_pipe`, which turns `BrokenPipe` into the `StdoutPipeClosed` sentinel that `main.rs` maps to silent exit 0 (`src/cli/printer.rs:23-40`, `src/main.rs:211-219`).
- `completions` is "fully exempt": no report module, wired directly in the `app.rs:163` arm, returns `ExitCode` (`.claude/rules/subsystem-cli-api.md:121-123`, `src/command/completions.rs:9-13`). It generates into a `Vec<u8>` first (an infallible sink, so `clap_complete`'s internal `.expect` cannot fire), then does one `write_all` + `flush` on stdout, each `.map_err(tag_stdout_pipe)` (`:46-50`).
- It takes no `--format`: the global flag is accepted (`src/cli/options.rs:62-63`, `global = true`) and ignored; no JSON document exists. A `shell init` script printer would fit the same tier. The pipe contract is pinned by `test/tests/test_broken_pipe.py:71-78` (`["completions", "zsh"]`).
- It is not free: `main()` builds the Tokio runtime (`src/main.rs:189`) and `Context::new` plus `telemetry().start` run before any arm (`src/app.rs:45-46`), so a printer still pays process startup (the discussion's 2.7 ms `--version`, unverified).
- Payload-plain precedent with JSON available: `fetch` (`.claude/rules/subsystem-cli-api.md:125-130`). Human-facing warnings go to stderr via `tracing`, never stdout.

### B6. The no-op `grim install` path versus `grim status`

Order in `src/command/install.rs:77-123`, then `src/install/installer.rs:708-805`:

1. Scope resolve, then **non-blocking advisory lock**: creates `grimoire.toml.lock` beside the config, verifies the inode, and unlinks it on drop (`install.rs:79-82`, `src/lock/advisory_lock.rs:93-130`, `:4-8`). `status` does neither.
2. `require_fresh_lock` (`install.rs:442`, `fresh_lock` `:455-480`): parse lock, compare `declaration_hash` (`status` does the same comparison, `status.rs:2010-2012`).
3. `hook_consent::resolve` (`install.rs:95`): resolves hook/settings arming policy, reads consent records, may prompt on a TTY.
4. `global_clients` (`:96`, `src/command.rs:331-349`), client detection via `install_target` (`:97-100`).
5. `access_seam` (`:104`): `Context::access_with_mode` runs `ensure_layout` (5 `create_dir_all` + stat, `src/store/paths.rs:137-163`, `src/context.rs:382`) and builds `RegistryClient::with_plain_http_hosts` (`src/oci/access/registry_client.rs:70-74`, a full `Client::new`). `plain_http_hosts` loads the global config (`src/command.rs:703-717`). No request is sent for an unchanged lock.
6. `load_state` (`:105`), same as `status`.
7. `refuse_stale_edges` (`installer.rs:731`, `:2848`): skips every entry already recorded at its pin ("an unchanged install must not need the network", `:2842-2844`).
8. Per artifact `integrity_gate` (`:984`, `:1922`): hashes each recorded output (`current_hash`), the same work `status` does, then returns `AlreadyInstalled` (`:1982-1984`).
9. **Unconditional `persist_and_converge`** (`:777`, `:826-873`): `state.persist` rewrites `state.json` through `atomic_write` (`src/install/install_state.rs:1325-1349`, `:1241-1279`; `src/store/atomic_write.rs:32-70` = tempfile, `sync_data`, rename, directory `fsync`), even when every item was `AlreadyInstalled`; then `sync_config` for every client in the set (reads and may splice vendor config), then `converge_for` hooks.
10. `armed_after_convergence` and the report (`install.rs:121-122`).

Not profiled; the above is what the code does beyond `status`, ranked by how likely each is to cost milliseconds: the state rewrite with two fsyncs, the per-client `sync_config`, `ensure_layout` plus client construction, then consent resolution. Earliest safe "nothing to do" exit: after step 2 (lock fresh) and the consent/client-set resolution of steps 3-4, before step 5. It would have to prove four things: the lock is the one last applied (see B7), the effective client set and its roots are the same, the hook and settings policies would arm nothing new, and the outputs are intact. A stat-only check can prove the first; it cannot prove the last without stat or hash of outputs (which is what `integrity_gate` does). `refuse_stale_edges` already shows the established "unchanged needs no network" stance.

### B7. Fingerprints a stat-only "lock changed since last install" check could compare

- Lock: `grimoire.lock` has `[metadata]` with `declaration_hash`, `declaration_hash_version`, `generated_by`, `generated_at` (`src/lock/grimoire_lock.rs:30-46`, `deny_unknown_fields`). `generated_at` is "preserved verbatim when the resolved content of every artifact is unchanged" (`:41-42`), so it is not a content stamp.
- Install state: `<workspace>/.grimoire/state.json` and `$GRIM_HOME/state/global.json` hold `{version: 2, records[{kind, name, pinned | path+hash, dev, outputs[{client, target, content_hash, support_dir?, ...}]}]}` (`src/install/install_state.rs:565-579`, `:586-598`, `:649-655`, `ClientOutput` `:86-111`). **No lock digest, lock mtime or lock size is recorded anywhere at install time.** The records' `pinned` digests are the lock's pins at install time, so a lock-vs-state comparison today means parsing the lock and diffing pins, which is what `status` does.
- Both state structs are `deny_unknown_fields` (`install_state.rs:585`, `:650`); stability.md allows additive state fields (`docs/src/content/docs/stability.md:44`) but an older grim reading a file with a new top-level or record field hard-rejects it (`stability.md:903-909`). A new stamp in `state.json` therefore breaks a downgrade; a separate file avoids that.
- I1 limits where a stamp may live: `.grimoire/state.json` is repo-resident and "not safe storage" (a local test showed `git pull` replacing a gitignored state file; `.claude/rules/arch-threat-model.md:65-96`). A stamp that only feeds a notice is advisory, but anything that gates a write must live under `$GRIM_HOME`.
- The project's `.grimoire/` also holds a self-managed `.gitignore` (`install_state.rs:826-835`) and the transient `grimoire.toml.lock` sidecar.

### B9. `grim-hook` and `grimoire-hook-core` (ten lines)

1. `grim-hook` is a separate bin crate whose only dependency is `grimoire-hook-core` (`crates/grim-hook/Cargo.toml`); the core depends on `serde` and `serde_json` only (`crates/grimoire-hook-core/Cargo.toml`, `schemars` optional behind `schema`).
2. No Tokio, clap or tracing: synchronous `std`, `main` -> `run` -> `dispatch` (`crates/grim-hook/src/main.rs:41-189`); `product-tech-strategy.md` records it as the one sanctioned deviation.
3. Its linked crate set is pinned by an allowlist test over `cargo tree -p grim-hook` (`crates/grim-hook/tests/guards.rs:14-32,56-62`).
4. Size budget 512 KiB, 640 KiB on musl (`crates/grimoire-hook-core/src/lib.rs:38-43`), built with `profile.hook`: `opt-level = "z"`, fat LTO, `panic = "abort"`, symbols stripped (`Cargo.toml:189-195`).
5. The main crate does not depend on it as a cargo edge: `build.rs` runs a nested cargo build and embeds the bytes via `include_bytes!` as `GRIM_HOOK_BIN` (`build.rs:1-8`); `ensure` writes the launcher only if the bytes differ (`src/install/launcher.rs:7-8`). The main crate does depend on `grimoire-hook-core` with feature `schema` (`Cargo.toml:34`).
6. Hot-path input is the dispatch table beside the executable plus stdin; the only environment variable read is `GRIM_LOG` (`main.rs:1-8,40-41`); `table_path` canonicalises the directory, never the leaf (`:128-136`); the table read is capped (`:142-150`).
7. Two source-level bans hold the runtime crates to "no config, scope, `Context`, telemetry handle or env data-root accessor" (C-007) and "no digest primitive" (C-009) (`src/command/hook.rs:11-22`), because a client-spawned process runs with the workspace as CWD (I1/T3).
8. What it shares with grim: the table, manifest, projection, glob and audit types in `grimoire-hook-core` (`lib.rs:10-35`); nothing of `Context`, `GrimPaths` or the config types.
9. Output is escaped: handler text reaches a terminal only through `escape_control`, which turns C0/DEL/C1 into `\u{..}` (`main.rs:64-76`). The notice-wording requirement in the discussion has a ready precedent.
10. As a precedent for a hook-side check it shows the shape (std only, dependency allowlist, size budget, no shared config reads), not a reusable fast path: grim's own startup (Tokio runtime `src/main.rs:189`, `Context::new` `src/app.rs:45`) is not on it.

### B12. ADR conventions and the closest ADRs

- Template `.claude/templates/artifacts/adr.template.md`: header comment, `## Metadata` (Status, Date, Deciders, Beads Issue, Related PRD, Tech Strategy Alignment checkboxes, Domain Tags, Supersedes, Superseded By), then Context, Decision Drivers, Industry Context & Research, Considered Options (3), Decision Outcome (+ Quantified Impact, Consequences), Technical Details (Architecture, API Contract, Data Model), Implementation Plan, Validation, Links, Changelog.
