# Research: Harness mods, community practice (lane: community threads and blogs)

## Metadata

**Date:** 2026-11-18
**Domain:** packaging
**Triggered by:** discussion on shipping "Claude mods" (UI and behaviour extensions of the harness) through grim; shape A (kind for one harness) versus shape B (harness-neutral kind with one payload per harness)
**Expires:** 2027-02-18 (the mods API is seven weeks old; re-verify within three months)

Method note. Every claim below carries a URL and was fetched on 2026-11-18 unless stated. "Says" marks what a source states; "infer" marks my reading. GitHub issue and comment data came from the `gh` CLI against the live repos (counts as of the fetch). The `claudeissues.com` mirror could not be fetched from this host, so issue content was read from github.com directly. This lane returns findings only, no recommendation.

## Direct Answer

Claude mods are about seven weeks old (announced 2026-10-01, Claude Code 2.1.287). Anthropic's stated channel is the plugin marketplace, and a mod is by definition a plugin whose `hooks/hooks.json` has a `modules` entry. Practitioners treat mods as Claude-specific by default, with a small and growing minority who build one core and a host adapter per harness, and one active third-party attempt (Qwen Code) to re-implement the Claude contract elsewhere. Discussion of registry, pinning, signing and org rollout is real but mostly framed against the Claude plugin system, not against a harness-neutral format.

## Key Findings

### 1. How mods are shared today

1. Anthropic's own statement: "A mod installs as a plugin, from a marketplace"; "Mods ship inside plugins, so you install and share them like any plugin"; share by sending a directory or zip, a private marketplace repo, org managed settings, a public marketplace repo, or submission to Anthropic's directory. Sources: [mods overview](https://code.claude.com/docs/en/plugins/mods/overview.md), [create a mod](https://code.claude.com/docs/en/plugins/mods/create.md), [launch post](https://claude.com/blog/claude-code-mods).
2. In practice almost every shared mod in the design thread is a GitHub repo that is its own marketplace, announced with the same two lines: `claude plugin marketplace add <owner>/<repo>` then `claude plugin install <name>@<repo>`. Examples in the thread: [pixelband](https://github.com/anthropics/claude-code/issues/91870#issuecomment-5850001376), [verbs](https://github.com/anthropics/claude-code/issues/91870#issuecomment-6280795145), [cc-mods](https://github.com/anthropics/claude-code/issues/91870#issuecomment-6312070758), [flightdeck](https://github.com/anthropics/claude-code/issues/91870#issuecomment-5961512212). Single-author multi-mod repos are common (e.g. [ray-amjad/claude-code-mods](https://github.com/ray-amjad/claude-code-mods), [nateherkai/claude-code-mods](https://github.com/nateherkai/claude-code-mods)).
3. Size of the corpus (all 2026-11-18):
   - [karanb192/awesome-claude-code-mods](https://github.com/karanb192/awesome-claude-code-mods) says "8,898 mods, last scanned 2026-11-17", 1,026 stars. It is an independent scanner that searches public GitHub repos and records what `claude plugin validate` reports each mod can read, write, run or send. Infer: 8,898 counts repos or entries the scanner matched, not vetted or used mods; a StashBase post of 2026-10 says the same list had 359 mods on October 2 and that "most mods are only a few weeks old with a handful of stars" ([StashBase](https://stashbase.ai/blog/best-claude-code-mods/)).
   - GitHub topic `claude-code-mod`: 999 repos (GitHub search API `total_count`, 2026-11-18; may be capped or exact, unverified).
   - Largest single mod repos by stars (gh search, 2026-11-18): [prismantis](https://github.com/NahumLitvin/prismantis) 462, [claude-flightdeck](https://github.com/scasella/claude-flightdeck) 322, YeonwooSung/my-claude-code-mods 877 (a personal collection), hamzafer/claude-code-mods 497. The 9,767-star `rehan-remade/universal-modder` is about game modding, not this topic (noise).
   - Other lists: claudemods.ai (votes, not run by Anthropic), claude-code-templates (about 38 mods), per StashBase.
   - Anthropic samples: [claude-code-playground/claude-code/mods](https://github.com/anthropics/claude-code-playground/tree/main/claude-code/mods), "shared as they are, without support"; built-in mod sources in [anthropics/claude-code/mods](https://github.com/anthropics/claude-code/tree/main/mods).
4. Other routes seen: copy a directory out of `~/.claude/dev-mods/<session>/` to keep a mod Claude wrote for you (create page); ship the mod inside an npm package and print its path via a CLI command (ruvnet gist, [field guide](https://gist.github.com/ruvnet/a485e930b148185197fc53fd38b429ea)); a user MCP finder plugin that searches the scanned catalogue (awesome list README). I found no dotfile-repo or copy-paste-gist distribution specific to mods (absent, not proven absent).
5. Discovery is on GitHub, ranked by third parties. The awesome list's value proposition is an access scan ("what each one can access before you install it"), which says the official directory is not the main discovery path yet. Infer.

### 2. What hurts (mods, and the plugin machinery they ride on)

- **Version breakage when the harness updates.** Anthropic's create page: "The events and methods can change between releases, so your README is the place to say which Claude Code version you tested with." Real regressions in the open tracker: [#110615](https://github.com/anthropics/claude-code/issues/110615) (2.1.322 to 2.1.326: one mod's pane opened by another mod renders blank, reproduced by a second user with synthetic mods, open), [#108580](https://github.com/anthropics/claude-code/issues/108580) (regression in 2.1.317: desktop stops attaching as a surface so mod UI is lost), [#107152](https://github.com/anthropics/claude-code/issues/107152) (resumed conversation keeps a mod tool's old `inputSchema` after the mod updates). The ruvnet field guide: "the API moves between releases"; the type files "always win over this guide." StashBase: some older mods fail on 2.1.287.
- **Surface variance inside one harness.** A mod must handle terminal, Desktop and VS Code differently: "A tree with an element the surface lacks is refused whole" (ruvnet); the overview table shows drawing absent in `claude -p` and cloud sessions; many open issues are "mod UI does not draw in Remote Control / cloud / side chat / split view / empty screen" ([#105772](https://github.com/anthropics/claude-code/issues/105772), [#110178](https://github.com/anthropics/claude-code/issues/110178), [#103429](https://github.com/anthropics/claude-code/issues/103429), [#101748](https://github.com/anthropics/claude-code/issues/101748)). Infer: the nearest existing "same mod, several runtimes" problem is already inside Claude Code.
- **Conflicts between two mods.** [#100789](https://github.com/anthropics/claude-code/issues/100789): "every band plugin also does layout for every other band plugin"; a commenter says one plugin that omits `await next(e)` hides the second plugin's band. Docs carry a troubleshooting section "another mod's band shows and yours doesn't". The order is "load order" within the user tier ([#100789](https://github.com/anthropics/claude-code/issues/100789)). Conflict is real but only a handful of issues; I found no cross-mod conflict resolution tooling.
- **Trust.** Anthropic: "A mod is code that runs with your permissions... Mods aren't sandboxed"; it can read secrets, see every prompt, approve tool calls; `claude plugin validate` lists hooks and calls statically ([overview](https://code.claude.com/docs/en/plugins/mods/overview.md)). Community: [#91870 comment](https://github.com/anthropics/claude-code/issues/91870#issuecomment-5965802196) from a mod author: "A mod's file access isn't confined... any mod can read and write whatever the user can"; the awesome list sells an access scan as its core feature; StashBase: "install mods the way you'd install a package." Count from the scanner (359-mod snapshot, 2026-10-02, StashBase): 127 start processes, 95 write files, 75 reach the network, 111 see every prompt.
- **Team and org rollout.** Heavy and recurring in the tracker: Team plans load a built-in guard `cc-plugin-sec-default` that skips user-tier hooks on several events. [#110469](https://github.com/anthropics/claude-code/issues/110469): "the one distribution channel a small Team organization has without device management... is the one channel whose mods cannot be seated" (the claude.ai org plugin library cannot make a mod count as the org's). [#109411](https://github.com/anthropics/claude-code/issues/109411) (let admins exempt members), [#104236](https://github.com/anthropics/claude-code/issues/104236), [#102653](https://github.com/anthropics/claude-code/issues/102653). Also [#101258](https://github.com/anthropics/claude-code/issues/101258) and [#108595](https://github.com/anthropics/claude-code/issues/108595): org sync strips the `types` key from `plugin.json`, so a mod that uses `$.state` fails to load. Infer: manifest fidelity through a registry or sync is itself a failure mode for mods.
- **Per-project versus per-user scope and cloud.** [#100737](https://github.com/anthropics/claude-code/issues/100737) (referenced from the design thread): plugins declared in a repo's settings are not installed in cloud sessions; desktop-installed and user-scoped plugins do not carry over. Anthropic docs: managed `prependPlugins` and repo settings cannot set the order lists (a repository cannot seat org mods).
- **Marketplace update mechanics for plugins in general** (affects mods): a large cluster of open and closed bugs about auto-update deleting the marketplace directory, silent failure to upgrade, stale clones, and extraction paths, e.g. [#40153](https://github.com/anthropics/claude-code/issues/40153), [#46594](https://github.com/anthropics/claude-code/issues/46594), [#94516](https://github.com/anthropics/claude-code/issues/94516), [#42931](https://github.com/anthropics/claude-code/issues/42931). Fix status of each unverified; titles read via search result summaries and mirror site, dates range 2025 to mid-2026.
- **Cache by version.** Create page: "Claude Code caches an installed plugin by version, so your edits don't reach the installed copy until you increment the version and install again."

### 3. What users ask for

Counting method: I fetched all 278 comments of the design thread [anthropics/claude-code#91870](https://github.com/anthropics/claude-code/issues/91870) (opened 2026-09-03, 132 thumbs-up, 168 distinct commenters) and counted comments matching case-insensitive word-bounded regexes. Regex hits are rough: a comment can match for an incidental use. Counts: marketplace or registry 19; signed, signature, signing, provenance or attestation 12; managed settings or admin 38; lockfile, lock file, sha256 or digest 2; portability, cross-harness, "other harness" or similar 4; named other tool (Codex, OpenCode, Gemini CLI, Cursor, Copilot, Qwen) 11; supply chain or malicious 0. The thread skews to engineers building mods and to security and admin concerns; it is not a sample of mod users.

- **Registry/directory.** Asked mostly implicitly; anchor request: OpenCode's marketplace master issue ([anomalyco/opencode#28696](https://github.com/anomalyco/opencode/issues/28696), 46 reactions, "the one feature keeping masses from migrating", closed 2026-05-21). For Claude, the community already built the registry itself (awesome list scanner site). Anthropic has the "Claude directory" for submission.
- **Pinning and a lockfile.** Essentially absent as a mod request (2 digest or lockfile hits). The closest: a commenter in the thread notes "an allowlist on `plugin.register` that matches by name pins a name, not bytes", and asks Anthropic to expose the resolved plugin root and the marketplace entry's sha/version so an org mod can verify "the code that was reviewed" ([comment](https://github.com/anthropics/claude-code/issues/91870#issuecomment-5622508181)); a follow-up from the same author ships a signature-checking mod (PromptSign). Anthropic docs do offer "pin the marketplace and the mod's entry" for org mods ([admin](https://code.claude.com/docs/en/plugins/mods/admin.md)).
- **Signed mods.** Requested as org-side verification, not as an author feature: PromptSign (above); a signed subagent run receipt, [#104409](https://github.com/anthropics/claude-code/issues/104409), which concerns run provenance, not mod provenance.
- **Team distribution.** Strong and recurring (#110469, #109411, #100737, thread comments on org marketplaces and sync).
- **Cross-harness portability of UI/behaviour mods.** Requested by a minority, and mostly by authors of tools that already span hosts, not by mod end users:
  - [tavaresgmg](https://github.com/anthropics/claude-code/issues/91870#issuecomment-5541556260): "The same six scripts run under Codex and Cursor through a thin adapter, because all three harnesses hand a JSON payload to a process. A TypeScript function against `$` only runs where `$` exists." Asks whether the command-hook interface stays beside function hooks, "since that is what keeps one policy usable in more than one tool."
  - [tonydzi](https://github.com/anthropics/claude-code/issues/91870#issuecomment-5719772175): "a `$` object that exists in one runtime turns a shared shelf into a fork... Keeping an equivalent declared payload shape for function hooks costs little now and is close to unaffordable later."
  - [wkasekende](https://github.com/anthropics/claude-code/issues/91870#issuecomment-6303343066) (OpenCues): the Mods API "is also becoming a standard others follow: Qwen Code is building a compatibility layer on the Claude Code authoring contract".
  - Shell command hooks are the existing portable layer; function mods are not portable. Both commenters say so independently.
- Maintainer view on the same question is in section 5.

### 4. Nearest equivalents in other harnesses

Briefly, same three questions.

- **OpenCode.** Own plugin and TUI-plugin system plus themes (themes live under `~/.config/opencode/themes`, with open theme bugs such as [#54235](https://github.com/anomalyco/opencode/issues/54235)). Users ask for one package that follows them across harnesses, but the object of that request is skills and MCP, not UI. [#40993](https://github.com/anomalyco/opencode/issues/40993) (26 reactions, 18 comments, closed 2026-08-07) asks OpenCode to adopt the Agent Plugins standard; a commenter says: "the main issue is that you have to install the plugin separately for every harness, which means it ends up duplicated... Ideally, plugins would work the same way: you'd install them once at the system level, and every harness would automatically discover" them; another: "Many of us live in enterprises where we are forced into a particular harness... we either have to create a duplicate set of opencode specific variants or make our own bridge plugins." Community bridges exist (opencode-claude-bridge and opencode-claude-marketplace-bridge on npm, per search results; they bridge commands, agents, skills, MCP, not Claude UI mods).
- **Gemini CLI.** Extensions are declarative; hooks are shell commands. [#17505](https://github.com/google-gemini/gemini-cli/issues/17505) asked to import Claude plugin bundles ("you currently have to re-author everything because the formats and folder structures differ"), closed stale; a community translator tool appeared instead. [#29970](https://github.com/google-gemini/gemini-cli/issues/29970) (open, 2026-10-27): "Adopting the same contract would let one extension run on all three CLIs." Zero reactions, one bot reply. Infer: thin demand evidence.
- **Qwen Code.** [QwenLM/qwen-code#13749](https://github.com/QwenLM/qwen-code/issues/13749) (open since 2026-10-09, 7 comments): "Implement a Mod runtime in Qwen Code using the Claude Code authoring contract... Compatibility is a versioned, tested subset, with an explicit status for each event, host API, tool mapping, and UI surface" plus "a capability matrix with supported, limited, unsupported, and unverified entries". The only concrete instance of shape B-like thinking found, though it is implemented as "other harness reads the Claude format" rather than "one artifact with two payloads". An implementation tracking proposal; no stage implemented per its own text.
- **pi.** Extension issues are about host APIs (events, trust), e.g. [earendil-works/pi#11193](https://github.com/earendil-works/pi/issues/11193) (project packages skipped when trust is not saved). A thread commenter built a bridge that runs pi as a Claude Code subagent ([FazalAAli](https://github.com/anthropics/claude-code/issues/91870#issuecomment-5725437710)). No portability ask found in pi's own tracker (not exhaustively searched).
- **Cursor.** Cursor 2.5 added plugins that bundle skills, subagents, MCP, hooks, rules ([forum](https://forum.cursor.com/t/cursor-2-5-plugins/152124), per search summary; page not fetched). Cross-use is via dual-manifest repos (`.claude-plugin/plugin.json` plus `.cursor-plugin/plugin.json`) and community forks such as `kdoroszewicz/cursor-plugins-claude`, per search summary, unverified beyond that. A forum user asked how to add third-party marketplaces.
- **Agent Plugins 1.0** ([spec](https://agent-plugins.org/specification), fetched): vendor-neutral spec by Amazon, Cursor, Microsoft, OpenAI, Vercel, later Google. Says: "defines exactly two component types: skills and MCP servers"; commands, hooks, agents, rules and LSP excluded as "too client-specific for a stable portable contract"; client-specific data goes under a reverse-domain `extensions` namespace and a same-named directory, and "clients ignore namespaces they don't implement." Infer: this is a standards-body precedent for a shared core plus per-client payload slots, and for excluding UI and hooks from the portable part.
- **A cross-host mod in the wild.** OpenCues is a prompt-box mod that its authors say runs "on Claude Code, Pi and OpenCode" ([gemini-cli#29970](https://github.com/google-gemini/gemini-cli/issues/29970)); the repo ([opencues/opencues](https://github.com/opencues/opencues)) has `packages/` (core, runtime, cli) and `integrations/` with one directory each for `claude-code`, `opencode`, `gemini-cli`, `chrome`, `shell`, `dsh`, `windows` (GitHub contents API, 2026-11-18). Infer: the working cross-harness pattern is shared core plus one adapter directory per host, authored by the mod's owner, not a neutral artifact consumed by a package manager. One project; do not generalise.

### 5. Maintainer statements

- **Format stability (Anthropic docs, fetched 2026-11-18).** "The events and methods can change between releases, so trust these [generated type] files over any page, this one included, when they disagree" and the README should name the tested Claude Code version ([create](https://code.claude.com/docs/en/plugins/mods/create.md)). The launch post gives no stability or versioning guarantee ([blog](https://claude.com/blog/claude-code-mods)); it says "We plan to move more built-in features to mods over time."
- **Design thread author (Anthropic engineer, per author field `poteat`; employer not confirmed by the fetch).** 2026-09-09: "much of the semantics are now set in place, and we don't anticipate as many breaking changes as our first week" ([thread head](https://github.com/anthropics/claude-code/issues/91870)). On goals: "_my_ personal goal is for this to work on any surface powered by the Claude Code binary" ([comment](https://github.com/anthropics/claude-code/issues/91870#issuecomment-5532500675), truncated in my fetch; read in full before quoting).
- **Distribution channel.** Marketplace plus Claude directory; org install via managed settings only counts as the organization's for a directory-source marketplace today; remote sources "gain the tier in a later release" (per a thread comment quoting the docs; the 2026-11 admin page already lists remote-marketplace org mods from v2.1.324).
- **Portability to other harnesses.** No Anthropic statement found. The launch post says mods "work in the Claude Code CLI and desktop app" and is silent on other tools. Docs describe surfaces only within Claude Code.
- **Other vendors.** Agent Plugins TSC (spec above) states what is portable. Gemini CLI's bot reply on #29970 sizes the request as a new in-process runtime and is not a decision. Qwen's tracking issue is a vendor stating intent to implement the Claude contract.

## Evidence for and against shape A (one-harness-only kind)

For:
- Anthropic scopes mods to Claude Code, says the API can change between releases, and ships mods as ordinary Claude plugins ([create](https://code.claude.com/docs/en/plugins/mods/create.md)).
- Demand for cross-harness UI or behaviour mods is thin in the sources found: 4 portability-themed comments out of 278 in the central thread, 0 reactions on the Gemini request, and the OpenCode portability demand is about skills and MCP.
- Within Claude alone the surfaces differ (terminal, Desktop, VS Code, `-p`, cloud) and mods must branch on `e.surface`; that variance already costs mod authors ([overview](https://code.claude.com/docs/en/plugins/mods/overview.md), ruvnet gist).
- Agent Plugins excluded hooks and UI from the portable core as "too client-specific".

Against:
- Mods are plugins by Anthropic's definition and plugin machinery bugs (sync stripping `types`, marketplace refresh, org seating) show up as mod failures; a Claude-only kind that bypasses the Claude plugin manifest would carry those risks differently, not remove them (infer).
- A mod commonly ships beside skills and MCP in one plugin ("A plugin can hold all of them", overview), and several popular mods pair a skill with a mod ([claude-handoff](https://github.com/REMvisual/claude-handoff)); a mod-only kind splits one author-facing unit (infer).

## Evidence for and against shape B (neutral kind, per-harness payloads)

For:
- Working precedent for a core plus per-host adapters: OpenCues, and Agent Plugins `extensions` namespaces with "clients ignore namespaces they don't implement".
- Stated author pain: tavaresgmg and tonydzi (section 3); OpenCode enterprise users who maintain "duplicate opencode-specific variants" (#40993).
- A second implementer exists (Qwen Code issue) and a third has been asked (Gemini #29970), so the Claude contract is already being treated as a de facto surface by some.
- Mods are unusually inspectable: `claude plugin validate` lists hooks and calls statically, which gives a per-harness payload a checkable capability list (infer).

Against:
- Function-mod code is not portable: "A TypeScript function against `$` only runs where `$` exists" (tavaresgmg). Qwen's issue calls its result "a versioned, tested subset" with unverified entries, so equal behaviour across harnesses is not what is on offer.
- The one live adapter target (Qwen) reads the Claude format; it does not need a neutral kind, only a reader of the Claude one (infer).
- No vendor, including Anthropic, has made a statement of portability for UI/behaviour extensions; the stable cross-vendor part (Agent Plugins) is skills and MCP only.
- Each payload would inherit its harness's version volatility; Claude's changes between releases, so a neutral kind would be only as stable as its least stable payload (infer).
