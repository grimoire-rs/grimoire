## Research: lock pin and install scope — repo archaeology

Method: `git log -S/-G/--follow`, `git show`, `git blame` over 958 commits (first commit 2026-05-15), plus ADRs, plans, specs, docs and tests in this worktree (branch `uno`). Nothing was executed. Line numbers are against the current worktree unless a SHA is given. Commit dates are author dates.

### Direct answer (short)

- The stale-lock refusal on a **partial** resolve is an explicit, early, written decision (phase 3, `3d2ed57`, 2026-05-15), ported from OCX, with the rationale "a partial would launder a stale lock under a new hash". It was never an ADR; the rationale lives only in a doc comment and an error string.
- `grim lock` (no names) always fully re-resolving every declared reference is the **original** shape (`936aed9`, 2026-05-15: "resolve the whole declared set") and its docs have said "Resolves the floating tags declared in grimoire.toml to concrete digests" unchanged since 2026-06-01 (`ee27e95`). I found no proposal, ADR, plan, research note or test (before the 2026-11-03 discussion) that proposes, decides or rejects keeping existing pins on `grim lock`. The behavior reads as the default consequence of how `resolve_lock` was ported, not as a recorded decision either way. A test added on 2026-11-03 (`e51bad7`) does assert that `grim lock` rolls a moved transitive tag forward.
- `grim add` falling back to a full `resolve_lock` on `StaleLock` is explicit in its comments from its first version (`b06814a`, 2026-05-15): a partial relock cannot work after the add itself edited the declaration, so a full resolve is "the correct recovery". The bundle-always-full-resolve branch was added with bundles (`49944cd`, 2026-06-01).
- `grim update <names>` installing and pruning the whole lock is the original shape (`936aed9`), not a recorded decision; `update` was written as "re-materialize the new lock". No commit, ADR or doc states that the named-binding scope should or should not bound install/prune/reap. By contrast `grim add` was explicitly scoped to "only the added entry" (`5023fc7`, 2026-07-04).
- The integrity gate in `update` was a hard-coded `force = true` from the start (`936aed9`) until `f95b521` (2026-08-12), which treated it as a bug ("a contract restoration"), not a design change.
- A "current state vs target state, derive mutations" model exists in the repo for **lock/file removal** (`adr_effective_set_mutations.md`, 2026-06-11, `E_before \ E_after`; extended to dependency closures in `adr_artifact_dependencies.md` Decision 4). I found no ADR or commit that applied it to install, prune, reap or relock scope, and none that attempted and reverted it.

### Key findings (numbered)

1. **`declaration_hash` origin.** Introduced in `866d790` (2026-05-15, "config (global+project), lock, atomic store (phase 2)"): "DesiredSet + JCS declaration hash ... Adapted from OCX project/{config,lock,project_lock}.rs". `src/config/hash.rs` header (as of that commit): "The declaration hash is the staleness pivot: the lock records the hash of the declaration it was resolved from, so a later command can detect that `grimoire.toml` changed without re-resolving." The same commit adds `LockErrorKind::StaleLockOnPartial` ("partial-resolve refused: lock declaration_hash ... does not match current ...; retry with a full resolve") and `declaration_hash_version` ("Bumping this is a breaking change"). No ADR, plan or spec exists for phases 2-4 (the earliest ADR commit under `.agents/adr` is `0ad3280`, 2026-06-10; the `.agents/plans` history starts 2026-08-09 after `408435a`).

2. **Where the stale-lock laundering rationale is written.** `3d2ed57` (2026-05-15, "OCI access seam, cache, resolve (phase 3)": "transactional resolve_lock + resolve_lock_partial with stale-lock guard ... Adapted from OCX oci/index.rs + project/resolve.rs"). Doc comment on `resolve_lock_partial` then and now (`src/resolve/resolver.rs:498-501`): "if the predecessor's `declaration_hash` does not match the current declaration, a fresh resolve is required (a partial would launder a stale lock under a new hash)". Guard comment `src/resolve/resolver.rs:519` "Stale-lock laundering guard — BEFORE any I/O or access call." The rationale is exactly one sentence; the mechanism it describes is that a partial resolve writes a lock stamped with the new hash while carrying forward entries resolved for an older declaration (`build_lock(merged, set)` in `3d2ed57`). The word "launder" recurs only in tests/comments that apply the same idea to other defects (`test/tests/test_bundles.py:464` for remove, `src/install/installer.rs:2810`), not as a further stale-lock decision.

3. **What a stale lock implies, by command (all explicit in code at first writing).**
   - `grim install`: refuse, exit 65 `LockStale`, "run `grim lock` before installing"; `936aed9` (2026-05-15) module doc "Install does **not** resolve: it requires a lock that is present and whose `declaration_hash` matches the live config (otherwise it tells the user to run `grim lock`)". Current check: `src/command/install.rs:436-441`.
   - partial `grim update <names>`: refuse, exit 65 (`936aed9` module doc: "`resolve_lock_partial`, which enforces the stale-lock guard => exit 65"). Machine-readable reason `stale-lock` added by `d6a5996` (2026-07-11) because consumers "could only detect the partial-resolve stale-lock refusal by string-matching `message`". Current error carries `retry: "a full resolve"` (`src/resolve/resolver.rs:526`).
   - full `grim update` / `grim lock`: never refuse; re-resolve everything (`936aed9`). `roll_forward` (`src/resolve/resolver.rs:578-596`; extracted without behavior change by `9269972`, 2026-09-27, "Behaviour, messages and exit codes are unchanged") encodes: names and a predecessor => partial (guard inside); otherwise full.
   - `grim add`: partial attempt, then full on stale (finding 4).
   - `grim remove`/`uninstall` with an unresolvable id mismatch: leave the lock deliberately stale, skip the hash restamp, tell the user to run `grim lock`. Decision "honest staleness" in `adr_effective_set_mutations.md:255-290` (bug-fix decision, 2026-06-20), Option C, rejecting offline reconcile because "flipping provenance while retaining the `:latest` digest would pin an unproven digest". Test `test/tests/test_bundles.py:445-476` ("grim must NOT launder the lock").
   - Docs: `docs/src/content/docs/commands.md:547-563` states install refuses on stale lock, "`grim lock` is what makes them agree again", and "only a partial `grim update <name>` refuses" while a full update rewrites the lock.
   - "Partial forbidden" as an absolute does not exist: partial is permitted when the hash matches (`adr_artifact_dependencies.md:569-579`).

4. **`add` relock fallback (`relock_entry`).** First version in `b06814a` (2026-05-15, phase 5, `src/command/add.rs`), inline: partial relock when a previous lock exists, and on `StaleLock` "The added entry made the predecessor stale; a full resolve is the correct recovery (every entry is declared, so this is consistent)." Extracted as `relock_entry` and `relock_declared` by `c62aa56` (2026-06-11, "add: relock_entry() owns the partial-relock-with-stale-fallback so the TUI can declare through the same path") and `ed94f94` (2026-06-11). Current: `src/command/add.rs:1380-1408` (fallback at 1391-1401), `relock_declared` at 1354-1368. Reading of the code (not executed): `add` mutates the declaration and invalidates the hash cache before relocking (`src/command/add.rs:290-331` passes the already-edited `set`), so any add that changes the declaration reaches the stale branch; the partial path can only succeed when the edit left the declaration hash unchanged. Whether `add` is intended to ever take the partial branch successfully is not stated anywhere I found; the comment at `add.rs:1346-1350` and `add.rs:322-326` ("a partial relock of just this entry when a previous lock exists and is not stale") describes it as the happy path.

5. **Why bundle `add` always fully resolves.** `49944cd` (2026-06-01) comment in `add.rs`: "A bundle declaration expands into members whose names differ from the bundle's binding name, so a partial relock keyed on the bundle name cannot work — always do a full resolve for bundles." Carried into `relock_declared` (`ed94f94`, `src/command/add.rs:1346-1349, 1363-1364`). The reason recorded is name keying, not freshness. Related, in the resolver: at `49944cd` `resolve_lock_partial` called `build_work` (which expands every declared bundle over the network) before filtering to the named subset, with the comment "Expand bundles + merge so a requested name can be a bundle member" (`49944cd:src/resolve/resolver.rs:98`). So bundles were re-fetched on every partial from the moment they existed, because requested names can be bundle members only discoverable by expansion.

6. **`resolve_lock_partial` and carry-forward.** Introduced in `3d2ed57` (2026-05-15): "Re-resolve only the named subset, carrying every other previous entry forward verbatim." Carry-forward was keyed `(kind, name)` over `previous.skills` + `previous.rules`. Widened per kind (agents, mcp, hooks, bundles) in later commits (`2abec21`, 2026-06-11, records bundle snapshots "on both the full and partial paths"). Redesigned for the dependency graph in `e51bad7` (2026-11-03) per `adr_artifact_dependencies.md` Decision 3 "Partial resolve" (lines 569-579): "An unselected child keeps its previous pin only when its winning requested identifier is unchanged ... Nodes no longer reachable are dropped. Declared bundles are re-fetched as today." Current `build_carry` doc, `src/resolve/resolver.rs:331-338`: root pins are carried because "the declaration hash proves the declaration unchanged"; "Declared bundles are never carried: they are always re-fetched." The full path (`names = None`) carries only `requires` for the offline fallback (`resolver.rs:339-349`, plus the ADR's "Offline locking" paragraph, lines 440-455), never pins.

7. **Keeping pins on `grim lock` (no names): never proposed, decided or rejected before this discussion.** Searched `.agents/adr`, `.agents/plans`, `.agents/specs`, `.agents/research`, `.agents/discovery`, `.agents/review`, `CHANGELOG.md`, `docs/src`, `test/` for pin-preservation, "idempotent lock", "re-pin", "lock never". Hits are all about something else: `handover_repin_declared_version.md` and `CHANGELOG.md:304`/`commands.md:384` are about `grim add <repo>:<newtag>` changing a *declaration* (shipped as "Re-pin a declared artifact instead of refusing the tag change"); marketplace plan notes "adding `[marketplace]` never re-pins" (`plan_harness_marketplace_export.md:73`) concern declaration-hash scope. The only adjacent design text is that `grim lock` on an unchanged declaration is expected to be byte-identical and report `unchanged` (`test/tests/test_lock.py:43-61`, `src/command/lock.rs:73-100`) — which holds only while the tag has not moved. The dependency ADR's "Floating by default" (`adr_artifact_dependencies.md`, Decision 3) and `concepts.md:245` ("re-resolved on each `grim lock` and `grim update` like any other") state re-resolution on `lock` for dependencies as the intended contract, and `test/tests/test_dependencies.py:88-95` (`e51bad7`) asserts "A transitive node rolls forward when its tag moves. `lock` re-resolves without materializing". The `grim lock` doc does not say whether it moves a tag-moved pin; the closest statements are listed in finding 12.

8. **Declared bundles "always re-fetched".** No bundle-specific ADR exists in the repo (the bundle feature `49944cd`, 2026-06-01, predates `.agents/adr` content; its design is only in the commit message and code comments). The sentence "Declared bundles are re-fetched as today" is Decision 3 of `adr_artifact_dependencies.md:579` (Accepted, `2ee3ff2`/`e51bad7`, 2026-11-02/03) and plan item C-025 (`plan_artifact_dependencies.md:241`: "declared bundles are re-fetched"); it states a status quo, not a new rationale. Mechanical reasons visible in code history: (a) requested names can be bundle members only knowable after expansion (finding 5); (b) the bundle's pin is stored as a `[[bundle]]` snapshot whose member list "go[es] stale between locks (same staleness model as member pins — acceptable)" (`adr_effective_set_mutations.md:66`, Option 1 cons); (c) `build_carry` has an explicit exclusion (`resolver.rs:337-338`). I did not find text explaining why a bundle's own digest pin could not be carried like a root's.

9. **`grim update <names>` installs the whole lock.** Original `936aed9` (2026-05-15) `update.rs`: after `resolve_lock_partial`, `install_all(&new_lock, ..., true)` over the entire lock ("Re-materialize with force so a changed digest overwrites the prior ... that is the rolling-release contract"). `names` appeared only on the resolve side. Current: `install_all_with_progress(&new_lock, ... args.force.into(), InstallIntent::Declared, ...)` over the whole lock at `src/command/update.rs:176-187`; `prune_orphans(&mut state, &new_lock, ...)` at `update.rs:~225` and `reap_dropped_clients` after it are likewise unscoped (`58070b7`, 2026-06-01 "reconciles the materialized tree to the freshly resolved lock"; `086184b`, 2026-07-18, "reconciles the per-client dimension too", Refs #43). `58070b7` mentions a "partial-update carry-forward guard" test, i.e. partial updates were considered for the *lock*, with prune treating "dropped out of the lock" as the orphan criterion. The `update` docs say "pass binding names to scope it" (`docs/src/content/docs/commands.md:611-613`), introduced with the first mdBook docs (`ee27e95`, 2026-06-01). No commit message, ADR or plan discusses scoping install/prune/reap to the names; `git log --grep` for update/partial/named found none. Issue #269 appears only in `.agents/discussions/lock-pin-stability.md` (not in `CHANGELOG.md`, ADRs or docs). The "closure of named bindings" install scope is first described in the current discussion artifact.

10. **Contrast: `add` install scope was explicit.** `5023fc7` (2026-07-04): "Only the added entry (or a bundle's members) is installed — the rest of the lock is left for `grim install`." Pure lock projections `single_entry_lock`/`bundle_members_lock` moved from the TUI into `command::add`; later generalized to `reachable_lock`/`seed_lock` (`e51bad7`; `src/command/add.rs:790-853`) and `ForceScope::Only` (`e51bad7`; `add.rs:709-711`). `ForceScope` (introduced in `e51bad7`, `src/install/installer.rs`) is the only existing "scope" parameter on the installer; `update`'s main path passes `args.force.into()`, its dev path `ForceScope::All` (`update.rs:607`).

11. **Integrity gate / `--force` history in `update`.** Timeline:
    - `936aed9` (2026-05-15): `install_all(..., true)` — force hard-coded, with the comment "A user-modified file is still overwritten on update — that is the rolling-release contract."
    - `58070b7` (2026-06-01): prune honors `--force` for locally modified orphans ("mirroring the install integrity gate").
    - `086184b` (2026-07-18): reap honors `--force`; explicitly distinguishes "update's implied rolling-release force" from `--force`.
    - `d137e9c` (2026-08-01): persist install state before prune/reap so a prune failure cannot leave the state at old digests while tree/lock are new.
    - `f95b521` (2026-08-12), "fix(update): run the same integrity gate as install": "`grim update` passed a hard-coded `force = true` ... a locally modified artifact was overwritten silently — exit 0 ... while `grim install` refused the identical bytes with 65. The `--force` help text claimed to govern exactly this and did not." Declared "Not a breaking change — a contract restoration" because `commands.md` on `main` already documented the shared gate. Also scopes the refusal to outputs the pass would actually overwrite (preserved clients, layout-moved outputs). A new pin still overwrites machine-managed content without a flag.
    - `5ad5009` (2026-08-12): keep the report when the gate refuses (additive `refused` field).
    - Docs: "Changed in 0.13.0" note at `commands.md:628-631`; `guides/lifecycle.md:91-95` documents that a refused update has already rolled the lock forward ("the refusal stops the write to your file, not the write to the lock").
    - Code comment recording the history: `src/command/update.rs:132-143`.
