## 3. Per-harness payloads inside one artifact

No kind carries a payload per harness in separate layers or files. The layout code accepts exactly one content layer plus at most one requires layer (`src/oci/manifest.rs:78-104`, `LayerLayout::{Content, ContentWithRequires, BundleMembers}`); zero, three or more layers, two content layers or two requires layers return `UnsupportedLayout`. The settings ADR explicitly considered and rejected "one layer per harness; a tar payload" in favour of "one JSON document with vendor objects, in one layer" (`.agents/adr/adr_settings_artifact_kind.md:101`). So the only per-harness carrying in the repo is vendor-keyed tables inside one document (settings) or vendor-namespaced metadata keys inside one markdown/TOML file (skills, rules, agents, hook `<vendor>.event`).

Client selection is by installed/selected client set (`ClientTarget`, detection per `subsystem-client-detection.md`), then per kind by `client_supports_kind` (`src/install/installer.rs:1748`) and `kind_is_permanently_declined` (`:1791`), keyed on scope. A client with no payload or no surface: permanent decline logs at debug; a scope gap logs a warning; settings with zero applicable pieces across all clients reports `gated` with cause `no-applicable-settings` (`adr_settings_artifact_kind.md:631`). A multi-payload layout (shape B with several layers) would be a new `LayerLayout` variant; older grim treats an unknown layout as 65 `expected a single-layer artifact` (`docs/src/content/docs/stability.md:915`). A shape B inside one tar layer (a directory per harness) has precedent in neither kind; hook is the only tar kind that carries code, and its tree is harness-neutral.

## 4. Stability constraints

- AGENTS.md Principle 9 (`AGENTS.md:170-175`): additive only; schemas, layouts and renderers need upgrade fixtures and self-heal proofs. A new kind is additive; `deny_unknown_fields` on lock and state means an older grim refuses a lock holding the new array.
- `docs/src/content/docs/stability.md:22-33` freezes CLI, JSON reports and `grimoire.toml`/`grimoire.lock`, with experimental exemptions for hooks (`:525-578`) and settings (`:580-599`). The settings exemption lists what may change in any minor: the config table, the lock array, the experimental key, the document grammar, the typed key list, schema output, consent flags, report keys, exit codes, the record file format. Not exempt: literals added to otherwise-frozen reports (additive policy).
- `.agents/adr/adr_render_layout_stability.md` (Accepted 2026-07-09): vendor on-disk layout is outside the 1.0 contract, discoverable via `grim status --format json`; plugin rendering is deferred as a render mode on the Claude vendor, not a new `ClientTarget` (Option 2 rejected), because Claude's registration surfaces were undocumented and Copilot's churning. The same reasoning applies to a mod format that is a builtin of one client build.
- What `[options.experimental]` bought: a flag-off no-op (declares and locks; phase fetches nothing, writes nothing, status `gated`; `adr_settings_artifact_kind.md:184-186`), a statement that the surfaces "may change in any minor release, in ways that are not always additive" for hooks (`stability.md:525-527`), and the OCI wire format frozen anyway (`stability.md:569-572`: a `schema = 1` `hook.toml` stays readable by every future grim). Flag keys: `src/config/declaration.rs:285-357` (`hooks_enabled`, `settings_enabled`); the flag is not the gate, workspace consent is (`:351-353`).
- Older grim behaviour, from `stability.md:883-899` (settings vs 0.15.1) and `test/tests/test_old_grim_settings.py`: lock with the new array, exit 78 on status/install, and `lock`/`add`/`update` overwrite it silently; `grimoire.toml` with the new table or key, 78; a bundle with a member of the new kind or a `requires` edge to one, 65 and nothing installed; `grim add` of the new artifact, 65; global state holding its record, 74; consent record keys dropped (re-prompt). Mechanism for the artifact itself: `kind_from_manifest` (`src/oci/annotations.rs:371`) returns `None` for an unknown annotation value, and the fetch path then fails with "is not a Grimoire artifact (no kind on the manifest)" (`src/fetch.rs:347-356`); the wire kind literal is written as the annotation so an older reader cannot mistake it for another kind. A user on an older grim therefore sees a refusal, never a silent partial install, for direct adds; the lock-rewrite hole above is the exception.

## 5. Trust, as written

- `.agents/adr/adr_artifact_trust_model.md:62` decision 2: all kinds equally trusted, no per-kind consent. Two scoped exceptions, hooks (2026-08-28) and settings (`:97-113`, 2026-11-04). The stated reason is release history: these kinds had never shipped, so they could ship gated without a Principle 9 breach. The text says "this is not an invitation to gate the next kind" (`:105`, box text restated at `:166-168`), and a "kind X is executable, therefore gate it" review finding is declared invalid (Consequences). A third gated kind needs an ADR amendment, not a reviewer's finding.
- `.agents/adr/adr_hook_workspace_consent.md:169-200`: the gate is a per-workspace consent record `$GRIM_HOME/hooks/consent/<workspace-key>.json`, kind-agnostic (`<binding>@<registry>/<repository>` entries, settings keys beside them), flag pair `--trust-workspace`/`--no-trust-workspace` with `--trust-hooks` aliases, no environment form. `:361-386` records the I2 trade: workspace is a name, content digest still pins bytes.
- `.claude/rules/arch-threat-model.md:33-50`: grim "arms code that a client executes automatically"; attackers T1 malicious publisher, T2 mutable-identity swap, T3 untrusted cloned repo, T4 prompt injection, T5 local process; non-goals N1 insider with commit access, N2 compromised machine, N3 malicious client, N4 user bypassing a shown gate, N5 own-config DoS. I1 (`:67`): anything armable, including the executed payload, lives under `$GRIM_HOME` or a per-developer repo-resident surface the client treats as local; a thing is armable if grim will execute it or read arming instructions from it.
- As written, an executable-code kind falls under the hook exception's mechanism: the workspace consent record and flag pair, the experimental flag, payload under `$GRIM_HOME` (I1), digest pin (I2). Whether a third kind may be gated is explicitly not settled by the text; whether a mod is "armed by grim" or merely "installed for the client to run" is open. Note the tension: `docs/src/content/docs/clients.md:128-133` ("grim will never install a plugin, extension, or any other runtime code into your client") and `:767-769` ("grim never installs code into a client") were written before or beside hooks; hooks are grim-run dispatcher code, not client-loaded code, so the sentence still reads as true for hooks but not for a mod the client loads in-process.

## 7. Local evidence of the mod format (this machine, Claude Code 2.1.327)

A mod is a Claude Code plugin with a hooks module, authored through the builtin `plugin-authoring` skill (shipped inside the binary, extracted at load to `/tmp/claude-1000/bundled-skills/2.1.327/<hash>/plugin-authoring/` with `reference.md`, `look.md`, `types/claude-code.d.ts`, six examples). Layout:

- `<mods root>/<mod-name>/.claude-plugin/plugin.json`: `{ "name", "version", "description" }`; optional `"types": "./types/index.d.ts"`, `userConfig`, `dependencies`.
- `hooks/hooks.json`: `{ "modules": ["./register.tsx"] }`, one path relative to the file.
- `hooks/register.tsx` or `.ts`: `export const register: Register = (on, options) => { ... }`, type imported from `'claude-code'`; hooks are `on(event, matcher?, ($, e, next) => ...)`.
- Optional `types/index.d.ts`: contract for the mod's `$.state` values; `claude plugin validate` checks it. Engine lays editor types into `<mod>/.claude-plugin/types/`.
- Mods root for this session: `~/.claude/dev-mods/<session-id>/<mod-name>/` (directory exists, empty). Hot reload asks the person once ("Turn on the mods Claude writes in this session?"); `claude --plugin-dir <folder>` loads one otherwise; `CLAUDE_CODE_PLUGIN_DIRS` also named in `reference.md`.
- Capabilities per the skill table: pane (`$.ui.open`, `ui.render` on `Pane`), band above the prompt (`AbovePrompt`), tool-call row decoration, desktop context-menu row, status line entry (`$.ui.status`), theme (`$.theme.set` at `session.start`), toast (`$.ui.toast`), tool-call hooks (`tool.call`), prompt hooks (`prompt.submit`, `prompt.compose`), audio, slash commands (`$.command.register` + `command.run`), plus `$.clock/$.tool/$.agent/$.model/$.fs/$.process`. UI elements come from `$.ui.resolve(e)` by surface (`terminal`, `desktop`, `vscode`, `mobile`), so one module already adapts across Claude surfaces.
- Sharing: a GitHub repo with `.claude-plugin/marketplace.json`; consumers run `/plugin install <mod> --marketplace <owner>/<repo>`; the skill defines a secret-scan step before push (`mcp__plugin-authoring__scan_secrets`). This is the existing Claude plugin marketplace channel, so the packaging and distribution machinery matches the plugin format grim already knows how to export.
- Runtime storage: `~/.claude/plugins/store/<plugin>_<marketplace>-<hash>.json` holds per-plugin key/value state (builtin `cc-plugin-agents-md`, `cc-plugin-diff`, and marketplace plugin `ponytail`); `$.state` is session scoped, `$.store` across sessions (skill text). Installed plugins: `~/.claude/plugins/installed_plugins.json` (version 2, per-scope entries with `installPath`, `version`, `gitCommitSha`).
- Two things not checked: no mod files exist under `~/.claude` or the repo `.claude/` (none were authored; nothing was written under the mods root), and whether Claude Code reads mods only from plugins in this format or also from a standalone mods directory is not stated beyond the skill text. The manifest has no harness key; a mod is Claude-only by construction (`from 'claude-code'`), and no second harness was found documenting an equivalent in this repo's research.

## Evidence by axis for the two candidate shapes (no recommendation)

Shape A: kind supported by one harness.
- For: matches the format (a Claude-only module API, `claude-code` import); precedent for single-vendor surfaces (Claude `claudeMdExcludes`, `settings_fields()` returning a subset of clients; `client_supports_kind` already answers per kind per client); watchlist reopen text names exactly this ("new kind, ADR first"); smaller blast radius for the first release (still 100+ files by the settings/hook measures); no payload translation to maintain.
- Against: the declined-kinds text says "No other client reads them, and an artifact kind is a publish, lock and render contract" (`clients.md:762-764`); a one-harness kind bakes a vendor name into a frozen contract surface (kind literal, lock array) unless named neutrally; every Principle 9 constraint applies to a kind only one vendor can ever render.

Shape B: harness-neutral kind, a payload per harness.
- For: settings is the in-repo precedent for vendor-keyed content in one layer, with vendor-key validation, one consent record and unknown-vendor warnings already built (`adr_settings_artifact_kind.md:196-219`); hook shows a neutral kind with native passthrough per vendor; the metadata convention (`vendor-metadata.md`) is the same split (common once, vendor-unique under `<vendor>.`).
- Against: no second harness has a documented in-process UI extension surface in this repo's research (none found); the layer layout admits one content layer (`manifest.rs:78-104`), and the settings ADR rejected one layer per harness; a tar of per-harness directories has no precedent, and a payload per harness multiplies the code a user consents to (each harness's payload is executable); older grim answers an unknown layout with 65.

## negative:

- No document in the repo defines, mentions or decides on mods. The prior-art decline row covers output styles, themes (plugin component form), monitors, LSP and workflows, not hooks-module mods.
- `docs/src/content/docs/clients.md:128-133` ("never install runtime code into a client") contradicts a mod kind if read literally; the hook kind coexists with it only because grim runs the dispatcher.
- No kind has more than one content layer, and settings recorded that rejecting per-harness layers was a ratified choice.
- No second harness with an equivalent module API was found in repo research.
- The plugin export cannot carry hooks today (`family.rs:165`), so an export route for mods is not a ready path.
- Local mods dir empty; nothing observed first hand beyond the builtin skill's text.

## leads:

- Prior-art web scan: what other harnesses expose for in-process UI extensions (OpenCode plugins, Zed extensions, Cursor, Droid, Copilot extensions) to test the shape B premise.
- Vendor semantics: the Claude Code plugin docs for `hooks.json` `modules`, the stability of the `claude-code` module API, and whether grim could install a mod as an ordinary Claude plugin (marketplace route) instead of a new kind; the export `admits` seam is where this lands.
- Threat model recon: what in-process mod code can do that a grim hook cannot (`$.fs`, `$.process`, `$.model` in `reference.md`), and whether consent plus digest pin is sufficient, or the I1 payload-location rule applies (mod code is loaded by the client from its own plugin dir).
- Repo archaeology: the issue behind `clients.md` "Known gaps" for Claude kinds ([grimoire-rs/grimoire#141](https://github.com/grimoire-rs/grimoire/issues/141)) and any user requests since.
- Stability lane: how the lock/older-grim rows would read for a mod kind, reusing the settings table at `stability.md:883-899`.
