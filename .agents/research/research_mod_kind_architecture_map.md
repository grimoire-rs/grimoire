## Direct Answer

A `mod` kind is a normal tar-layer directory kind (like `skill` and `hook`) with three unusual parts: a per-harness directory layout inside one layer, generated wrapper files at install time, and a consent record that loses its kind and (as written in the dossier) its binding. Roughly 50 Rust files carry an `ArtifactKind::Settings` arm today, so the kind-enum fan-out is the mechanical bulk. The three decisions with real design cost are the consent-record change (it conflicts with an Accepted ADR decision), the project-scope Claude load route (it collides with keys the settings kind already owns), and the "no runtime code" promise (a grim-generated wrapper sits on the wrong side of an Accepted ADR's class 3 unless that ADR is amended).

- What "one record, workspace plus a plain list of `registry/repository` sources, no kind, new path `$GRIM_HOME/consent/`" touches:
  1. `ConsentRecord` field set. Today `hooks: BTreeSet<String>` and `deny_unknown_fields`; a rename to `sources` changes the record JSON, which is allowed (experimental), and an old grim reading a new record at the *old* path cannot happen because the path moves.
  2. `consent_key`, `declared_consent_key_for`, `consent_key_for`, `split_by_kind`, `is_settings_key`, `SETTINGS_KEY_PREFIX` collapse: the per-kind split disappears, so `ConsentPolicies::new` (`policy.rs:499`) evaluates one set, and the settings and hooks policies share one `Consent`. `HookPolicy::kind` still picks the flag. This also removes the "hook binding named `settings:x`" guard at `consent.rs:207`.
  3. **Semantics change from per-binding to per-source.** `evaluate` (`consent.rs:240`) compares `declared.difference(&record.hooks)`; with sources the declared set is the set of `registry/repository` of every gated artifact, so a second hook from an already-listed repository no longer drifts. This is the weakening named in 1.2 item 2.
  4. Path: `consent_dir` moves from `hooks_dir(grim_home).join(CONSENT_DIR)` to `grim_home.join("consent")`. `ensure_consent_dir` (`hook_dispatch.rs:~215`) currently calls `ensure_hooks_dir` for its parent; it would stop. `RESERVED_ARTIFACT_NAMES` (`src/oci/hook.rs:188`) contains `consent` because the directory sits under `hooks/` and a hook bound as `consent` would collide; after the move the entry is dead weight but removing it from a frozen reserved list would make a currently refused hook name legal. Keep it (additive-only discipline), and the test `every_grim_owned_name_under_hooks_is_a_reserved_binding_name` (in `hook_dispatch.rs`) must be updated to stop expecting a `consent` child under `hooks/`.
  5. Readers: the file list in 1.2 item 3. Seven acceptance and manual tests and the golden `consent.project.json` fixture.
  6. Old records: dossier says ignore and delete `$GRIM_HOME/hooks/consent/` on first new write. An old grim on the same `$GRIM_HOME` keeps reading the old path, so a user who runs both versions has two records (old one stale, new one live); the old grim never sees the new consent and re-asks. Fail-safe in both directions, but "delete the old folder" lets a newer grim revoke consent for an older grim.
  7. Global scope: always consented, no record (unchanged); `grim hook allow --global` exits 64.
  8. The flag pair: `--trust-workspace` / `--no-trust-workspace` (aliases `--trust-hooks` / `--no-trust-hooks`) is already kind-neutral for hook and settings since 0.16.0 (`src/cli/options.rs`, `HookTrustOpts`); a mod needs only a new `[options.experimental] mods` flag read, and the pair "beats the consent record in both directions" (owner decision 2026-08-28). `grim consent allow|revoke|list` is already an alias of `grim hook`.

## Key Findings

1. The dossier's consent change is not a restatement: it conflicts with `adr_hook_workspace_consent.md` decision 2 (binding in the key) and with the code comment at `src/hook/consent.rs:172-175` that records the attack the binding stops. Whether source-level consent is acceptable is an owner call that the ADR must make explicit.
2. `enabledPlugins` is already a reserved key that the settings kind refuses (`src/install/vendor.rs:2383-2392`), and `extraKnownMarketplaces` is a settings-owned row restricted to GitHub sources (`src/oci/settings.rs:26`, `:30`). The "register a directory marketplace in project settings" route therefore needs a new key-owner decision, not just a new write.
3. `com.grimoire.requires-features` protects only `0.16.0` and later: `v0.15.1` has no `features.rs`. Fail-closed on 0.15.x rests on `deny_unknown_fields` for config and lock (exit 78), the bundle and `requires` 65 path, and the `global.json` 74 path, as the settings matrix recorded.
4. `client_supports_kind`, `admits`, `status` drift and `expected_outputs` all decide support without the artifact in hand; "supported clients are the directories present" needs the harness set carried in an annotation or lock field, or those predicates change signature.
5. `test/tools/p9_diff.py` `ADDITIVE_STDOUT_KEYS` and the three golden `consent.project.json` fixtures are silent gates that the consent move and any new report field will trip.

## Recommendation

For the architect: settle three decisions before design starts, because each blocks the shape of the rest. (a) Source-versus-binding consent, as an explicit amendment of decision 2 with the hostile-second-hook scenario answered. (b) Whether a grim-generated plugin wrapper is class 3 under `adr_vendor_support_tiers.md`, and if not, the sentence that carves it out of both the ADR and `clients.md#compensation`. (c) Where the supported-harness set lives so predicates can read it without the content layer. Everything else (kind enum, build, config, lock, docs) follows the `settings` and `hook` checklists mechanically.
