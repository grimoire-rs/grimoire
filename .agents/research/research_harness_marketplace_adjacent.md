# Research: Catalog projections into foreign channels — adjacent-field precedent

## Metadata

**Date:** 2026-09-15
**Domain:** packaging
**Triggered by:** /hex-discuss harness-native-marketplaces
**Expires:** 2027-03-15

## Direct Answer

Every ecosystem examined runs some form of "canonical registry + generated projection into a
vendor channel," and the pattern is stable, not experimental — but it survives only when three
conditions hold: (1) the projection is generated by automation keyed off the canonical source
(bot/Action/checker), never hand-maintained, (2) it is explicit about what it cannot carry forward
(signatures, revocation, private scoping) rather than silently degrading, and (3) it exists because
the foreign channel is otherwise *unreachable* from the canonical one (a ToS wall, a different
runtime, a different discovery surface) rather than as a redundant nicety. Where a projection loses
fidelity silently (Terraform network mirrors dropping signatures by default, jsDelivr/unpkg/cdnjs
resolving to whatever a compromised upstream currently serves) it becomes an attack surface
(polyfill.io) or a trust footgun that needs a second mechanism (`terraform providers lock`) bolted
back on. Where the projection is the *only* legal path into a channel (Open VSX for VSCodium/Cursor)
it grew into critical infrastructure in its own right (300M+ downloads/month) rather than
cannibalizing the canonical registry, because the two serve non-overlapping runtimes. No case
examined shows a maintained generator being retired for lack of value; retirements found were
either registry deprecations unrelated to the projection pattern (GCR shutdown) or organic
migrations toward a *more* native distribution (Bitnami's move off classic `index.yaml` onto OCI).

## Key findings

- **Automation-or-nothing is the load-bearing rule.** Every durable projection examined is bot- or
  Action-driven off the canonical source (cdnjs 15-min scan, Homebrew 3-hourly autobump, Scoop
  hourly Excavator, Flathub hourly checker, nixpkgs continuous `r-ryantm`). The one hand-maintained
  case (Open VSX dual-publish) has staleness baked in as the *known, accepted* cost, not a surprise —
  publishers who don't run the second `publish` step simply don't appear there. [cdnjs
  autoupdate](https://github.com/Ultimater/cdnjs/blob/master/documents/autoupdate.md),
  [Scoop wiki](https://github.com/ScoopInstaller/Scoop/wiki/App-Manifest-Autoupdate).
- **Version-only automation silently drops nested pins.** Homebrew's `autobump --bump-synced` updates
  the top-level version/tarball but does not regenerate transitive resource stanzas, so pinned
  sub-dependencies drift out from under a "successfully bumped" formula. This is the general shape of
  "the generator updated the pointer but not everything the pointer implies." [Homebrew
  discussion](https://github.com/orgs/Homebrew/discussions/6183).
- **Mirrors silently drop cryptographic guarantees unless a second, explicit mechanism restores them.**
  Terraform's network mirror protocol has no signature field at all — only an optional hash — and
  installs unverified if even that's missing. Trust is only recovered because `terraform providers
  lock` snapshots official checksums *before* trusting a mirror long-term. A projection is safe only
  if it either (a) never claims a security property it can't carry, or (b) ships the bolt-on that
  restores it. [HashiCorp provider network mirror protocol
  reference](https://developer.hashicorp.com/terraform/internals/provider-network-mirror-protocol).
- **A projection that resolves live, unpinned content is a supply-chain attack surface.** polyfill.io
  (acquired by Funnull, then injecting device-targeted malware into 100k+ sites via
  `cdn.polyfill.io`) is the sharpest cautionary case: a CDN-style live-resolving mirror inherited the
  *trust* of "it's just a copy of a well-known open-source library" without carrying forward any of
  npm's provenance. Cloudflare/Fastly/Google had to intervene with their own rewritten mirrors as
  incident response. [Sonatype writeup](https://www.sonatype.com/blog/polyfill.io-supply-chain-attack-hits-100000-websites-all-you-need-to-know),
  [Censys analysis](https://censys.com/blog/july-2-polyfill-io-supply-chain-attack-digging-into-the-web-of-compromised-domains/).
- **A projection is worth maintaining when the foreign channel is legally or technically unreachable
  from the canonical registry, not just "more convenient."** Open VSX exists because Microsoft's
  Marketplace ToS bars other products (VSCodium, Cursor, Windsurf, Gitpod, Theia) from using it at
  all — it is not a redundant nicety, it is the *only* path, which is why it grew to 300M+ monthly
  downloads on its own weight rather than syphoning traffic from the Marketplace. [Eclipse
  announcement](https://newsroom.eclipse.org/news/announcements/open-vsx-registry-surpasses-300-million-monthly-downloads-industry-leaders-back),
  [VSCodium docs](https://github.com/VSCodium/vscodium/blob/master/docs/extensions.md).
- **CDN/mirror usage and canonical-registry usage are measured on disjoint axes, so "cannibalization"
  is hard to even detect.** npm's own download counter only counts registry pulls; CDN `<script>` tag
  loads never touch it. This means ecosystems adopting a CDN projection have no built-in signal for
  whether it grew or replaced canonical adoption — the metric gap itself is a finding. [npm download
  counts explainer](https://blog.npmjs.org/post/92574016600/numeric-precision-matters-how-npm-download-counts-work.html).
- **Freshness bots need a manual audit gate when the source format is unstable across releases.**
  cdnjs auto-detects new npm/git versions but holds every update for human review because file layout
  inside packages changes release to release — and any library that can't be automated at all is
  simply dropped from the projection rather than hand-maintained indefinitely. [cdnjs
  CONTRIBUTING.md](https://github.com/cdnjs/packages/blob/master/CONTRIBUTING.md).
- **Even within one ecosystem, "the projection" is often two independently-generated layers, not one.**
  Helm's classic `index.yaml` is generated by the chart publisher's own CI
  (`chart-releaser-action`) onto their own GitHub Pages; ArtifactHub is a *second*, separately-run
  crawler/indexer on top of that (or on top of OCI registries) for search/discovery, which OCI
  natively lacks. The "vendor store" and the "search index into the vendor store" are commonly
  separate generators with separate owners. [chart-releaser-action](https://github.com/helm/chart-releaser-action),
  [ArtifactHub Helm charts docs](https://artifacthub.io/docs/topics/repositories/helm-charts/).

## negative:

- No direct evidence was found of a maintainer publicly writing "we stopped generating the mirror
  because it wasn't worth it" for any of the 7 requested cases — searches for retirement/regret posts
  surfaced only unrelated container-registry *product* shutdowns (Google Container Registry → Artifact
  Registry, March 2025) which are not examples of this catalog-projection pattern being abandoned.
  Absence of evidence, not evidence of absence — the search terms may simply not match how such posts
  are titled. [GCR shutdown notice](https://groups.google.com/a/kubernetes.io/g/dev/c/U5jTmvhoYLg) (tangential, not a projection retirement).
- The JetBrains `updatePlugins.xml` case does not actually fit the "generated projection of a public
  registry into a foreign channel" pattern — it's an independent, usually hand-maintained private
  catalog that IDEs merge with Marketplace search results, not a mirror of the Marketplace. Kept in
  the table per the brief's explicit request, flagged as a weak/non-matching case rather than dropped.
- Could not find a quantitative study directly comparing "adoption growth in the canonical registry
  attributable to the existence of a CDN/mirror projection" — the npm-CDN axis-4 answer above
  (disjoint metrics) is inferred from how download counting works, not from a study that measured
  causal adoption lift. Treat as a plausible but unconfirmed mechanism, not a cited result.
- Nix's `nixpkgs-update`/`r-ryantm` and Flathub's checker are not, strictly, "canonical registry →
  foreign vendor channel" projections — nixpkgs and Flathub *are* the canonical distribution for their
  respective ecosystems. They're included because the brief named them explicitly and because the
  freshness-automation mechanism generalizes directly to the projection case; the fidelity/adoption
  axes read differently for them than for a true secondary-channel mirror.
- One 2026-vintage source (jsDelivr Q1 2026 latency/outage benchmarking, cited via BlazingCDN blog) is
  a third-party comparison-site article, not a primary jsDelivr/unpkg source — treat the specific
  latency numbers (P50/P95 ms) as indicative, not verified against jsDelivr's own status/statistics
  page.
- Found but did not fully chase: a Check Point report describing jsDelivr as having been used to
  expose users to phishing/malicious packages ("invisible to security tools") — relevant to the
  fidelity-loss axis for CDN projections generally, but not chased to a primary incident writeup or
  date-confirmed; flagged as a lead below rather than asserted as fact.

## leads:

- Chase the Check Point / Hackread reporting on jsDelivr being used as a phishing/malicious-package
  vector — if confirmed, it's a second CDN-trust-erosion case alongside polyfill.io, specifically
  implicating a *reputable* mirror rather than a hijacked standalone domain.
- China-region npm/registry mirrors (cnpm, Taobao/npmmirror, Aliyun) — full registry-to-registry
  mirroring rather than vendor-channel projection, but worth a follow-up if the harness cares about
  *registry* mirrors (offline/regional) as opposed to *vendor-store* projections.
- Docker Hub official images mirrored onto `ghcr.io` / cloud-provider registries — another
  generated-projection-into-a-different-distribution-surface case, not chased here for time.
- Homebrew-core's `BrewTestBot` verification pipeline (checksum/signature/notarization checks before
  a cask auto-bump lands) is a strong worked example of "what verification a generator should run
  before publishing a projected update" — worth a deeper read if the harness project wants a concrete
  verification-gate template.
- WinGet manifest auto-generation (winget-pkgs community PRs, `wingetcreate`) was not covered here but
  is structurally identical to Scoop/Homebrew and would round out the picture if a fourth
  Windows-ecosystem data point is wanted.
