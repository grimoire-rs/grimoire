# Research: Harness-native extensions ("mods") and how a package manager could model them

## Metadata

**Date:** 2026-11-18 (every URL below was fetched or searched on this date unless stated otherwise)
**Domain:** packaging
**Triggered by:** Discussion on shipping "Claude mods" through grimoire. Decides whether harness-native extensions become (A) a single-harness artifact kind or (B) a harness-neutral kind with one payload per harness.
**Expires:** 2027-02-18 (the mods format is under three months old and its docs say events and methods change between releases)
**Lane:** prior-art web scan. Findings, `negative:` and `leads:` only. No recommendation.

Verification marks: "verified" means the primary page was fetched in this run. "Search-only" means only a search snippet or a secondary source was seen. "Unverified" means not confirmed.

## Direct answer

A Claude Code mod is a Claude Code plugin whose `hooks/hooks.json` carries a `modules` key pointing at one JavaScript or TypeScript file. It has no format of its own beyond that key, and it ships through the same plugin marketplaces. Most other harnesses have a code extension surface (OpenCode, Kilo, pi, Amp, Cline, OpenClaw, Copilot CLI) or a theme file (Codex, Gemini, OpenCode, Warp), but each one is harness-specific code against that harness's own API. The only cross-vendor spec found, Agent Plugins 1.0, standardizes skills and MCP servers only and gives each vendor a reverse-domain `extensions` namespace plus a same-named directory for everything else. That is shape B in the wild. Prior art for both shapes exists. No concrete case of a generic per-target type that ended up with one target was found.

## 1. Claude Code mods

All from https://code.claude.com/docs (fetched 2026-11-18) unless noted.

**What a mod is.** "A mod is a plugin that changes how Claude Code looks and behaves. It's made of JavaScript or TypeScript event handlers" ([mods overview](https://code.claude.com/docs/en/plugins/mods/overview.md)). The plugin overview defines it the same way: "A hooks module: hooks written as JavaScript functions, which can also draw panes and add commands. A plugin that has one is called a mod" ([plugins overview](https://code.claude.com/docs/en/plugins)). The word "mod" is therefore a plugin that contains a hooks module, not a separate package type.

**On-disk format.** Three files in the smallest case: `.claude-plugin/plugin.json` (the ordinary manifest, "Mods add no required fields"), `hooks/hooks.json` with `"modules": ["./register.js"]` (one path, relative), and the module itself, which exports `register(on, options)`. Allowed extensions: `.js .mjs .cjs .jsx .ts .mts .cts .tsx`, ES module ([mods reference](https://code.claude.com/docs/en/plugins/mods/reference.md), [create](https://code.claude.com/docs/en/plugins/mods/create.md)). "Having [the `modules` key] is what makes the plugin a mod." The manifest has an optional `types` field pointing to a `.d.ts` for `$.state` values and `$` nouns ([manifest reference](https://code.claude.com/docs/en/plugins/manifest-reference.md)).

**Runtime.** Handlers run inside the Claude Code process, apparently in a worker thread. The docs say a crash loop "unloads every mod that isn't built in" after three worker crashes ([admin](https://code.claude.com/docs/en/plugins/mods/admin.md)). "You don't need Node.js, a bundler, or a build step, because Claude Code loads `.js` and `.ts` files directly" ([create](https://code.claude.com/docs/en/plugins/mods/create.md)). Static analysis constrains the code: event names must be string literals, `$` calls must be written in full, only relative imports or `claude-code` are allowed. `claude plugin validate` prints `hooks:` and `calls:` lines for review.

**Capabilities.** Panes beside the transcript, a band above the prompt, restyling of built-in elements (spinner, tool row, ask dialog), tool-call and prompt interception, `/commands` without a model turn, model calls, timers, `$.theme` backdrop (v2.1.319 or later). Not the permission prompt ([overview](https://code.claude.com/docs/en/plugins/mods/overview.md)). The local skill's wording "theme, panel, band, status line, toast, slash command, hook on tool calls" is broadly consistent. I did not find the word "toast" or "status line mod" in the fetched pages (unverified as a named mod element).

**Install locations and scope.** Same as plugins. User, project and local scope through `enabledPlugins` in `~/.claude/settings.json`, `.claude/settings.json`, `.claude/settings.local.json`. Files land in `~/.claude/plugins/cache/<marketplace>/<plugin>/<version>/`. A plugin directory saved under `~/.claude/skills/` or `<project>/.claude/skills/` also loads ("skills-dir" origin). Session-only via `--plugin-dir`. A mod Claude writes in-session goes to `~/.claude/dev-mods/<session-id>/` and loads only in that session unless copied out ([loading](https://code.claude.com/docs/en/plugins/loading.md), [create](https://code.claude.com/docs/en/plugins/mods/create.md)).

**Enabling.** On by default. Per mod: disable in `/plugin`. All mods one session: `--safe-mode`. All mods: `"disableAllHooks": true` in settings. Org: `allowManagedModsOnly` on the built-in guard `cc-plugin-sec-default@builtin` ([overview](https://code.claude.com/docs/en/plugins/mods/overview.md), [admin](https://code.claude.com/docs/en/plugins/mods/admin.md)).

**Distribution.** Plugin marketplaces (`marketplace.json`, sources: relative path, github, url, git-subdir, npm, archive, command), copy a folder with `--plugin-dir`, Anthropic's directory, sample repo `anthropics/claude-code-playground` ([overview](https://code.claude.com/docs/en/plugins/mods/overview.md), [marketplace reference](https://code.claude.com/docs/en/plugins/marketplace-reference.md)). Blog: "Mods ship inside plugins, so you install and share them like any plugin" ([blog, dated Oct 1 2026](https://claude.com/blog/claude-code-mods)).

**Trust prompt.** There is no per-mod consent prompt on first load. The docs warn that "A mod is code that runs with your permissions" and mods "aren't sandboxed". The only gate named is the folder trust dialog: "In an interactive session in a directory the user hasn't trusted yet, no mod loads until they answer the trust prompt" ([admin](https://code.claude.com/docs/en/plugins/mods/admin.md)). A project-scope plugin additionally needs that trust check ([loading](https://code.claude.com/docs/en/plugins/loading.md)). Hot reload of a Claude-written mod asks a question in default mode. A built-in guard blocks a user's mod from rewriting managed instructions where managed settings exist.

**Version introduced.** The anthropics/claude-code CHANGELOG, fetched via raw GitHub: "2.1.287 - Added Claude Mods: plugins may now modify deeper behavior" ([CHANGELOG.md](https://raw.githubusercontent.com/anthropics/claude-code/main/CHANGELOG.md)). The overview says mods are on by default from v2.1.287 in the terminal and v2.1.286 in the Desktop app, and that an earlier env flag `CLAUDE_CODE_ENABLE_FUNCTION_HOOKS` existed in "early access" and is now ignored. Blog date: 2026-10-01 ([blog](https://claude.com/blog/claude-code-mods)). The changelog head was 2.1.327 on fetch day.

**Stability.** No "experimental" or "beta" label on mods themselves. The explicit statements are the opposite of a freeze: "The events and methods can change between releases, so trust these files over any page" and "your README is the place to say which Claude Code version you tested with" ([create](https://code.claude.com/docs/en/plugins/mods/create.md)). The reference says its entries cover "the CLI and the Desktop app as of v2.1.290, and the VS Code extension as of v2.1.299", and that the GitHub copy of the types "can be older than the Claude Code version you have installed" ([reference](https://code.claude.com/docs/en/plugins/mods/reference.md)). Changelog entries 2.1.323 to 2.1.327 change mod behavior in every release (e.g. 2.1.323 "Changed mods: a `*`, namespace or negated hook on `engine.create` now only observes"). Other Claude surfaces call out stability separately: `experimental.themes` and `experimental.monitors` in `plugin.json` are inside an `experimental` key "whose manifest shape may still change" ([manifest reference](https://code.claude.com/docs/en/plugins/manifest-reference.md)). Code Mode is labeled "an experimental opt-in" in the changelog.

**Version gating exists.** `engines: { "claude-code": ">=2.1.400" }` in `plugin.json` and in marketplace entries, requires v2.1.323 or later. Older versions (v2.0.15 to v2.1.75) reject a manifest or whole marketplace containing the field with an `Unrecognized key` error ([manifest reference](https://code.claude.com/docs/en/plugins/manifest-reference.md), [marketplace reference](https://code.claude.com/docs/en/plugins/marketplace-reference.md)).

**Relation to earlier surfaces.**
- Settings hooks: shell command, HTTP request or prompt configured in settings, run outside the process. Mods are in-process functions. "Claude Code calls both kinds hooks"; docs rename the old kind "settings hook". Both can live in the same `hooks/hooks.json` (`modules` beside `hooks`) ([overview](https://code.claude.com/docs/en/plugins/mods/overview.md), [reference](https://code.claude.com/docs/en/plugins/mods/reference.md)).
- Status line: a separate pre-existing setting; `disableAllHooks` also turns it off, `allowManagedModsOnly` leaves it alone ([overview](https://code.claude.com/docs/en/plugins/mods/overview.md), [admin](https://code.claude.com/docs/en/plugins/mods/admin.md)).
- Output styles and themes: plugin components with their own directories (`output-styles/`, `themes/`) in the standard layout. Themes are JSON files and sit under `experimental.themes`. These are declarative, no code ([manifest reference](https://code.claude.com/docs/en/plugins/manifest-reference.md)). A mod can additionally set a backdrop with `$.theme`.
- Plugins: a mod is a plugin. One plugin can hold skills, agents, MCP servers, settings hooks and a mod together ([overview](https://code.claude.com/docs/en/plugins/mods/overview.md)). `allowManagedModsOnly` and `disableAllHooks` "stop a mod and leave the rest of its plugin in place" (same page).
- Reserved names: plugin names starting `cc-plugin-` or equal to `claude-mods` are refused by `claude plugin validate` ([manifest reference](https://code.claude.com/docs/en/plugins/manifest-reference.md)). Two enabled plugins with the same manifest name: only one hooks module loads ([loading](https://code.claude.com/docs/en/plugins/loading.md)).

## 3. Shared semantic core?

Findings:
- No cross-vendor spec covers code extensions. Agent Plugins 1.0.0 standardizes "a portable package format for Agent Skills and MCP servers"; "the 1.1.0 working draft adds portable hooks" ([spec README](https://github.com/agentplugins/agent-plugins-spec)). Quote from the 1.0.0 text: "Other component types are outside the v1 format and do not affect conformance", rationale names commands, hooks, agents, rules and LSP servers as excluded ([spec 1.0.0](https://github.com/agentplugins/agent-plugins-spec/blob/main/spec/1.0.0.md)). Themes and UI are not mentioned.
- The manifest permits ten top-level fields only: `$schema, name, version, description, author, homepage, repository, license, keywords, extensions` ([spec 1.0.0 section 5.2](https://github.com/agentplugins/agent-plugins-spec/blob/main/spec/1.0.0.md)). "Clients MUST report and ignore each unknown field."
- The extension hook for vendor content: "Client-specific manifest data MUST be represented under a reverse-domain namespace in `extensions`." Each namespace also maps to a top-level directory of the same name, such as `com.example.client/`. "A client MUST ignore manifest entries for namespaces it does not implement" (same, section 8). The site adds: distribution, installation, permissions, user experience and client-specific capabilities "remain under each client's control" ([agent-plugins.org](https://agent-plugins.org/)).
- Copilot already uses it. "`com.github.copilot` ... holds Copilot-specific plugin content that the spec doesn't standardize. Other clients ignore it." Custom agents, commands, rules, hooks load from there. "The CLI and app also load extensions such as canvases" ([GitHub changelog 2026-08-12](https://github.blog/changelog/2026-08-12-agent-plugins-1-0-in-vs-code-copilot-cli-and-the-copilot-app)). Copilot says 1.0 was published August 6, 2026. Legacy plugin format stays supported "with no migration required".
- Who adopted the spec: Kiro Powers follow it ("recommends the Agent Plugins format for new powers", [Kiro](https://kiro.dev/docs/powers/)); Cursor has Agent Plugins at root `plugin.json` alongside `.cursor-plugin/plugin.json` ([Cursor](https://cursor.com/docs/plugins)); OpenClaw loads it ([OpenClaw](https://docs.openclaw.ai/plugins)); contributors named in a secondary report: AWS, Anysphere, Microsoft, OpenAI, Vercel, with Google joining ([search summary](https://www.dsebastien.net/agent-plugins-specification/), not primary). I did not find Anthropic or Claude Code adopting it. The manifest filenames collide: Claude uses `.claude-plugin/plugin.json`, Agent Plugins uses root `plugin.json` ([search-only](https://thenewstack.io/agent-plugins-portability-gaps/)). In one third-party test Claude Code's validator reported the unknown `extensions` field and ignored it at load (search-only, [startdebugging](https://startdebugging.net/2026/08/agent-plugins-1-0-vs-vendor-specific-plugin-formats/)).
- Convergent file layouts without a spec: Claude (`.claude-plugin/plugin.json`, `marketplace.json`), Copilot (`marketplace.json`, `PLUGIN-NAME@MARKETPLACE-NAME`), Qoder (`.qoder-plugin/plugin.json`, `name@marketplace-name`), OpenClaw (loads "Claude-compatible marketplace plugins via `--marketplace`"). These share the "plugin directory plus marketplace catalog" idea and the `hooks/hooks.json` file name, not event vocabularies.
- Hook event vocabulary is per vendor. Settings-style hooks use `PreToolUse` and `SessionEnd` in Claude and Junie, shell commands in Cursor, Gemini, Copilot, Qoder. Code-style events: `tool.call` in Claude mods and Amp, `beforeTool`/`afterTool` in Cline, `api.on(...)` typed hooks in OpenClaw. No shared registry found.

Conclusion for this question: the only shared semantic core is the portable layer (skills, MCP, and in 1.1 draft hooks). Code extensions that draw UI have no shared core. Evidence: each in the table uses its own API object and module signature.

## 4. Prior art for the modelling question

Per-target payload inside one package or index:
- **OCI image index.** `manifests[].platform` has REQUIRED `architecture` and `os` when present, optional `os.version`, `os.features`, `variant`; `platform` itself is OPTIONAL, "SHOULD be present if its target is platform-specific"; "If multiple manifests match a client or runtime's requirements, the first matching entry SHOULD be used"; `artifactType` is a separate optional string for non-image artifacts; "An encountered `mediaType` that is unknown to the implementation MUST NOT generate an error" ([image-index.md](https://raw.githubusercontent.com/opencontainers/image-spec/main/image-index.md)). Note: platform selection is a fixed os/arch vocabulary, there is no harness field. Grimoire's own OCI layer would need a new annotation or `platform.features` use. Not verified in this run: `platform.features` is "RESERVED for future versions" per the same page, so it cannot carry harness names today.
- **npm.** `os`, `cpu`, `libc` fields with allowlist and `!` denylist values; `engines` "advisory only and will only produce warnings" unless `engine-strict`; `optionalDependencies` "build failures do not cause installation to fail" ([package.json docs](https://docs.npmjs.com/cli/v11/configuring-npm/package-json)). The page did not state whether an `os`/`cpu` mismatch skips or errors (unverified). The Claude `engines` key copies the npm idiom, and Kilo's `engines: { "opencode": ... }` skips the plugin with a warning on mismatch.
- **VS Code platform-specific extensions.** "`vsce publish --target win32-x64 win32-arm64`"; a package published without `--target` "will be used as a fallback for all platforms that have no platform-specific package"; "Starting with version 1.61.0, VS Code looks for the extension package that matches the current platform" ([publishing docs](https://code.visualstudio.com/api/working-with-extensions/publishing-extension)). The target set is a closed list (win32-x64, linux-arm64, darwin-*, alpine-*, web).
- **Terraform provider registry.** Provider packages are keyed by `os` and `arch` which "must echo back" the request; each has `download_url`, `shasum`, `signing_keys`; a version lists `platforms` ([provider registry protocol](https://developer.hashicorp.com/terraform/internals/provider-registry-protocol)). Selection is client-driven, server returns one package per query.
- **Nix flakes.** Per-system outputs keyed by system string: `packages.x86_64-linux.default`, "`packages.x86_64-linux` must be an attribute set of derivations built for the `x86_64-linux` platform" ([nix flake manual](https://nix.dev/manual/nix/stable/command-ref/new-cli/nix3-flake.html)).
- **Homebrew.** Per-platform components inside one formula: "`on_macos`, `on_linux`, `on_arm` or `on_intel` blocks", plus version blocks such as `on_sequoia` ([Formula Cookbook](https://docs.brew.sh/Formula-Cookbook)). Per-platform bottles not covered on the page read (unverified).
- **Agent Plugins `extensions`** (see section 3): one neutral package, a reverse-domain namespace per client. Unknown namespaces ignored.
- **Claude marketplace entries.** One plugin entry can name one `source`; `engines` gates by Claude Code version only; no per-harness field ([marketplace reference](https://code.claude.com/docs/en/plugins/marketplace-reference.md)). Claude plugins are single-vendor by construction.

How AI-config managers treat single-harness features:
- **rulesync.** One tool-per-target model. Plugin targets such as `claudecode-plugin` are "excluded from `--targets "*"`" so ordinary projects do not get package-level directories. Kiro split into `kiro-cli` and `kiro-ide` because they "use diverging config formats". For Roo and Zoo, "Enable one of the two targets per project". For Tabnine, `opencodev1` rather than `opencode`, "because the latter writes for OpenCode 2.x" ([rulesync README](https://github.com/dyoshikawa/rulesync)). Per-tool frontmatter "barely covered".
- **ruler.** Per-agent sections in `ruler.toml`; MCP servers per agent; skills copied to each agent's native dir; "Agents without native skills support are skipped with a warning"; subagents reach only five targets and "Windsurf, RooCode, Aider, and Gemini CLI are skipped with a warning"; rules are not per-agent: "all agents receive the same concatenated rules" ([ruler README](https://github.com/intellectronica/ruler)).
- **skills.sh / `npx skills`.** Detects installed agents, installs skills to project or global per agent, `-a` targets one agent. The README does not describe agent-specific fields or non-skill types ([vercel-labs/skills](https://github.com/vercel-labs/skills); the linked `docs/agents.md` and `docs/creating-skills.md` were not read).
- **Agent Plugins 1.0** as above, with the 1.1 draft adding portable hooks.
- **OpenClaw** consumes Claude, Codex, Cursor and Agent Plugins layouts and maps them "into its plugin inventory" ([OpenClaw](https://docs.openclaw.ai/plugins)). That is an adapter-reader model, not a per-target payload.

## 5. What goes wrong in practice

Concrete cases with sources. Search-only cases are marked.

1. **Code-extension API breaks between harness versions.**
   - OpenCode v2: "the only intentional breaking changes in V2 are the server API and the plugin API" and "may continue to change during the beta" (search summary of [migrate-v1](https://opencode.ai/v2/docs/migrate-v1/), search-only; the migration page itself was not fetched because of a redirect). A blog reports V1 plugins "do not load on V2" ([byteiota](https://byteiota.com/opencode-v2-your-plugins-are-broken-here-is-what-changed/), search-only, secondary).
   - Claude mods: five changelog entries from 2.1.323 to 2.1.327 alter mod semantics; `engine.create` handling changed so that wildcard hooks "now only observe" (changelog, verified). The docs tell authors to document which version they tested.
   - Kilo: parts of the TUI API "still evolving"; `experimental.` hooks "may change between releases" (verified, [Kilo plugins](https://kilo.ai/docs/automate/extending/plugins)).
   - Copilot CLI extensions: "experimental ... subject to change" (verified).
   - Warp themes: "the format may change" (verified).
2. **A package type or format frozen to one vendor name that later forked or died.**
   - GitHub App-based "Copilot Extensions" sunset: new ones blocked September 2025, existing ones disabled November 10, 2025, replaced by MCP servers, "a replacement, not a migration" ([sunset notice](https://github.blog/changelog/2025-09-23-deprecate-github-copilot-extensions-github-apps), search snippet only; the page was not opened). Client-side VS Code extensions were not affected (same snippet).
   - Gemini CLI replaced by Antigravity CLI for unpaid and Google One users on June 18, 2026 (verified, [Gemini extensions page](https://geminicli.com/docs/extensions/)). Grimoire already lists Antigravity with a different skills root than Gemini (local vendor table). Whether Gemini extensions carry over to Antigravity: unverified.
   - Kiro splits into `kiro-cli` and `kiro-ide` in rulesync because configs diverged (verified, [rulesync](https://github.com/dyoshikawa/rulesync)). Qoder has a separate China variant `qoderclicn` (search-only, [Qoder plugins](https://docs.qoder.com/cli/plugins-reference)).
   - Two files named `plugin.json` with different schemas and locations (Claude `.claude-plugin/plugin.json`, Agent Plugins root `plugin.json`) are reported as unrelated formats (search-only, [thenewstack](https://thenewstack.io/agent-plugins-portability-gaps/)). Cursor documents both side by side (verified, [Cursor](https://cursor.com/docs/plugins)).
3. **A forked harness copying the extension format and renaming the identifiers.** Kilo keeps `engines.opencode` while the package is `@kilocode/plugin`; a third-party installer ports OpenCode plugins by swapping names and paths (see section 2). The Kilo docs page itself notes its engines example range "doesn't match the Kilo version shown elsewhere" (WebFetch summary of [Kilo plugins](https://kilo.ai/docs/automate/extending/plugins), a note by the fetch tool).
4. **Per-target payload type that ended up with one target.** I did not find a concrete case. Closest: VS Code `--target` has a universal fallback by design, and Agent Plugins `extensions` is open to any namespace, and observed adopters are several vendors (Copilot uses its namespace). No evidence of a single-target degenerate use. This question is unanswered, not answered "no".

## Key findings (decision-relevant, with sources)

1. A "mod" is a plugin plus a `modules` key; there is no separate mod package or manifest. Distribution, scope, enabling and trust all reuse the plugin machinery ([overview](https://code.claude.com/docs/en/plugins/mods/overview.md), [reference](https://code.claude.com/docs/en/plugins/mods/reference.md)).
2. Mods are weeks old and explicitly unstable between releases; version introduced 2.1.287, and five of the next releases touch mod semantics ([CHANGELOG](https://raw.githubusercontent.com/anthropics/claude-code/main/CHANGELOG.md), [create](https://code.claude.com/docs/en/plugins/mods/create.md)). The marketplace schema already has a version gate, `engines.claude-code`, that old clients reject outright ([marketplace reference](https://code.claude.com/docs/en/plugins/marketplace-reference.md)).
3. Eight harnesses have an in-process code extension API with different, non-interchangeable APIs (table in section 2); a shared core exists only for skills and MCP (Agent Plugins 1.0) and for hooks in a draft ([spec README](https://github.com/agentplugins/agent-plugins-spec)).
4. Shape B already exists as a published cross-vendor pattern: Agent Plugins `extensions` with a reverse-domain namespace and same-named directory, with "MUST ignore" for unknown namespaces; Copilot is a live user ([spec 1.0.0](https://github.com/agentplugins/agent-plugins-spec/blob/main/spec/1.0.0.md), [GitHub changelog](https://github.blog/changelog/2026-08-12-agent-plugins-1-0-in-vs-code-copilot-cli-and-the-copilot-app)). Claude Code itself does not read that scheme (search-only, [startdebugging](https://startdebugging.net/2026/08/agent-plugins-1-0-vs-vendor-specific-plugin-formats/)).
5. Shape A also has precedent: Claude's marketplace entry and `.claude-plugin` are single-vendor, rulesync keeps plugin targets out of wildcard runs and splits `kiro` into two targets, ruler skips agents that lack a feature with a warning ([marketplace reference](https://code.claude.com/docs/en/plugins/marketplace-reference.md), [rulesync](https://github.com/dyoshikawa/rulesync), [ruler](https://github.com/intellectronica/ruler)).
6. Trust model of mods differs from grim's hook consent: Claude has no per-mod prompt, only folder trust plus an org guard; mods "aren't sandboxed" and can "approve a tool call before you're asked" ([admin](https://code.claude.com/docs/en/plugins/mods/admin.md), [overview](https://code.claude.com/docs/en/plugins/mods/overview.md)). pi gates project-local extensions on project trust; OpenClaw disables workspace plugins by default (section 2).
7. Platform-selection prior art uses closed vocabularies (OCI os/arch, VS Code target list, Terraform os/arch, Nix system string). None of the fetched specs has a field for a runtime that is an application rather than an OS and CPU; OCI `platform.features` is "RESERVED" ([image-index.md](https://raw.githubusercontent.com/opencontainers/image-spec/main/image-index.md)).
