# Research: incremental static-site builds on GitLab/GitHub Pages

## Metadata
- Date: 2026-09-28 (all URLs accessed this date)
- Lane: incremental Pages deploys (neutral; no design recommendation)
- Question: can an Astro package-index site (~400 OCI artifacts, later + per-harness zips/trees) skip unchanged work between runs and deploy partially, and what does the current indexer/grim cost per artifact?
- Sources: URLs inline; code refs are `file:line` in `/home/mherwig/dev/grimoire-indexer` (IDX) and `/home/mherwig/dev/grimoire-duo` (GRIM). Web fetches were summarised by a small model; numbers below are quoted from those summaries.

## 1. Pages platforms: partial deploy and limits
- **GitHub Pages (`actions/deploy-pages`)**: deploys one artifact, "a single gzip archive containing a single tar file", no symlinks/hardlinks; recommended <1 GB, hard ceiling 10 GB; default retention 1 day (https://github.com/actions/upload-pages-artifact). The deploy-pages README documents no partial/incremental mode; `timeout` default 10 min (https://github.com/actions/deploy-pages). Published site <=1 GB, deployment times out after 10 min, soft 100 GB/month bandwidth (https://docs.github.com/en/pages/getting-started-with-github-pages/github-pages-limits). No file-count limit found in these pages.
- **GitLab Pages**: content is whatever `public/` holds in the `pages` job artifact; deploy is triggered by the `pages` job/property (https://docs.gitlab.com/user/project/pages/). No incremental update exists; backlog item gitlab#29265 referenced in search results, not verified (search summary only). GitLab.com: max site size 1 GB, artifact max 1 GB compressed (https://docs.gitlab.com/user/gitlab_com/). Self-managed: default site size 100 MB, "200,000 file entries (including directories and symlinks)" per site (https://docs.gitlab.com/ee/administration/pages/index.html). GitLab.com file-count limit not stated on the GitLab.com page.
- **GitLab parallel deployments** (`pages.path_prefix`): several deployments coexist, "the last one to be completed is deployed" per prefix. This partitions a site by prefix; each prefix is still a full replacement. Premium/Ultimate only for extra deployments (gitlab.com page above).
- negative: neither platform documents a delta upload. Pages platform docs say nothing about diffing against the previous deployment; "full replacement" for GitLab is from doc phrasing + search summary, not an explicit sentence.
- lead: GitHub legacy "publish from branch" pushes a git tree, so upload is git-delta, but the Pages build/deploy behind it still publishes the whole tree; repo guidance <1 GB ideal, <5 GB strongly; files >100 MiB blocked, >50 MiB warned (https://docs.github.com/en/repositories/working-with-files/managing-large-files/about-large-files-on-github).

## 2. Skipping unchanged work
### (a) CI cache keyed on content hashes
- **actions/cache**: 10 GB/repo; entries unused >7 days evicted, oldest first when over quota; entries immutable (new key per change); restore scope = current branch, default branch, and PR base branch; sibling/child branches cannot read each other (https://docs.github.com/en/actions/reference/workflows-and-actions/dependency-caching). Rate limits 200 uploads/min, 1500 downloads/min per repo.
- **GitLab cache**: `cache:key:files` derives key from file content; protected and non-protected branches do not share cache by default (`-protected` / `-non_protected` suffix); "caching is an optimization, but it isn't guaranteed to always work"; eviction depends on runner storage or S3 lifecycle; `fallback_keys` up to five; multi-runner needs distributed (S3) cache (https://docs.gitlab.com/ci/caching/). GitLab.com instance-runner cache size/expiry not found in docs (search returned nothing).
- for: keeps exact prior outputs, no network dependency on the live site. against: best-effort by design; a default-branch `pages` job on a protected branch only sees the protected-scope cache; a cold cache degrades to full work (no correctness impact if keyed on digests). Content-hash-keyed dirs are what Hugo documents as safe to restore (`resources/_gen`, https://gohugo.io/configuration/caches/; third-party summary https://www.glukhov.org/post/2025/11/hugo-caching-strategies/).
- lead: today IDX caches only npm on both forges (see section 4); no enrich/render output is cached.

### (b) Fetch previous deployment from the live site
- Already the IDX pattern for metadata: `enrich --seed` reads `<site>/enrich.json` (IDX `src/enrich/checkpoint.ts:1-30`), read cap `LARGE_RESPONSE_BYTES = 16 MiB` (IDX `src/validate/adapters/http.ts:27`). Writer warns when the file exceeds the cap; a checkpoint that publishes but can never be re-read is possible (checkpoint.ts around the size check). Any unreadable checkpoint = warn + full re-download, never fail (checkpoint.ts header comment).
- for: no cache-scope or eviction problems, works across branches and runners. against: needs the site URL to be reachable and equal to what was last deployed; a deploy that failed halfway, a CDN-stale read, or a first run leaves nothing to seed from; base64 inlining of every file (checkpoint.ts `packCheckpoint`) does not scale to hundreds of zips inside a 16 MiB JSON; would need a per-file hash manifest + per-file GETs instead.
- negative: this makes "what was deployed" the source of truth, so a corrupted/partial deploy is faithfully re-seeded.

### (c) Commit rendered output to a git branch/repo
- GitHub file limits above (100 MiB block, repo <1-5 GB advised). Binary zips that change every version grow history without bound (each new `<base>+<hash>` zip is a new blob). Byte-reproducible zips dedupe identical content in git, changed ones do not delta well.
- for: git is a content-addressed store with diffing; a `pages` job can `git clone` the output branch. against: history growth, push permissions/tokens in CI (IDX templates currently take no write token for enrich: `gitlab-enrich.sh` header "Nothing is committed and no token is involved"), and the repo-wide "never push from CI to default branch" style constraints of the index repo (auto-merge gate templates `github-automerge.yml`, `gitlab-ci.yml` gate).
- lead: Open question whether the index repo's committed sidecar tree pre-dates the checkpoint design (checkpoint.ts header says sidecars were once treated as committed, then found "committed nowhere").

### (d) Rendered output as OCI artifacts in a registry, keyed by digest
- OCI registries are a generic content-addressed store (ORAS: https://oras.land/docs/); Bazel remote cache uses the same input-hash -> output-blob idea (https://nesbitt.io/2026/07/07/content-addressing-in-package-managers.html, summary only). grim is itself an OCI client (`GRIM src/oci/`).
- for: digest-keyed (`<base>+<hash of member digests>` is already an input hash), blobs deduplicated, no 10 GB/7-day cache limits, works from any runner/branch. against: needs a writable registry and credentials in the Pages job (auth surface the current template avoids), retention/GC policies are registry-specific (ghcr.io untagged-version cleanup, not verified here), and an extra network hop per zip on cold runs. No source found describing this exact pattern for a static-site build.
- negative: nothing found shows a comparable index doing (d); it is inference from OCI-as-storage docs.

## 3. Comparable generators / registries
- **Astro**: experimental `incrementalBuild` skips re-rendering `getStaticPaths()` pages whose module graph and user `cacheKey` are unchanged; cache in `cacheDir` (default `node_modules/.astro/`), "Cache and restore this single directory between builds"; introduced 7.2.0 per the docs page; `build.concurrency` > 1 disables the cache; only pages with a `cacheKey`; middleware changes do not invalidate (https://docs.astro.build/en/reference/experimental-flags/incremental-build/). Content-collection `entry.digest` suggested as cacheKey. Prior discussion: https://github.com/withastro/roadmap/issues/1388. negative: experimental flag; skips render only, not the enrich network calls or the full Pages upload.
- **Hugo**: file-level incremental in watch mode; CI persists `resources/_gen` + module cache keyed on inputs (sources above).
- **Docusaurus**: "Faster" with Rspack persistent cache (`rspackPersistentCache`) speeds bundling on repeat builds; not a per-page skip (https://github.com/facebook/docusaurus/pull/10931).
- **Artifact Hub**: tracker runs every 30 min; "if the digest of a version changes, that version is indexed again" (https://artifacthub.io/docs/topics/faq/, https://artifacthub.io/docs/topics/repositories/) - digest-keyed skip on the ingest side, dynamic app not a static site.
- **formulae.brew.sh**: GitHub Action periodically pulls taps, regenerates JSON API via `brew generate-*-api`, Jekyll builds, deploys to GitHub Pages (https://github.com/Homebrew/formulae.brew.sh). Whole-site build each time; no per-package skip found.
- **crates.io/docs.rs**: sparse index is static per-crate files served by CDN (https://rust-lang.github.io/rfcs/2789-sparse-index.html), each publish updates one file; docs.rs builds per release via a queue (https://docs.rs/about/builds). Dynamic services, not Pages.
- **Nix/Hydra**: binary cache addresses narinfo by input-addressed store hash, NARs by content hash; existing path = skip (https://alternativebit.fr/posts/nixos/future-of-nix-substitution/ , https://fzakaria.com/2021/08/12/a-nix-binary-cache-specification). Closest analogue to a `<base>+<hash>` key.
- **Open VSX**: extension files in object storage; no incremental static-build info found (sitemap lastmod issue https://github.com/eclipse-openvsx/openvsx/issues/2229). npm-style static mirrors: nothing specific retrieved.
- Summary: content-hash skip is common at the ingest/store layer; none of the static-hosted examples found do partial *deploy*, all redeploy the full tree.

## 4. Indexer state (code facts)
- GitHub and GitLab enrich identically: `npm run enrich -- --seed` (IDX `templates/ci/github-enrich.yml`, `templates/ci/gitlab-enrich.sh`). GitLab installs grim by tarball inside the job (`gitlab-enrich.sh`), GitHub likewise in a step.
- Caching differs only in what is cached: GitLab `default.cache` = key `package-lock.json`, paths `.npm/`, `.npm-gate/` (IDX `templates/ci/gitlab-ci.yml:10-16`); GitHub `actions/setup-node` `cache: npm` (`github-pages.yml`). Neither caches `enrich/`, `dist/`, or `GRIM_HOME`. GitLab `pages` job runs only on `$CI_COMMIT_BRANCH == $CI_DEFAULT_BRANCH`.
- Deploy: GitHub `upload-pages-artifact path: dist` then `deploy-pages` (2 jobs); GitLab `rm -rf public && mv dist public`, `artifacts: paths: public`. Both full.
- Concurrency: none. `enrichIndex` loops files sequentially, awaiting each `enrichOne` (IDX `src/enrich/index.ts:337-350`); comment says "batch with a worker pool if an index ever grows into the hundreds". No flag/option. Per-call timeout 60 s, `execFile` per invocation (`index.ts:spawnGrim`).
- Skips already in place: `describe` never skipped ("cheap and runs every time", index.ts header); description companion download skipped when `fetch --description --digest-only` digest equals stored `descDigest`; contents `fetch` skipped when `describe.digest` equals stored `contentDigest`.
- negative: `describe` is also what refreshes tags, support links and deprecation; a probe on the artifact digest alone would not see a new tag or an edited companion (companion has its own digest).

## 5. grim cost and probe
- **Batching**: none. `DescribeArgs.reference: String` (GRIM `src/command/describe.rs:22-30`); `FetchArgs.reference: String` (`src/command/fetch.rs:35-40`). One ref per process. lead: `grim mcp` (long-lived server) exposes `grim_describe`/`grim_fetch` (`src/command/fetch.rs` header), not tested here for per-call overhead.
- **`describe` round trips** (`GRIM src/fetch.rs:886-960`): `list_tags` (GET tags/list), `resolve_digest` (HEAD manifest), `fetch_manifest` (GET manifest), plus, only when a `__grimoire` tag exists, `companion_support` = another resolve + manifest GET (`fetch.rs:614-633`). About 3 requests, about 5 with a companion, plus any bearer-token exchange (not measured). No blob pulled.
- **Per artifact per run** today: 2 process spawns (`describe`, `fetch --description --digest-only`) + 1 HEAD; extra spawn(s) only when a digest moved. ~400 artifacts = ~800 spawns sequential. Wall time not measured.
- **HEAD probe**: yes. `grim fetch <ref> --digest-only` (and `--description --digest-only` for the companion tag) calls `resolve_digest_only` (`GRIM src/fetch.rs:716-745`) -> `access.resolve_digest` -> `oci-client fetch_manifest_digest`, which does `HEAD /v2/<name>/manifests/<ref>`, reads `Docker-Content-Digest`, and falls back to GET only if the header is absent (`GRIM external/rust-oci-client/src/client.rs:987-1030`; header const `digest.rs:9`). Report is `{ref, digest}`, no manifest/blob download.
- Caveats: OCI spec says the header SHOULD be returned (https://github.com/opencontainers/distribution-spec/blob/main/spec.md), so GET fallback exists for non-compliant registries. In online mode `CachedAccess` never reads the cached pin (`GRIM src/oci/access/cached_access.rs:75-84`), so every probe hits the registry. Docker Hub does not count HEAD toward pull limits; a GET does (https://www.augmentedmind.de/2024/12/15/docker-hub-rate-limit-head-request/); ghcr.io public: no documented limit found (community thread only).
- Digest-pinned refs resolve to themselves with no I/O (`registry_client.rs:343-347`); irrelevant unless the index stores digests.
