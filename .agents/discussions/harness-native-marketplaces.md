# Discussion: Harness-native marketplaces rendered from the catalog

State: handed-off → loop · Updated: 2026-09-27
Ratified: 2026-09-27 → loop
Confidence: ratified by the owner (explicit /hex-loop invocation on this artifact after the six-part restate); research vintages 2026-09-15 (recon, prior art, adjacent) and 2026-09-27 (plugin format lanes a–c, support matrix, Agent Plugins 1.0 verification, Claude app install surfaces)

## Intent

Adopting grim today means every consumer installs the `grim` binary. In
some environments that is hard (locked-down corporate machines; users who
live only inside their harness and will not learn a second CLI). Several
top-tier harnesses ship their own plugin marketplace surface (git repo or
zip based). Question: should the catalog/index be projected into
pre-defined, generated, harness-native marketplaces so those users can
consume grim-published artifacts with zero grim install.

Out of scope: grim-owned plugin containers installed on the user's
machine and any plugin artifact type (`research_plugin_schemes.md`;
Decisions › No plugin type); replacing OCI as the canonical channel; tar
archives; index-of-indexes; `grimoire.toml` as a plugin or marketplace;
reference rewriting on rename.

Outcome shape (revised 2026-09-27): a two-phase build. **Phase 1** —
`grim export plugin`, `grim update --marketplace`, `marketplace.toml` +
`marketplace.lock`, `[plugins.x.rename] strip_prefix`, clients mapped to
the Claude and Agent Plugins 1.0 manifest shapes, folder or `--zip`
output. **Phase 2** — `grim export marketplace`, marketplace-level
metadata, auto-maintenance CI component, opt-in annotation + candidates,
curated public marketplace. The frozen-contract details (schemas, JSON
output, exit codes) are settled in an ADR before code.

## Requirements

Phase 1 only. Phase 2 decisions below are recorded, not built in this run.

- An ADR fixes the `marketplace.toml`/`marketplace.lock` schema, export JSON output and exit codes before any code.
- `grim export plugin` exports ad-hoc refs and declared plugins per `--client`, as a folder or `--zip`.
- Export output is rendered exactly like `grim install` and is byte-reproducible across runs.
- Claude and Agent Plugins 1.0 manifests carry the plugin name, derived version and named omissions.
- `grim update --marketplace` rolls selected plugin pins forward without installing anything.
- `[plugins.x.rename] strip_prefix` renames members and fails closed on empty names, collisions and stale references.
- No duplicate lock, update or render path: every new behaviour reuses the seams in Decisions › Reuse mandate.
- Acceptance tests, docs pages and the `grim-usage` catalog drift review land with the feature.

## Decisions

- Trigger population: harness-only users + locked-down corp machines. Not
  CI/ephemeral sessions (owner, 2026-09-15). The internal admin-rollout case,
  excluded on 2026-09-15, is back in scope via declared team plugins (below).
- Purpose: **on-ramp**, not a first-class channel. The projection is lossy
  by design (no digest pinning, lockfile, drift, ratings) and says so —
  "powered by grim; install grim for the rest". No parity contract is
  frozen under Principle 9 for the mirror.
- Scope (owner, 2026-09-27; supersedes "whole public index, index
  inclusion is the curation gate"): a marketplace is a **curated view**, not
  a mirror — the index is already criticized as too full, and the
  marketplace must not repeat that. The public grimoire marketplace starts
  from a **curated seed** (first-party bundles: `grim-essentials`, arcana
  `hex`) and grows by hand-picked additions, regenerated by index CI.
- *Superseded by Plugin declarations (below) for membership; kept as the
  discovery aid.* Membership (owner, 2026-09-27): defined by a **filter view** — ordinary
  `[[registries]]` entries (index locator + `include`/`exclude`) in a config
  the curator owns, fed to `grim export marketplace`. No new schema; growth
  = add a pattern, regenerate. Export takes bundles only. Unlike browse
  (fail-open: an uncompilable filter is dropped and the source browsed
  unfiltered, `docs/src/content/docs/configuration.md#browse-filters`),
  **export fails closed**: an invalid filter or one admitting zero bundles
  aborts non-zero — fail-open here would publish the whole index. The docs
  sentence "the filter applies to search, TUI, MCP and nothing else" needs
  an additive update. Rejected: publisher annotations as the gate
  (publisher-controlled, floods like the index); a bespoke bundle-list TOML
  (new frozen schema, manual per entry).
- Opt-in (owner, 2026-09-27): **publisher annotation as a request, curator
  review as the gate.** A publisher marks a bundle with a new annotation
  (working name `com.grimoire.marketplace`, additive under Principle 9); the
  curator sees annotated bundles not yet admitted by the view as a
  candidate list and adopts them by adding a pattern. The annotation never
  admits anything on its own. Self-serve remains: anyone can run their own
  marketplace over their own view and users add it by URL. Rejected: an
  announce-PR against the view config (owner preferred the annotation
  signal).
- Two marketplace kinds (owner, 2026-09-27): the grim index is a **goods**
  marketplace (one entry per skill/agent/mcp, by reference); a harness
  marketplace's unit is always a **plugin** (a collection). They are not the
  same thing and the projection should not pretend otherwise.
- *Superseded by Plugin declarations (below).* Granularity: **bundles only** (owner, 2026-09-27; supersedes "one plugin
  per index artifact" of 2026-09-15). One plugin per bundle; loose goods are
  not wrapped. Bundle name = plugin name = namespace (`<bundle>:<skill>`),
  which removes the doubled-name problem. Accepted cost: a publisher with a
  single skill gets no harness-marketplace reach until they publish a bundle.
- *Superseded by Plugin declarations refined (below): team setup is a
  declared plugin, not a raw lock export.* Scope widened (owner, 2026-09-27): **a project's resolved set
  (`grimoire.lock`) exports as a plugin too**, bringing the internal
  admin-rollout case back into scope. The lock is the source (exact digests,
  reproducible); `grimoire.toml` only via `grim lock` first. One export
  pipeline, two inputs: a bundle ref (resolve → lock-shaped set → render) or
  the project lock (render only). This makes export a local operation, which
  pulls it into grim (see Export, below).
- Freezing: bundle members are references (often floating, e.g. `:0`); a
  plugin is a by-value snapshot. Export **re-resolves members on every run**
  (for the public marketplace: every index rebuild); plugin `version` = bundle version plus a short hash over
  the resolved member digests, so a member patch release reaches plugin users
  as a new plugin version (owner, 2026-09-27).
- On-ramp seam: plugin metadata (description, homepage → index entry) plus
  the marketplace README. *Content rule superseded by Phase-1
  settlements: rendered like install, not byte-identical.*
- Targets (owner, 2026-09-27; supersedes "Claude-shape only"): **two
  manifest families first** — Claude shape (`.claude-plugin/plugin.json` +
  `marketplace.json`; reaches Claude Code, Droid, Junie, OpenClaw) and
  **Agent Plugins 1.0** (root `plugin.json`, `skills/` + `mcp.json`; reaches
  Copilot, Codex, Cursor). Agent Plugins carries no agents or rules, so
  those members are omitted there and named in the description. Gemini
  (`gemini-extension.json`), `.cursor-plugin/`, Kilo, Qoder deferred until
  pull appears. Amp, Goose, Cline, Warp, Zed have no plugin mechanism.
  Whether one folder can carry both manifests over a shared `skills/` is
  untested — first spike of the plan.
- Export lives in grim (owner, 2026-09-27; supersedes the 2026-09-15
  "`fetch --unpack` + indexer assembles" split): **`grim export plugin`**,
  additive subcommand. Input: a bundle ref, or the project lock when run in
  a project. Output: one plugin tree per manifest family, rendered by the
  existing vendor renderers; `--zip` for upload surfaces (Anthropic only
  today: claude.ai skill upload, Claude Code `archive` source). The indexer
  CI calls the same command to fill the public marketplace repo — no
  rendering logic outside Rust. Accepted cost: a new frozen CLI contract
  under Principle 9. Why it changed: per-family rendering, lock input and
  zip output all need local export; the indexer would otherwise re-implement
  the renderers.
- Marketplace generation lives in grim too (owner, 2026-09-27): grim
  writes the whole marketplace (plugin trees plus `marketplace.json` per
  family) from a set of bundle refs or index entries; the indexer only runs
  it and hosts the output (git push / Pages). An admin can build a private
  marketplace with grim alone. Strongest counter-argument, noted once: this
  freezes a second CLI surface, and grim must accept a list of bundles as
  input (explicit refs or an index), which the ADR has to shape.
- Majors: **latest major only** (owner, 2026-09-27). A bundle with live
  `:0` and `:1` exports `:1`; one version per plugin matches every
  marketplace, and the namespace users type stays stable.
- Rules: **per family** (owner, 2026-09-27; supersedes "excluded
  everywhere"). Shipped where the family has a rules surface (Cursor
  `rules/*.mdc`, Gemini `contextFileName`, Kiro steering, Antigravity
  `rules/`); omitted where it has none (Claude Code, Codex, Droid, Agent
  Plugins 1.0), with the gap named in the plugin description. Still no
  rule-as-skill wrapping.
- Phasing (owner, 2026-09-27): **phase 1 = `grim export plugin`** — input
  a bundle ref or the project lock; output one tree per targeted family
  (Claude shape, Agent Plugins 1.0), as a folder or `--zip`. Primary user:
  an admin/manager onboarding a team without git, into the **Claude app**
  (Desktop, claude.ai, Cowork) — not only Claude Code (owner, 2026-09-27).
  Resolved (`research_claude_app_install_surfaces.md`): the Claude app
  **accepts a whole Claude-shape plugin zip** — `Customize > Plugins > Add >
  Upload plugin` (per user) and `Organization settings > Plugins & skills >
  Upload a plugin` (admin; Default access Available / Installed by default /
  Required, per group on Enterprise); `.claude-plugin/plugin.json` at the
  archive root, 200 MB / 5,000 files. So the Claude family's `--zip` output
  serves Claude Code and the Claude app alike — no third family. In chat:
  skills and commands load, remote MCP works; agents, hooks and local MCP
  (incl. `.mcpb`) are ignored in chat but work in Cowork and Code. Export
  never emits `bin/` (blocks install outside Claude Code).
  **Phase 2 = marketplace**: `grim export marketplace`, filter view,
  opt-in annotation + candidate list, curated public marketplace. Phase 2
  builds on phase 1's rendering; its decisions above stay recorded but are
  not phase-1 scope. Why: a marketplace always needs a hosted repo (git is
  the only route outside Claude Code), an export needs nothing.
- CLI vocabulary (owner, 2026-09-27): **no new word — `--client`**, same
  comma list and same default (`[options].clients`) as `install`/`update`.
  "Manifest family" (Claude shape / Agent Plugins 1.0) stays internal and in
  the docs table: claude, droid, junie, openclaw → Claude shape; copilot,
  codex, cursor, **agents** → Agent Plugins (`agents`, the vendor-neutral
  client in `src/install/vendor_agents.rs`, is the natural name for the
  vendor-neutral spec). Repeatable and comma-separated, as on `install`
  (`src/command/install.rs:48`). **Default: config `[options].clients`,
  else `agents`** (owner, 2026-09-27) — install's chain minus machine
  detection, which is meaningless when exporting for someone else; the
  Claude-app upload case therefore passes `--client claude`. A client with
  no plugin surface is an error when named explicitly, skipped with a note
  when it comes from the config default.
- Output naming (owner, 2026-09-27): **one output per requested client,
  always `<name>.<client>` (`.zip` with `--zip`)** under `-o <dir>` —
  predictable regardless of client count; two clients sharing a format get
  byte-identical files. Version lives in the manifest, not the filename. Without
  `--zip`: directory `<dir>/<name>.<client>/` whose top level is the plugin
  root. With `--zip`: the same contents with no wrapping folder — the Claude
  app requires `.claude-plugin/plugin.json` at the archive root. **Zip is
  the only archive format** (no researched target accepts tar.gz);
  `--zip` stays a boolean, a later `--tar` would be additive.
- *Partly superseded by Plugin declarations refined (below): the 0-ref
  lock input is dropped.* Inputs (owner, 2026-09-27): positional **`<ref>…`, zero or more**, same
  reference forms `grim add` accepts (fully qualified, short id,
  alias-qualified), **any artifact kind**. 0 refs = the project
  `grimoire.lock` (found by normal discovery; another project via the
  global `--config`, no new flag). 1 ref = plugin name derived from it
  (bundle or artifact name; a single skill yields `foo:foo`, accepted when
  exported deliberately). **Anything other than exactly one ref (lock, or
  2+ refs merged into one plugin) requires `--name`** — usage error
  without it; no project-dir default (accidental namespace). Member
  collisions across inputs: same name + same digest → deduplicated;
  same name + different digest → error naming both sources. Phase 2
  marketplace stays bundles only. Strongest counter, noted once: multi-ref
  duplicates what a lock or local bundle already expresses; kept because it
  is the same merge the lock export needs.
- Upgrade path (2026-09-27): phase 2 `grim export marketplace` loops the
  phase-1 plugin rendering over the view's bundles into `<name>.<client>/`
  dirs plus a `marketplace.json`; a CI job (indexer or the owner's own)
  commits the output to a git branch or dedicated repo and pushes; users
  add that URL in Claude Code or Desktop's "Add marketplace". **Phase-1
  constraint: reproducible output** — same input → byte-identical trees
  and zips (fixed zip timestamps and entry order, stable JSON key order),
  else every regeneration is a git diff and a phantom plugin update. Open
  for phase 2: whether Desktop's "Add marketplace" accepts a branch/ref or
  only a repo default branch (Claude Code sources accept a ref).
- *Placement superseded by Config file (below).* Plugin declarations (owner, 2026-09-27; supersedes "Membership = filter
  view" and "Granularity: bundles only" for marketplace membership): a
  harness marketplace lists only plugins, and a plugin is **any set of
  refs**. Declared in `grimoire.toml` as `[marketplace.plugins.<name>]` with
  `include = [<ref>…]` (any kind) and optional `description`; plus an
  optional `[marketplace]` table (`name`, `owner`, `description`).
  `[marketplace.plugins.x]` is the stored form of `grim export plugin <refs…> --name x`
  — the table key is the name. **Export-only**: `grim install` ignores
  `[plugins]` (`[bundles]`/`[skills]` = "I use", `[plugins]` = "I publish
  as a plugin"). The lock scopes entries per plugin (additive `plugin =
  "<name>"` field), so members need to agree only within a plugin, and
  `grim update <plugin>` rolls one plugin without materializing anything.
  A normal project can declare `[marketplace.plugins.team]` to export its own setup.
  Filter view + opt-in annotation remain the curator's discovery aid
  (`--candidates`), not membership. Additive schema under Principle 9.
- *Placement superseded by Config file (below): `marketplace.toml`, not
  `grimoire.toml`; `[marketplace.plugins.x]` becomes `[plugins.x]` there.*
  Plugin declarations refined (owner, 2026-09-27): nested under the
  marketplace — `[marketplace]` (optional `name`, `owner`, `description`)
  and `[marketplace.plugins.<name>]` (`include`, `description`). Plugins
  are **export/marketplace output only**: never installed locally (members
  already install natively; a local plugin would duplicate every skill
  under a `plugin:` namespace — grim-owned local containers stay deferred
  per `research_plugin_schemes.md`) and never a published OCI kind (the
  bundle is the publishable collection; plugin = harness-side by-value
  render of it). CLI: `grim export plugin --plugin <name>` (repeatable)
  selects declared plugins — a flag, not a positional, because a name
  would be ambiguous with a short-id ref; the table key is the name, no
  `--name`. No refs and no `--plugin` = every declared plugin (none
  declared → error with hint). `grim export plugin <ref>… --name x` stays
  the ad-hoc path. **Team setup = declaration only** (owner): the "no ref
  = export the project lock" input is dropped; a team declares
  `[marketplace.plugins.team]`. Accepted cost: refs appear in both
  `[bundles]`/`[skills]` (use) and `include` (export) and can drift.
- No plugin type (owner, 2026-09-27): plugins are **not** a first-class
  grim type — no OCI kind, no install, no TUI/search rows. They are export
  output only. The "prefix/namespace" request is real but out of this
  work; its route is an optional bundle install mode as a local plugin
  container (reserved slot, `adr_render_layout_stability.md`;
  `research_plugin_schemes.md`) — separate thread.
- Config file (owner, 2026-09-27; supersedes the `grimoire.toml`
  placement): **dedicated `marketplace.toml` + `marketplace.lock`**,
  following the `publish.toml` precedent ("NOT a grim bundle — this file
  drives `grim publish`", `catalog/publish.toml`): `grimoire.toml` = what I
  use, `publish.toml` = what I publish, `marketplace.toml` = what I
  distribute as plugins. Top-level `name`, `owner`, `description`;
  `[plugins.<name>]` with `include`, `description`. The lock reuses the
  grimoire lock format plus a plugin scope; no clash with `grim update`
  binding names. Read by `grim export plugin --plugin` and `grim export
  marketplace` (default `./marketplace.toml`, else `--marketplace
  <path>`); the update entry point is `grim update --marketplace` (Decisions ›
  Update entry point). Phase 1 ships the file with
  `[plugins]` (team case); marketplace-level fields matter from phase 2.
- Phase-1 settlements (owner, 2026-09-27):
  - **`marketplace.lock` ships in phase 1.** `grim export plugin --plugin`
    reads it, and writes it when absent or stale versus
    `marketplace.toml`: reproducible and pinnable, so a team zip changes
    only on purpose. `grim update --marketplace` (phase 1) rolls it forward.
  - **Rendered like install** (supersedes "SKILL.md bytes stay identical to
    the OCI artifact" under On-ramp seam): export writes exactly what `grim
    install` would write for that client via the vendor renderers
    (e.g. `render_universal_skill_doc` for `agents`). One behaviour,
    per-client correct; digest identity with the OCI layer is not claimed.
  - **Declared plugin version: optional `version` field** in
    `[plugins.x]`; export appends `+<member-digest-hash>`
    (`1.2.0+a1b2c3d`). Absent → `0.0.0+<hash>`. Meant to be pipeline-
    maintained as code (owner): `--version <v>` overrides it (leading `v`
    stripped), exactly the `publish.toml` / `grim publish --version <git
    tag>` precedent (`catalog/publish.toml`). Precedence: `--version` →
    `version` field (local fallback) → `0.0.0`; the hash suffix is always
    appended. Typical flow: git tag → CI `grim export plugin --plugin <p>
    --version "$TAG" --zip` → release asset / admin upload.
  - Dual-manifest spike **dropped** — one output per client makes a shared
    folder unnecessary.
- Plugin sources (owner, 2026-09-27): **`include` refs only.** Weighed
  and rejected: `from = "<grimoire.toml>"` (plugin sourced from a
  project's locked set) and "grimoire.toml is itself a plugin". Reason:
  maintainability — one source kind means one editing path, and plugin
  entries use the same ref strings as `grimoire.toml` declarations, so a
  later TUI/CLI management flow ("add ref X to plugin P") reuses the
  existing add-a-ref flow. **Design constraint:** `marketplace.toml` stays
  machine-editable by grim (no free-form, includes or inheritance);
  management commands / TUI support are a later thread. Accepted cost
  stands: team refs duplicated between `grimoire.toml` and `include`.
- Prefix stripping (owner, 2026-09-27; phase 1): opt-in per plugin, as a
  **`[plugins.x.rename]` table** with `strip_prefix = "<p>"` as its only
  phase-1 key — a table so later rules are additive keys (e.g. an explicit
  `map = { old = new }`, or `pattern`/`replacement` regex) without a
  competing top-level field (Principle 9). Regex not built now (no case
  yet); the fail-closed checks below apply to every future rename rule. Motivation: skills published
  loose carry a manual prefix (`hex-plan`) that becomes redundant inside a
  plugin namespace (`hex:hex-plan` → `hex:plan`). Export renames every
  matching member — directory and frontmatter `name` together (Agent
  Skills / Claude app require folder = name) — as one more render step.
  **Fails closed** (non-zero, nothing written) when a stripped name is
  empty, two members collide after stripping, or any member file still
  references an old name or relative path (reported as file:line; hex
  today links `../hex-core/references/…` and names `/hex-plan` in prose, so
  it would stop — intended). **No reference rewriting**; whether grim ever
  rewrites paths is a separate later question.
- `marketplace.lock` content (2026-09-27): **inputs only** — the grimoire
  lock format (`[metadata]` with `declaration_hash` over
  `marketplace.toml`; `[[skill]]`/`[[agent]]`/… entries with `pinned`
  digest and bundle provenance) plus an additive `plugin = "<name>"`
  scope on every entry. The same artifact in two plugins gets one entry
  per plugin and may pin different digests. **No versions stored**: each
  plugin's visible version is derived at export (`--version` → field →
  `0.0.0`, + hash over that plugin's pins), so the CI tag stays the single
  source and an update scoped to one plugin changes only that plugin's
  version and bytes. The marketplace itself carries no harness-visible
  version — harnesses track updates per plugin. The lock is rewritten only
  when a pin changes (no timestamp churn).
- Update entry point (owner, 2026-09-27; **phase 1**, supersedes the
  `grim export marketplace --update` sketch): **`grim update --marketplace
  <path> [<selector>…]`** — the existing verb, same semantics (re-resolve
  floating tags, roll only the selected lock entries forward), never
  materializes anything. Selectors: `<plugin>` (all its members) or
  `<plugin>:<member>` (one artifact; colon mirrors the harness namespace);
  member = original artifact name as keyed in the lock, pre-`rename`;
  unknown selector → error. Update changes pins, export renders — the
  same split as `grim update` / install today. Moved into phase 1 because
  `marketplace.lock` ships there; without it a floating tag would freeze
  until the lock is deleted.
- Automatic maintenance (2026-09-27): the marketplace repo runs a
  scheduled CI job — `grim update --marketplace marketplace.toml`
  (floating tags in `include` roll
  forward; fixed tags hold) → `grim export marketplace -o .` → if the
  tree changed, open a PR (review gate, default) or push directly (curator
  opt-in). Shipped as a reusable component in `grimoire-components`.
  Reproducible output makes "no diff" the no-op signal. Consumer side is
  the harness's: a changed plugin `version` is what triggers its update
  (Claude Code: `/plugin marketplace update`, background auto-update off
  by default for private repos). A zip uploaded to the Claude app does
  **not** auto-update — re-upload by hand; the marketplace path is the
  auto-updating one.
- Phasing reconsidered (owner, 2026-09-27): merging the marketplace core
  into phase 1 was weighed once `marketplace.toml` shipped in phase 1 —
  **kept two phases**. Phase 1 stays the zip/folder export incl.
  `marketplace.toml` `[plugins]`; phase 2 adds `grim export marketplace`,
  marketplace-level fields, then discovery aids (the update entry point
  moved to phase 1, see Decisions › Update entry point),
  CI component and the public marketplace.
- Plugin name (owner, 2026-09-27): **bundle name, no override.** An
  override, if a real case appears, is an optional bundle-TOML metadata
  field — never an OCI annotation.
- **Reuse mandate (owner, 2026-09-27; binding for plan and review):** a
  lean Rust structure with no duplicate code paths — a second lock, update
  or render path is maintenance hell. Seams to reuse, not mirror:
  - lock: `src/lock/` (`grimoire_lock.rs`, `lock_io.rs`,
    `locked_artifact.rs`, `locked_bundle.rs`, `effective_set.rs`,
    `advisory_lock.rs`) — `marketplace.lock` is the same type and IO with
    an optional `plugin` scope, not a parallel struct;
  - update: `src/command/update.rs` roll-forward, parameterized by
    manifest/lock pair and "materialize: no" — `grim update --marketplace`
    is a mode of it, not a copy;
  - resolve: `src/resolve/` for every ref form;
  - render: `src/install/render.rs`, `materializer.rs`, `vendor_*.rs`,
    `target.rs` / `path_anchor.rs` — export = materialize into a staging
    root instead of client roots, so "rendered like install" holds by
    construction;
  - config discovery / `--config`: `src/store/paths.rs`.
  Genuinely new code is expected only for: the plugin manifests
  (`plugin.json` × 2 shapes), zip writing, `marketplace.toml` parsing, the
  `rename` step, and phase-2 `marketplace.json`. The plan must map every
  new behaviour to one of these seams or justify new code, and review
  gates on duplicate paths (a `code-check` / over-engineering perspective).
- Framing accepted with eyes open: a reach play. No adjacent ecosystem shows
  a projection measurably converting users to the canonical channel;
  conversion here is a README and metadata, not a mechanism.

## Verification

- `grim export plugin`: acceptance tests under `test/` — bundle ref and
  declared-plugin (`marketplace.toml` + `marketplace.lock`) inputs;
  per-client trees; each tree byte-equal to what `grim install --client
  <c>` materializes for the same members; `--zip` round-trips; additive subcommand only (Principle 9);
  JSON output + exit codes per `subsystem-cli-api.md`; catalog drift review
  of `grim-usage` per `catalog/README.md`; docs page.
- Reproducible: exporting the same input twice yields byte-identical
  directories and zips (compare hashes), across machines and timezones.
- Version: a member patch release under a floating bundle yields a changed
  plugin `version` (build-metadata suffix) and Claude Code offers the update.
- Omissions visible: a bundle fixture with a rule and an agent member yields
  an Agent Plugins tree whose description names both omissions, and a
  Claude tree that names the rule.
- Prefix stripping: fixture plugin with `[rename] strip_prefix` renames dirs and
  frontmatter names; fixtures for an empty result, a post-strip collision,
  and a leftover `../<old>/` path each exit non-zero, write nothing, and
  name the offending file:line.
- (phase 2) Fail-closed filter: `grim export marketplace` against a view with an
  uncompilable pattern, and against one admitting zero bundles, exits
  non-zero and writes nothing; a valid view exports exactly the admitted
  bundles and no loose goods.
- (phase 2) Indexer job: runs `grim export marketplace` against a fixture index and
  pushes the output; `claude plugin marketplace add` + `install` smoke on real Claude
  Code, and once on Copilot CLI. Regeneration against an unchanged index
  produces no diff.
