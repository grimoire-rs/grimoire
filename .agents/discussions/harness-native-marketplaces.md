# Discussion: Harness-native marketplaces rendered from the catalog

State: active · Updated: 2026-09-15

## Intent

Adopting grim today means every consumer installs the `grim` binary. In
some environments that is hard (locked-down corporate machines; users who
live only inside their harness and will not learn a second CLI). Several
top-tier harnesses ship their own plugin marketplace surface (git repo or
zip based). Question: should the catalog/index be projected into
pre-defined, generated, harness-native marketplaces so those users can
consume grim-published artifacts with zero grim install.

Out of scope: rendering plugin containers on the user's machine (already
researched, `.agents/research/research_plugin_schemes.md`); replacing OCI as
the canonical channel.

Outcome shape: clarity (build / don't build + rough shape). No plan or ADR
from this discussion.

## Decisions

- Trigger population: harness-only users + locked-down corp machines. Not
  CI/ephemeral sessions, not the internal admin-rollout case (owner,
  2026-09-15).
- Purpose: **on-ramp**, not a first-class channel. The projection is lossy
  by design (no digest pinning, lockfile, drift, ratings) and says so —
  "powered by grim; install grim for the rest". No parity contract is
  frozen under Principle 9 for the mirror.
- Scope: **whole public index**, one marketplace per supported harness,
  regenerated by index CI. Index inclusion is the curation gate; no second
  curation surface.
- Granularity: **one plugin per index artifact** — skill, agent, rule,
  bundle (bundle plugin carries its members). Names and versions round-trip
  1:1 with index rows.
- On-ramp seam: plugin metadata (description, homepage → index entry) plus
  the marketplace README. Published content is never mutated — SKILL.md
  bytes stay identical to the OCI artifact, so digest identity holds.
- Targets: **Claude-shape only** — one generated repo carrying
  `.claude-plugin/marketplace.json` + one directory per plugin. Reaches
  Claude Code, Copilot CLI / VS Code (documented fallback), Cursor, Droid,
  Kilo. Gemini (`gemini-extension.json`) and Codex (schema unpublished)
  deferred until pull appears.
- Generator split: **grim gains `fetch --unpack <dir>`** (additive flag;
  writes the artifact's file tree, bytes identical to the OCI layer);
  **grimoire-indexer CI** assembles the marketplace repo from `all.json`
  plus the unpacked trees and pushes it. No new grim subcommand; no
  marketplace logic in Rust. Rejected: `oras pull` in the indexer (second
  OCI client to keep in step), `grim marketplace render` (largest surface).
- Rules: **excluded, stated**. Rule artifacts are skipped; a bundle with
  rule members projects its other members and names the gap in its plugin
  description. No rule-as-skill wrapping (would misrepresent always-on as
  on-demand).
- Framing accepted with eyes open: a reach play. No adjacent ecosystem shows
  a projection measurably converting users to the canonical channel;
  conversion here is a README and metadata, not a mechanism.

## Threads

- Closed — "per-harness marketplaces": collapsed to one Claude-shape repo
  once prior art showed Copilot/Cursor/Droid/Kilo read that schema.
- Closed — "does grim need to be in the generator at all": layer is plain
  tar (`src/oci/description.rs:184`); chose the grim flag over oras for
  single-client consistency, not necessity.
- Closed — inverse question (grim-owned plugin containers on the user's
  machine) stays deferred per `research_plugin_schemes.md`; not this work.

## Open questions

- [NEEDS CLARIFICATION: hosting — repo name and org for the generated
  marketplace, and whether a self-hosted index (corp case) reuses the same
  indexer job against its own repo] Recommended: `grimoire-rs/marketplace`,
  generated by the same indexer CI a self-hosted index already runs — one
  code path, config-driven target repo.
- [NEEDS CLARIFICATION: plugin naming — Claude Code invokes skills as
  `<plugin>:<skill>`; one-plugin-per-artifact yields `foo:foo` for
  single-skill plugins] Recommended: plugin name = index short id, accept
  the doubled name; do not invent a namespace scheme the index lacks.
- [NEEDS CLARIFICATION: versioning + pinning — plugin `version` from the
  index row; marketplace entries pinned by git SHA or floating?]
  Recommended: version = index version, marketplace regenerated on every
  index rebuild, consumers pin by SHA if they care (Claude Code documents
  it); no lockfile emulation.
- [NEEDS CLARIFICATION: deprecation / removal — an artifact yanked from the
  index: remove the plugin dir, or keep with a deprecated marker?]
  Recommended: remove; the harness keeps the installed copy anyway, and a
  stale entry is worse than a missing one.
- Bundles: members become the plugin's `skills/`, `agents/`, MCP entries;
  `mcp` artifacts map to plugin MCP declarations — confirm the Claude
  plugin manifest accepts every field grim's mcp descriptor carries.
- Ratings and provenance annotations are not carried; state it in the
  marketplace README.

## Verification

- `grim fetch --unpack <dir>`: acceptance test under `test/` proving the
  unpacked tree is byte-identical to the OCI layer contents for a skill, an
  agent, and a bundle; additive flag only (Principle 9); catalog drift
  review of `grim-usage` per `catalog/README.md`; docs page update.
- Indexer job: generates the marketplace repo from a fixture index;
  `claude plugin marketplace add <repo>` + `claude plugin install` smoke on a
  real Claude Code, and the Copilot CLI fallback path once.
- Regeneration is idempotent — a second run against an unchanged index
  produces no diff.
- Rule exclusion visible: a bundle fixture with a rule member yields a
  plugin whose description names the omitted rule.
