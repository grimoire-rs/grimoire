## Context

The owner's intent: "`grim lock` was never meant to update." Only `grim update` may move an existing pin. Three defects on `main` break that. **Re-pin:** `grim lock`, `grim add` and every "run `grim lock`" recovery move existing entries to the tag's current digest. **Issue #269:** `grim update <names>` resolves the names, then installs, gates, prunes and reaps the whole lock. **Shared-reference carry:** `Carry.digests` is keyed by requested reference, so `grim update a` can keep an old digest with zero registry calls.

The root cause is structural. The lock cannot say which reference resolved an entry, so a re-lock has nothing to compare a request against. No record decided this: full re-resolve is the OCX-port default (archaeology, finding 7). The plan needs an accepted record because it carries a one-way door no accepted ADR covers: every lock's `pinned` value changes content.

## Decision Drivers

- Only `grim update` moves a pin; a moved tag stays put everywhere else.
- Principle 9 is the hard limit: no new lock field, `lock_version` stays 1, report actions only gain values, older grim still reads the lock.
- Change detection works per node, transitive nodes included, and offline.
- The owner's model: current state, target state, mutations derived from the difference.
- The destructive guards stay. No up-front install planner.

## Industry Context & Research

**Research artifacts:** `.agents/research/research_lock_pin_stability_{codebase,prior_art,reconcile,community,archaeology}.md`. **Trending approaches:** Prior-art family 4 compares each entry's recorded request: Nix `original`/`locked`, kbld, ToolHive `Source`. OCX moved there in `7378fe0b` with a `declared` field and lock v4. Poetry 2.0 flipped `lock` to keep pins. Helm #11308, open since 2022, is the cost of not doing so.

**Key insight:** A tag has no ordering, so request equality is the only decidable "still satisfied". Lockfile tools restrict the target; planners filter a whole-state diff; prune scope is where accidents happen.

### The pin rule: what a pin answers

The graph holds a set of requests for a key, and `pinned` holds one reference. Review 2's first root cause is treating the one as the other and then relabelling it: a row deleted because one identifier differed, a tag rewritten to a request the digest never answered, a conflict hidden because a shadowed edge read as agreed. One rule replaces those decisions.

**A pin answers a request only where the lock shows that a resolve of that request gave the pin's digest. A writer that did not resolve a tag does not write it.** The one exception is the stamp of consequence 1, by the edit that ends a proof.

`src/lock/pin_rule.rs` defines what a pin answers: the evidence rows below (`PinRecord::names`, `snapshot_matches`, `HashProof::of`, `edge_evidence`, `reached_requests`, and `WalkedEdges`, the edges each previous row records at its digest), the claim verdicts `answers_direct`, `answers_edge`, `answers_listed_edge` and `keeps_pin`, the restamp verdicts `held_by_edges`, `restamp_answers_declared` and `restamp_answers_edges`, and the one tag write `stamp_kept_pins`. Writers compose those answers and define none, with two exceptions. The part-pick step is a second tag writer: it writes `<tag>@<digest>` into the stamps of a part's rows (`PartBundles::write_stamps`, `src/resolve/part_bundles.rs`, owner decision OD-3) and restores held rows, by rules defined outside `pin_rule`. The other exception is the graph's attestation of a typed direct line, the second-to-last evidence row below, which only the walk can decide. The writers: `build_carry` and the graph's `Carry`, `drop_from_lock` with its three paths and its stale restamp (`src/lock/edit.rs`), `effective_set`, `grim add`, and `grim status --check` (`recorded_reference`). What stays outside is composition: which declaration a hash proves (`Prior`), agreement among edges (`merge_policy::settle`), and the graph's refusal to carry a pin onto a claim that names a digest (`Carry::answer`). The match rule itself is `PinnedIdentifier::answers`, which the rule calls. It also names a key a lock lists twice (`listed_twice`): nothing says which row is current, so neither is a pin.

The lock shows an answer in these ways and no others:

| Evidence | Answers | Why it is evidence |
|---|---|---|
| The pin's own record names the request: the match rule, or a `[[bundle]]` row's `repo` and `tag` at a digest the pin holds | Direct and edge claims | That reference resolved the pin |
| The request carries the pin's digest, in the pin's repository | Direct and edge claims | A digest names itself |
| The tagless pin's declaration in the proof | Direct claims | The hash proves the declaration; this is the stamp |
| A recorded edge, where the lock's hash proves a declaration in which the key is not direct | Edge claims | The graph settles a key with no direct claim by agreement: every edge gave one digest, or it exited 78 |
| An edge a parent lists at what the proof shows of it, on a tagless pin the proof holds through edges, in the pin's repository | Edge claims | The parent is read at its pin, or is a key the proof declares with no pin, so its list stands for what resolved this lock. Only an edge the parent's row records at that digest counts (`pin_rule::WalkedEdges`): grim 0.15.1 read no `requires` layer, so its rows list no dependent's edge. `Graph::read_as_proven`; a moved parent and a new key show nothing, and the conflict path takes them. Residual below for a parent with no pin |
| A bundle's edge onto a row, the bundle read at the digest the row's own stamp for it records | Edge claims, under a proof, and on a stale hash only for a tagged pin | The stamp records that the row came through that bundle at that digest and settled at its pin (OD-3) |
| Every edge onto a tagless pin in the line's repository answers the pin, and the tag a relock stamps from them is the typed line's | Direct claims | `grim lock` keeps that pin and stamps that tag, so `grim add` of the line keeps what `grim lock` keeps (OD-2). The graph defines it, not `pin_rule`: the edges are known only once the walk has met them, so such a line reads no tag until then and never attests again once it resolved (`Graph::may_attest`, `stamps_declared`, `attest_direct_claims` in `src/resolve/graph.rs`; plan RD5-52, RD5-57). A line at the tag a recorded edge stamps waits for the walk too: an edge grim 0.15.1 never walked can make `grim lock` release the pin. Such an edge counts once its tag resolves onto the pin and the line's own tag read, as `grim lock` settles it: a second walk keeps the pin, and a refusal there leaves the line's result (`Graph::confirmable`, plan RD6-Q1). The second walk also runs after the line's walk settled a refusal, and its result stands only while every key it confirmed stays attested (plan RD7-c1, RD7-c3). Residual below |
| A recorded edge beside one the pin names, on a lock whose hash is stale | Edge claims | A hand edit elsewhere must not move an honest diamond. Residual below |

An edge onto a key direct in the proof is shadowed, was never resolved, and proves nothing. A recorded edge may answer across repositories. An edge the lock did not record never does, so a pin is never carried into a new repository.

Four consequences hold the writers together:

1. **A kept pin keeps its tag.** `drop_from_lock` rewrites no tag and no repository on a tagged pin. The graph's winner applies to a digest this run resolved, never to a carried pin. After a diamond's holder leaves, `x:1@D` stays beside the surviving edge `x:2`: the pair is true, `pinned` records the reference that resolved the pin, and relocks keep it while the proof holds. A tagless pin takes its tag only from the stamp. A relock stamps from a claim in the pin's own repository. An edit that leaves a proven lock unproven stamps kept tagless pins first (`pin_rule::stamp_kept_pins`), the one write of a tag by a writer that resolved nothing, because the edit is the last holder of the proof: past it every tagless pin would resolve. A key direct in the proof takes its declaration's tag, and any other the winner among the edges the edited lock still records, in the pin's repository. Where none is left, it takes the winner among the edges the previous lock recorded from rows the proof reached. Otherwise a pin kept for a requester whose edges the lock does not record resolves afresh at the next relock. A digest-only request stays tagless. Nothing is stamped on a lock already stale, or where the hash stays a proof, and no digest changes.
2. **A pin stays while it answers a request on its key.** A row whose pin answers any surviving request stays, on every remove path, and under a proof a relock keeps the same pin and label `drop_from_lock` wrote, with zero resolves.
3. **A once-direct key is the case the lock cannot settle.** Its edges were never resolved, and after the declaration leaves nothing says so. `grim remove` is the one command holding that fact, so it acts on it:

   | Surviving requests the pin answers | Row | `declaration_hash` |
   |---|---|---|
   | All | Kept | Restamped as usual |
   | Some | Kept | Left stale |
   | None | Dropped, as `adr_effective_set_mutations.md` decides | Left stale |

4. **An edit that leaves a lock unproven and changes its rows writes a hash no declaration produces** (owner decision OD-1): `sha256("edited:" + old hash)`, through the same `Algorithm::Sha256` and in the same `sha256:<hex>` form, so no reader meets a new value. A declaration hashes JCS text, which opens with `{`, so the preimage is domain-separated. A hash that matches therefore proves the rows were written for that declaration, and an edit that lands on a stale lock's hash returns the lock as it is, except a target row nothing reaches, which leaves with the edit. An edit that changes no row keeps the hash. Nothing writes an empty hash, and one read from disk is stale. On the next relock a pin that names a recorded edge carries every recorded edge, as on any stale lock, so a shadowed edge at another version is not resolved: `grim lock` keeps the pin at exit 0 where a fresh resolve exits 78 (a consequence of owner decision OD-1, which dropped the empty hash), and `grim update` exits 78.

**Hand edits, decided.** Deleting a direct line by hand leaves a stale hash and nothing else, so a once-direct key reads as an honest diamond, and an honest diamond must survive a hand edit elsewhere even when the edge its pin does not name moved (PD-10). Only a resolve could tell them apart, and in that state both give the same digests, so `grim lock` carries: exit 0, pin and tag true, where a fresh resolve exits 78. A later declaration of the shadowed tag resolves, because a direct claim takes no edge as evidence. `grim update` exits 78 naming the conflict, and that is the signal. `grim status --check` is not: it re-resolves the pin's own tag while an edge names it (`pin_rule::recorded_reference`), so a shadowed edge at a tag the pin never held is not asked, and the row reads `false` until the pin's own tag moves.

The residual starts with a hand edit, and a later remove can carry it further. `grim remove`, `grim uninstall` and TUI delete on that stale lock restamp it when every row answers the edited declaration, which a row naming one of its edges does, unless an edge names a digest the pin does not hold: no pin answers that edge, and a relock follows it or exits 78. `grim install` then exits 0 where it exited 65, and the proof reads `Indirect` over an edge never resolved. A `grim lock` gives the same pins, so no wrong bytes follow. Asking for every edge at that gate was the other choice. It would add a refusal, and a tie against a new refusal goes to no refusal (Principle 9).

**Residuals.** A key the proof declares with no pin has no digest to read it at, so on `grim lock` or `grim add` a bundle with no row whose tag moved can stamp a kept tagless pin with a tag that never resolved it. The digest stays, and `grim status --check` reports the update. A selected bundle is read fresh and attests no edge, so under `grim update <bundle>` such a member resolves once with the tagless warning instead. Withholding the stamp on `grim lock` alone does not hold: that lock writes the bundle's row at its moved digest, a second `grim lock` reads the row's edge as a recorded edge, and nothing in the file tells which grim wrote the row, so the same pair follows one run later. Only a new field would hold it, which Principle 9 rules out. Reach: a declared bundle with no `[[bundle]]` row (a lock grim 0.3 or earlier wrote, or one whose `[[bundle]]` rows were cut by hand), or another declared key a hand edit left with no row, whose tag moved since. A lock 0.15.1 wrote over a dependent whose `requires` it never walked does not reach it: such a dependent's row records no edge, so its edges settle as a fresh resolve does (`WalkedEdges`, plan RD6-B1, RD6-B4). On a stale lock a pin naming no recorded edge vouches for none, so a surviving edge resolves once: the request does not match the reference that resolved the pin, which the source's rule allows. A pin that moves this way on `grim lock` is named by one warning (`unvouched_warning`). A hand-merged lock under a matching hash reads as agreed, in any repository a recorded edge names; `git diff` shows it (I5), and the class stays by reference: CWE-345. The same class reaches a walk-back over a pin a hand changed: `drop_from_lock`, `src/lock/edit.rs`, CWE-345. A lock whose hash matches a declaration while its rows do not, which only a hand or a grim before OD-1 writes, is taken as it is by an edit that lands on that hash (`drop_from_lock`, `src/lock/edit.rs`, CWE-345). The attacker is T3, as in the cross-repository Risk under Consequences: a cloned repository's committed lock can carry such a hash, and the remedy is the same, `grim update` or deleting the lock. `grim lock` writes the hash back. A lock already stale has no proof to stamp from, so the edit writes no tag, and a tagless pin there resolves once, named by a warning. A typed line that waits for attestation resolves its tag one pass later. So when that tag is gone and another node of the first walk fails too, that node's error is the one reported; a single failure keeps its exit (plan RD5-57). Beside an edge 0.15.1 never walked, the line reads its tag first, so a gone tag exits 79 where `grim lock` keeps the pin, as on 0.15.1 (plan RD6-R6b). Where keeping the pin walks its own manifest into a refusal the line's walk does not meet, or into an edge onto the key that lands elsewhere, the add takes the line's digest at exit 0, as 0.15.1 does, where `grim lock` refuses (plan RD6-Q2). Where the manifest the line's tag now names cannot be walked, such as a gone tag below it, the add exits with that read's code and writes nothing. That is 79 for a gone tag, as on c5e3824, where `grim lock` keeps the pin, so `grim lock` run first is the remedy (plan RD7-c2).


### D1: the resolving reference is recorded in `pinned` (one-way door)

`project()` stops stripping at `src/lock/grimoire_lock.rs:571` (line numbers in this record are as of the merge base `03393c5`), so `pinned` reads `registry/repo:tag@sha256:…` on every artifact entry, in `grimoire.lock` and `marketplace.lock`. In-memory pins are already tagged (`src/resolve/graph.rs:964-965`). No field is added and `lock_version` stays 1. `[[bundle]]` keeps its sibling `tag` and stays as it is. A digest-only request stays tagless on a direct or fresh resolve. A kept pin is the exception: `x:1@D` beside a lone digest-only edge `x@D` keeps its tag through relocks, because `x:1` did resolve `D`, and `grim update` writes `x@D`. For a transitive node the reference is the winning edge request, resolved against the parent's current pin. For agreeing diamond edges with different tags it is the settled `winner_id`; a digest-bearing edge wins with no tag, and across repositories the first-read id stays (`src/resolve/graph.rs:912-919`). The other edges' requests are never lost: the parent's `requires` still names them, so carry reads them there.

`drop_from_lock` is a lock writer too, and it writes no tag but the stamp of the pin rule's first consequence. That rule governs what it keeps.

**Match rule**, requested reference R against recorded pin P:

| R | Matches iff | Covers |
|---|---|---|
| Has a digest | Same registry/repository, same tag (or both none), same digest | Digest-pinned entries; `--pin`-frozen members (`repo@sha256:…`) |
| No digest | Same registry/repository, same tag | A moved tag carries. Unpinning (`repo:1@sha256:D` to `repo:1`) keeps D until `grim update <name>` |

**Pre-change migration.** `or_latest` adds `latest` only with neither tag nor digest, so a tagless P means a digest-only request or a pre-change lock. One exception: a bare absolute member id in a hand-authored bundle layer is not normalized to `latest`, so its pin is tagless; it stays on relock and moves on update. The test is per pin: a tagged request meets a tagless pin. A digest-only request never qualifies. For the source's case, every `pinned` stripped, the per-pin rule gives the lock-level outcome; a merged lock, tagged and tagless, also warns instead of moving pins in silence. It is judged per plugin part in `marketplace.lock`.

- **Clean:** the declaration proof or a recorded edge names the request. The next write stamps it onto the existing pin, with zero tag resolves. A tagless pin with no recorded edge, from a lock older than v0.10.0, a cut `[[bundle]]` row or a hand-removed row, keeps its pin too: its request is the one its parent lists, read by digest, and a bundle with no row costs one tag read (the plan's RF4 decisions withdraw RD3-3). A parent row that records no edge lists nothing, since its writer may never have read a `requires` layer: grim 0.15.1 writes one for every dependent, so a pin only those edges reach settles as a fresh resolve does, moving or exiting 78.
- **Drifted:** no proof, or a claim the proof cannot show, from a parent that moved or a key new to the lock. That pin resolves once and one warning names the cause and the nodes. On a wholly tagless lock this is "resolve everything once".
- **Clean is judged before the command's own edit.** `add` and the TUI write the config first. Their edit would otherwise read as drift and re-pin everything on the first `add` after an upgrade.
- **Cost:** "no registry contact" is exact on a warm store and means "no tag resolve" on a cold one (plan RD3-7), which is the wording the pages use. Manifests are still read by digest, store first, because edges come from the digest-verified manifest (dependencies ADR, Decision 3). A node the old lock never held, such as an edge 0.15.1 omitted, is simply added.

**What does not move.** Every `pinned` in `lock`, `add`, `status`, `why` and `export` JSON goes through `provenance()` or `strip_advisory()`; `update` prints digests. Install state is the one other file whose `pinned` does not strip (`src/install/install_state.rs:420-433`). `grim install` strips pins when it loads the lock, so a `state.json` this release wrote itself stays byte for byte as it is on main. One 0.15.1 wrote from a tagged lock holds the tag, because 0.15.1 loads `pinned` verbatim, and `grim install` leaves it there while it reports `unchanged`: both sides compare through `eq_content`, so it reads `installed`. A tagged pin is fetched by digest (`external/rust-oci-client/src/client.rs:2243`). `eq_content` ignores the tag, so a stamp keeps `generated_at` and reports `unchanged`.

### D2: an explicit refresh set per command

`Refresh { All, Names, Nothing }` replaces `Option<&[String]>` and `names.is_empty()`. One function, `target_lock`, replaces `resolve_lock_partial`, `roll_forward`, `relock_entry` and `relock_declared`. A pure `plan_lock` derives the dispositions from its result.

| Command | Refresh | Note |
|---|---|---|
| `grim lock` | `Nothing` | Path sources re-pack: `LocalContentChanged` names `grim lock` as the fix |
| `grim add X`, any kind | `Nothing` | X resolves unless the lock holds a pin that answers its reference, as under `grim lock` (OD-2) |
| `grim remove`, `grim uninstall` | no plan | Offline edit; `adr_effective_set_mutations.md` amended for the Some row (pointer in its header). A kept pin keeps its tag and its digest; an edit that leaves the lock unproven and changes its rows writes a hash no declaration produces (the pin rule) |
| `grim update`, and `--marketplace` with no selector | `All` | A marketplace update with no selector is still `grim update` |
| `grim update A…` | `Names` | Kind unknown; a stale lock stays exit 65 |
| TUI Update / TUI Install | `Names` / `Nothing` | Install reads the row's binding off `grim lock`'s own relock; Update and a picked version read it with the same `lock::verdict::row_binding` from a lock whose hash proves the declaration, so a gone pin stops only the update's own relock, as it does `grim update <binding>`. Install on a row that relock reaches at the row's repository edits nothing and saves it; a 78 on the row's key, a row nothing reaches, or a picked version declares, and a catalog row whose guessed name is bound at another source refuses. Update is `grim update <binding>` and writes no line unless a version is picked |
| `update --marketplace M <P>` / `<P>:<member>` | `All` / `Names` on P | Other parts carried verbatim |
| `update --marketplace M <P>:<bundle>` | `Names` on P, the bundle binding | Moves the bundle. Each row that carries its stamp records the new digest, and a member whose reference its list left alone keeps its pin (plan RD5-31, Constitution deviation row 23). Exits 79, as 0.15.1 does, on a plugin with no part, and for a bundle only a `requires` edge reaches on a part 0.15.1 wrote whose plugin includes no bundle (plan RD5-61); `<P>` moves it there |
| Export stage | `Nothing` | Only stale plugins reach it; today's `Whole` pick is overloaded |

**Per-node rule.** A pin moves only when its node is in the refresh set, or R does not match P. Everything else carries, even when its tag moved. A node absent from the previous lock resolves. A direct key new to the declaration keeps a pin that answers it, as under `grim lock` (owner decision OD-2): a `grim add` target the lock holds as a dependency or a member carries. An edit proves against the pre-edit declaration, else the edited declaration the lock still matches.

- **Carry key:** (kind, name) plus the recorded reference, never the reference alone. A selected node never reads a carried pin. The fresh-resolve memo stays keyed by reference, so one tag resolves once per run.
- **What answers a claim:** the pin rule. Registry, repository and any requested digest always match for a direct claim. An edge claim answers by the rule's evidence, read once from the previous lock, so an answer never depends on claim order. Residual: any recorded edge beside a matching edge reads as agreed until `grim update`, a shadowed one too on a stale lock.
- **Carry never copies the old entry.** A carried registry node still reads its manifest by digest, store first, because `StaleDependencies` promises `grim lock` repairs edges. A carried pin whose manifest is gone fails with exit 79 and points at `grim update <name>`; only that command may move it. Declared bundles carry by pinned digest while repo and tag are unchanged, and their members are re-read from that manifest. Offline, a carried bundle the store lacks reads its members from its lock row at the same digest and repository, as a node reads its locked `requires`. A row with no members does not stand in, so a lock from before the member cache stays exit 69, as does a selected or new bundle. `marketplace.lock` holds no bundle snapshot and may gain no field, so a bundle a part reaches, by include, by `requires` or through another bundle, keeps its pin in the stamps of the rows below it, where `bundle_tag` reads `<tag>@<digest>` (owner decision OD-3). The relock carries it at that digest wherever the graph meets it, through any parent, unless the run selects it (`PartCarry`, `lock::part_stamps`). Offline, a recorded digest the store lacks exits 81, as 0.15.1 did, and never follows the tag cache; a recorded bundle whose manifest the registry dropped exits 79 (coordinator ruling STOP-1, 2026-11-08). The stamp is the bundle's record: its repo, tag and digest name the request, as a `[[bundle]]` row's do. Only a run that selects the bundle records a digest: a whole update, a `<plugin>` pick, a `<plugin>:<bundle>` pick of that bundle (plan RD5-31, RD7-f11), or the export stage on a stale part. A pick of a bundle that nests it moves it only where the part records no digest for it. Where the part records one, the pick keeps the nested bundle at that digest and keeps the bundle's members at their pins, and exits 0, where 0.15.1 and c5e3824 followed the moved tag and exited 78 on the conflict it brought (owner 2026-11-08, "Allow 78→0"; the nested bundle keeps its recorded digest; deviation row 4). A pick that names the nested bundle or the member still moves it. On such a run a part that records none, written or re-resolved by 0.15.1, follows the tag, and the export stage warns once per part, naming every row below it that changed, including rows below a nested bundle that left. A `<plugin>:<member>` pick keeps every row outside its selection as the part holds it, pin, tag and stamp alike. It still reads every bundle the plugin reaches, a recorded one at its recorded digest and an unrecorded one at its tag. The rule holds for a requirement that is a bundle too: the bundle the run read for that name is judged as a row's pin is (RF9, review 9 B1). So is each bundle that bundle's list nests at any depth, read at the tag its edge names (RF10, review 10 H1). Where a bundle's tag read fails, the part's stamps of that tag prove the move when a row they mark moved (RF10, review 10 W1). A held row's requirement that the narrowed lock lacks is held with it, and an edge onto a key the plugin includes directly refuses nothing. It records a digest only for a bundle it selects, one a selected bundle nests, or one the part recorded. A bundle no row stamps, whose members the plugin also includes directly, stays read for the member check and records no digest (plan RD7-f11). A `<plugin>:<bundle>` pick records the picked bundle's digest on each row that carries its stamp, as a whole update does. A bundle no row stamps, one that only nests others or whose every member the plugin includes directly, passes its stamp to every row below it, a held direct include's row too, whose pin and tag stay. A row below a nested bundle carries that bundle's stamp, and also the stamp of each bundle above it that records a digest and that no row stamps. A bundle the picked one nests records its own digest only where no row of the part stamps it without one (plan RD7-g1-1, RD7-g1-2). A kept tagless row in a part that records a digest was rewritten by 0.15.1, so no edge attests it; it stays tagless and a warning names `grim update --marketplace` on the plugin. An include takes its kind from the part where a row's pin answers it, or a stamp that records a digest names it. Such an include reads no tag; any other reads its tag, so a bundle republished as a skill is read as a skill. A member it still lists keeps its pin while that pin's tag answers the edge. A bundle read at the digest a row's own stamp records answers that row's pin for its edge, as a `[[bundle]]` row's member list would. Residual: an unrecorded bundle's edge onto a diamond member whose pin records the other edge's tag resolves whenever the part is written. A moved tag there can move the pin, or exit 78 on a real divergence; a fix needs a lock field.
- **Diamonds:** a carried pin that loses a diamond is released and re-resolved, so a moved tag cannot produce a false 78. A real divergence after release still exits 78.
- **A requester whose edges the lock does not record** (plan RD6-0, RD6-G2), as every dependent's row grim 0.15.1 writes. The two lock writers read it by different rules. **The edit** reads only the edges the row records, whatever the store holds, so the row is a leaf and a row only that requester requires drops (plan RD6-G1 where its requires layer is missing, RD6-G2 where it is stored). Where the requester's stored requires reach a dropped row, or may reach it past a link the store lacks, the edit adds one `NoteKind::Unwalked` note. An entry with no row in the previous lock is such a link, whatever the tag cache holds (plan RD7-f31). It reads the requester's own manifest and requires layer, from the store or the registry. Past a stored requires layer the offline relock reads that layer. - **The laundering guard** stays on every lock write, as the identity half of the rule above. The declaration hash shows that the lock matches the declaration, not that a pin is genuine. `grim remove` restamps a lock that was already stale only where a stamp changes nothing a relock or an install would do: no key is listed twice, every key the declaration reaches has a row, every declaration holds its row by the match rule, every other row names an edge and holds any digest an edge names, and no row is left that nothing reaches. Anything else keeps its stale hash, or that hash would prove the wrong set. An edit can also land the declaration back on the hash a stale lock holds. That lock comes back as it was, because since OD-1 an edit that changes the rows of a lock it leaves unproven writes a hash no declaration produces, so a hash that matches was written for those rows. Any other edit that leaves the lock unproven and changes its rows writes that edited hash. Pins are not asked, because every tool that writes a pin also writes the hash.
- **Selection** matches per kind where the caller knows the kind. An unknown name stays exit 79. `Names` accepts a bundle binding: `grim update <bundle>` exits 79 on main because `declared_names` omits bundles, and the ratified scoped-prune case needs it.
- **Dispositions** (added, carried, moved, dropped) are a pure function of the previous and next lock. A stamp or a same-digest rewrite is `carried`. `LockAction` and `UpdateAction` keep their meanings; `UpdateAction` gains `restored`, derived from the install outcome, not the lock diff: the pin was carried and this run's pass wrote the artifact's files, a client's first copy included.
- **Hygiene:** an absent lock is `None`, and a plugin-scoped file reads as absent with a warning. On a command that relocks, every other unreadable or wrong-version lock fails with its load error, before any config write. `grim remove` and `grim uninstall` resolve nothing, so they warn once, edit the declaration and exit 0. `grim update <names>` with no lock warns, names any unknown name, and keeps exit 0.

### Consequences

**Named trade-off: `byte-identical` is narrowed.** `stability.md` promises byte-identity in three sentences (lines 139-143, 467-469, 486-487). Two golden modules and `test/tools/p9_diff.py` byte-compare locks. The ratified `pinned` choice changes those bytes. The discussion rejected `declared` citing those same sentences and did not notice that `pinned` changes bytes too.

What the promise protects is that an older grim keeps reading the file. The context at `stability.md:467-469` and `:486-487` says so, naming `deny_unknown_fields`; at `:139-143` and `adr_artifact_dependencies.md:50` that reading is inference, and the plan flags it. `declared` makes 0.15.1 refuse with exit 78; `pinned` does not. So this record states: reading on both sides must hold, proved by a real 0.15.1 run (Validation). `byte-identical` is narrowed to "identical apart from the advisory tag in `pinned`". The golden fixture bytes are never regenerated. The comparators gain one named equivalence.

**Positive:**
- The re-pin, #269 and shared-reference defects close at their cause. T2 narrows: a moved tag enters a lock only through `grim update` or a changed reference.
- Lock diffs show which reference resolved each entry.
- A downgrade round trip needs no format step. A 0.15.1 write strips every artifact tag. Under a matching hash this code reads that lock as clean pre-change: it keeps 0.15.1's pins, a tag that write rolled included, and stamps them with no tag resolve. Under a drifted hash each tagless pin resolves once, with a warning. So a downgrade is trusted as far as its hash goes, and Risks names where that hash lies.

**Negative:**
- One lock diff on upgrade touches every tagged pin line while the report says `unchanged`. A mixed-version team sees that churn repeatedly.
- A tag called "advisory" now decides carry. Only `eq_content` keeps treating it as advisory.
- `grim update a` no longer reports untouched unnamed rows, so `test_update.py:95` flips with `test_dependencies.py:88-95`.
- `grim lock` on a corrupt lock now fails where it used to overwrite. Deleting the file recovers it and moves every pin, so the recovery that keeps pins is restoring it from git or resolving the conflict markers.
- `grim lock` stops rolling floating tags forward, so stale-pin reports will follow (Cargo #8555). `grim status --check` still answers `update_available`.
- `grim lock` and `grim add` exit 0 on a diamond whose edges parted after a tag moved, where they exited 78. A job that read that exit as a signal loses it; bare `grim update` still exits 78.
- R1's largest exception (residual 1, ratified by the owner on 2026-11-08 as an R1 exception, no code changed). On every lock 0.15.1 wrote, `grim remove`, `grim uninstall` and the TUI delete drop a row only a dependent with no recorded edge requires. They exit 0, as 0.15.1 and c5e3824 do. The next online `grim lock` resolves that row afresh, so its pin moves if its tag moved. One online `grim lock` before the edit records the edges and keeps those pins (D2's requester bullet).

**Risks:**
- T3: a hand-edited digest with the same repository and tag now survives `grim lock`, and for a bundle that digest selects the member list. `grim install` already honours such a lock. What changes is that `grim lock` used to discard it and no longer does: for a checkout you do not trust, run `grim update` or delete the lock. Visibility is `git diff` (I5) and `grim status --check` (`update_available`) for a declared row, a bundle row and a dependency row's own pin. A direct claim in another repository, a requested digest that differs from the pin, and an edge the lock did not record in another repository are mismatches and never carry. A recorded edge is the next Risk but one. I2 holds: the tag decides carry only and never keys trust or consent.
- **Proposed, awaiting the owner.** This bullet's consent reach and timing are goal-loop decisions (RD-3 as corrected in RF2, RD3-6, "TUI consent"), recorded in the Proposed blocks after `adr_hook_workspace_consent.md` decision 4. That decision's accepted text states neither, and the shipped code follows the proposal. Offline an edge counts only when the parent's manifest the store holds at its pin lists it (`stored_reach`), and an add that consents to nothing new arms on the record as it stands. ## Migration and rollout

1. **In place.** Migration is the stamp or the one warned re-resolve. Read-only commands never rewrite a lock. `grim install` leaves tagless pins alone. So does `grim remove`, except that an edit leaving a proven lock unproven stamps kept tagless pins first (the pin rule, consequence 1). Older code reads tagged pins and strips them on write, so a revert needs no format step.
2. **Comparator equivalence `pinned-advisory-tag`.** On an artifact `pinned =` line, drop one `:tag` before `@sha256:`, then compare byte for byte. It never touches a registry port or `[[bundle]]`. It lands in `test_golden_pre_dependencies.py`, `test_golden_pre_hooks.py` and `test/tools/p9_diff.py`.

`src/resolve/pin_agreement_tests.rs` holds every lock writer to these clauses: `drop_from_lock` (`grim remove`), `undeclare_and_unlock` (`grim uninstall` and the TUI delete), `target_lock` as `grim lock` and `grim add` (`Refresh::Nothing`), `grim update <names>` (`Names`) and bare `grim update` (`All`), TUI Install and Update, each at the catalog's tag and at a picked version, as the production `plan_row` decides them, and `resolve_marketplace` per plugin part (first write, the export stage's reconcile, a member update). Registry truth, the declaration's reach, what a row records, what a pin answers and which binding holds a row are restated from the lock's rows, the declaration and the fake registry's own edges and tag history; no oracle reads a writer's code. Writers meet only on purpose: a fresh resolve (`exit-agrees`, `update-agrees`), `grim lock` after an edit (`remove-agrees`) or over a line typed by hand (`held-pin`), and `grim update <binding>` beside a TUI Update (`update-agrees`). Not exercised: `grim update --marketplace`'s file writes and staleness gate, a whole-plugin update after the first write, offline runs other than `grim lock` over an empty store or a store that holds manifests without their layers, several plugins, path includes and `project =` plugins.

- **no-move**: a pin that answers a surviving request survives every relock. An edit may drop such a row only by the RD5-38 residual: on a lock with no dependency data proven before or after the edit, beside a declared bundle with no member list the store cannot show, a row the edited declaration no longer reaches once those bundles leave the walk, named by the `LeftUnread` note (plan RD5-59, narrowed by RD6-x1). A shape retyping one bundle by hand beside a second declared bundle catches an edit that retags the kept row (plan RD6-x2).
- **no-false-pair**: every tag and digest written was the store's answer for that tag at some moment of the scenario.
- **exit-agrees**: a conflict a fresh resolve refuses is refused, and a relock refuses nothing a fresh resolve accepts. The one exception is a key whose declaration a tool took off with its row kept on an unproven lock: `grim lock` keeps that pin at exit 0, a consequence of the owner's decision to drop the empty hash (OD-1, goal § Issue resolution), and `grim update` still refuses. A run that typed a line is also exempt from the refusal check; fuzz seed 3478 needs it.
- **remove-agrees**: over a lock whose hash still proves the declaration, a relock writes what the edit wrote, with zero resolves.
- **fixed-point**: a second relock with no edit resolves nothing and leaves the file byte-identical.
- **proof**: a hash that matches states that every declaration has a row holding what it names, that a declared bundle's row carries the declared repository and tag, that every recorded edge has one, and that a key no declaration holds keeps any digest an edge names.
- **round-trip**: a line typed by hand and taken out by a tool leaves a true proof as it was. Since OD-1 a lock the edit lands on comes back as it was, rows included, except a target row nothing reaches, which leaves with the edit; the residual this leaves is in Residuals, § The pin rule.
- **stamped**: an edit that ends a proof leaves no tagless pin it could tag. A relock leaves no kept tagless pin under a tagged request in its own repository, unless a request names a digest.
- **held-digest**: a digest an edge names outright is the pin a relock writes.
- **held-pin**: `grim add` writes the target pin that `grim lock` writes over the same line typed by hand, from the lock `grim lock` stamps first when the hash proved the declaration. Where that `grim lock` succeeds the add succeeds, and where the add succeeds that `grim lock` refuses only on another key's 78.
- **declaration-left**: an edit that takes a key's registry declaration off keeps the key's row exactly when its pin answers a request the edited declaration still makes onto the key, and a pin that leaves any such request unanswered leaves the lock unproven. It is not judged where offline reading cannot settle the key: an edit that lands on the lock's hash, a declared bundle with no member list, an undeclared bundle an edge names with no row, or an edge of the key no request makes.
- **transitive**: an edit that takes a bundle's declaration off keeps its `[[bundle]]` row only marked `transitive`, since an edge alone then holds it, unless the row stays exactly as it was on a lock with no dependency data, which grim 0.15.1 must still read (plan RD6-E2).
- **unchecked-parent**: on a lock whose hash proved the declaration, an edit drops a target row that only rows recording no edge ask for, whatever the store holds, as 0.15.1 and c5e3824 do (plan RD5-23, RD6-G1, RD6-G2). On any lock, a row the edited declaration reaches only through rows recording no edge may drop: the residual, not owed.
- **unwalked-note**: an edit that drops rows beside a surviving row that records no edge names the rows, that row and the recovery (restore the config and `grimoire.lock`, run one online `grim lock`, repeat the edit) when the store's reach from that row may hold a dropped key, or when a link the store lacks hides it (plan RD6-G5, RD7-n1, RD7-f31). Beside no such row it names none.
- **stamped-member**: a row kept beside a declared bundle with no member list that the store shows provides it carries that bundle's stamp (plan RD5-35).
- **cold-relock**: an offline `grim lock` over a store with no manifest, or with every manifest and no layer, drops every row no edge the lock records reaches, whatever its kind, keeps every pin `grim lock` keeps that such an edge reaches, and writes the declaration's hash; the same lock relocked as a part holds no such row (`a_cold_offline_relock_keeps_only_what_a_recorded_edge_reaches`, plan RD6-0, RD6-F1).
- **mixed-store**: an offline `grim lock` over a store holding one 0.15.1 dependent's requires layer and not another's records the first one's edges alone; each edit of that lock, then an online relock after a tag move, holds every other clause, with the missing layer still missing or stored by another project after the relock; a row only the unread dependent requires drops either way (`an_edit_after_an_offline_relock_over_a_mixed_store_holds_the_pin_rule`, plan RD6-F2, RD6-G1, RD6-G2).
- **restamp**: an edit turns a stale lock into a proven one under a new hash only where every pinned row states what it answered: a tagged pin that names its key's declared reference, or for a key no declaration holds, an edge onto it. A tagless pin states nothing, so it keeps the lock stale.
- **unchanged-rows**: an edit that changes no row and leaves the lock unproven keeps its hash.
- **recorded-edges**: every row records the edges the store publishes at its pin, and a path bundle's row the members its file lists.
- **relock-error**: a relock refuses only with a 78 that names a key; any other error fails the clause.
- **tui-held**: a TUI Install or Update, at the catalog's tag or a picked version, takes the binding that holds the row, restated from the lock, the declaration and the store: a direct entry at the row's location under any binding, or a key the declaration reaches whose pin or a request onto it sits there. An Update writes no line, a pick writes the holding binding's line or, when nothing holds the row, the row's own, and an Install at the catalog's tag keeps the holding binding, declaring a line only for a row nothing holds or on a 78 on its own key. An action that writes no line leaves the declaration as it was, and none succeeds over a key the declaration reaches at another location. A refused action writes nothing and refuses only for a cause the state gives: a 78 where the requests can disagree (never that Install's on its own key), a stale lock or an unheld row on an Update, a tag the store does not serve (never on that Install of a held row), or a guessed name bound or reached elsewhere.
- **install**: a hash that matches states that every key the declaration reaches through the registry's edges at each row's digest has a row, and that every row is reached: `grim install` materializes exactly the rows.
- **refusal**: a refused `grim add` or `grim update` names a conflict, and `grim update <names>` on a stale lock refuses with stale-lock.
- **update-moves**: `grim update <name>` of a key declared at a tag pins what that tag serves.
- **update-agrees**: bare `grim update` writes the rows a fresh resolve writes and refuses where it refuses, and a TUI Update at the catalog's tag on a proven lock writes the rows `grim update <binding>` writes.
- **part-no-move**: a plugin part's relock moves no pin the part held except the selected member and rows below a bundle the part follows by tag (OD-3).
- **part-warning**: the part warning names every changed row below a followed bundle, nested ones included.
- **part-error**: a plugin part's write (the first, the export stage's reconcile or a member update) fails only with exit 78.
