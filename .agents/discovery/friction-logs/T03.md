# Friction log: T03 shared scope vs repo-only scope, and moving an artifact between them

## Context
The persona is a solo developer who works out of three repositories with Claude Code
and Codex CLI and has never used grim before; they want the same two rules and one
skill available in every repo they open without repeating the setup each time, plus
one extra skill that belongs to only one particular project, and they need to
learn from the documentation why grim has two scopes and which one to reach for in
each case, then actually set both up and learn how to tell an installed artifact's
scope apart and how to relocate one from the repo scope to the shared one. Before
starting they had `grim` on `PATH` and no project config anywhere. Written by a
subagent with no repository access, from the published docs pages and the grim
binary only.

## Pros and cons
- Good: `introduction.md`'s "Where to next" list points straight at Concepts for
  "skills versus rules, scopes, locks, and clients", so the scopes explanation was
  one click away from the landing page.
- Good: the "Scopes" section of `concepts.md` states the why in two adjacent
  sentences — project is "per-repository configuration that lives beside your
  code", global is "for artifacts you want everywhere" — no cross-referencing
  required to map the task's two asks onto the two scopes.
- Good: `quickstart.md`'s "Go global" section gave the exact two commands
  (`grim add --global`, `grim install --global`) with no new concepts introduced,
  so acting on the concepts-page explanation was copy-paste.
- Good: `grim context` and `grim context --global` cleanly answered "what scope am
  I looking at" — the `scope` field is unambiguous and the two invocations never
  show a merged view, so there was no ambiguity about which artifacts belonged
  where.
- Bad: `grim search` (empty query, whole catalog) turned up exactly one artifact of
  kind `rule` in the entire index (`hex-state`). The task asked to pick "any two
  rules" but there was only one rule to pick from anywhere in the catalog, so the
  shared set ended up with one rule instead of two — no doc page flagged that the
  catalog is this thin on rules.
- Bad: no page uses the word "move" for relocating a declaration between scopes.
  I had to infer the procedure from `grim remove` vs `grim uninstall` in
  `commands.md` (uninstall deletes files *and* undeclares, remove only
  undeclares) and from `grim add --global` in `quickstart.md`, then chain them
  myself; a reader who only skimmed the Scopes section of `concepts.md` would not
  know uninstall-then-add-global is the way, since that page does not mention
  uninstall at all.
- Bad: the project-scope skill did not land under `.claude/skills/` even though
  the persona's `~/.claude` exists — it landed under `.agents/skills/` because
  client detection for project scope looks at the *workspace* directory, which had
  no `.claude` marker yet. The behavior is documented in `concepts.md` under
  "Clients" ("When nothing is detected it targets the generic `agents` client"),
  so it is not a doc gap, but it was a real surprise mid-task until I reread that
  paragraph.

only global values, project `list` shows only project values" — same rule,

Last part: moving an artifact from repo scope to global. No page uses the word
"move" for this (grepped `move\b` across `commands.md`, `concepts.md`,
`quickstart.md` — only unrelated hits: default-registry reassignment, a
render-layout relocation, `grim remove`/`grim uninstall` table rows). Worked out
the sequence from the `grim remove` vs `grim uninstall` distinction in
`commands.md`: `remove` only undeclares and "leaves already-installed files... in
place", `uninstall` "deletes the materialized files, drops the install record,
and undeclares... from the config and lock" — the full inverse of install. So to
actually relocate rather than duplicate, uninstall at the source scope, then add
at the destination scope:
```
$ grim uninstall skill ai-config-authoring --color never
Kind   Name                 Status
skill  ai-config-authoring  uninstalled

$ grim add --global ghcr.io/grimoire-rs/skills/ai-config-authoring --color never
Kind   Name                 Pinned                                                             Status
skill  ai-config-authoring  ghcr.io/grimoire-rs/skills/ai-config-authoring@sha256:f89a210d...  added

$ grim status --color never
Kind  Name  Source  Pinned  State

$ grim status --global --color never
Kind   Name                 Source  Pinned  State
skill  ai-config-authoring  direct  ...     installed
skill  grim-usage           direct  ...     installed
rule   hex-state            direct  ...     installed
```
Project status is empty, global status now has all three — the move worked.
