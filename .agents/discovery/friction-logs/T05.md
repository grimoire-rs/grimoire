# Friction log: T05 open and operate the grim TUI

## Context
The persona has never used grim before and just got it installed alongside Claude Code and Codex CLI on their machine; they are the kind of developer who would rather arrow through a list than memorize flags, so the interactive browser is the natural entry point for them, and they are starting from a fresh project with nothing declared yet. They want to know: how to open the interactive browser, how to move around in it, what the row states and badges mean, how to install one artifact and update another from inside it, how to see an artifact's details, what "pending" means, and whether it can switch between project and global scope. Written by a subagent with no repository access, from the published docs pages and the grim binary only.

## Pros and cons
- Good: `commands.md`, heading `## grim tui {#tui}`, answers "how do I open it" in the very first sentence — `grim tui` opens an interactive browser over the declared registries, no other setup implied.
- Good: `commands.md` #tui states plainly that scope switching exists and names the key: "`g` to switch scope" — confirmed a second time in `concepts.md` under `## Scopes` ("The TUI can flip between the two at runtime"), so the answer is corroborated on two pages.
- Good: the detail pane and its three tabs (Overview / Readme / Changelog) are documented in their own subsection, `### Detail tabs and repository docs {#tui-detail-tabs}`, with the exact strip rendering shown as a text diagram — easy to recognize once seen.
- Good: "pending" is explained in real depth in `commands.md` #tui under the paragraph starting "**The `+ pending` badge**" — it is materialization drift, cross-referenced to `grim status`'s `outputs_pending` field, and it explicitly says pressing `i` clears it.
- Good: install/update-from-inside-the-TUI is confirmed at the top of the #tui section ("It supports multi-select with batch install, update, and delete") and the state-eligibility rules for `i`/`u`/`d` are spelled out precisely in the tree-mode key table.
- Bad: there is no single keymap table for the default (flat list) view. Movement keys are scattered across several non-adjacent paragraphs of `commands.md` #tui: the intro paragraph gives `t`, `v`, `o`, `g`, `h`, `space`; a much later paragraph ("There is no detail focus...") gives `↑`/`↓`, `j`/`k`, `pgup`/`pgdn`, `tab`, `esc`; `i`/`u`/`d` are only formally defined inside the **tree-mode group table**, phrased as "on a group," so a reader looking for the base single-row meaning of `i`/`u`/`d` has to infer it applies to a plain row too. A newcomer has to assemble the full key map by reading the whole section start to finish rather than looking one thing up.
- Bad: the docs repeatedly punt the complete legend to the app itself — "Press `?` for the full status legend" and "Press `?` in the TUI for the full key map" — meaning the canonical, complete reference is inside the running program, not in the shipped documentation. `grim tui --help` (run against the real binary) does not print any keybinding at all, only CLI flags, so there is no offline way to see the full key map before opening the TUI.
- Bad: row states themselves (`installed`, `outdated`, `locally modified`, `integrity-missing`, `not installed`) are formally enumerated on the *`grim status`* command page, not on the `grim tui` page — the TUI page assumes you already know these five and only adds `pending` and `via bundle` inline, so understanding "what a row state means" requires reading two separate command sections and mentally merging their vocab.
- Bad: badge glyphs are introduced piecemeal and only for the tree rollup — `↑` (outdated), `✱` (modified), `▣` (fully-marked group) are each defined once, in prose, next to unrelated sentences; there is no glyph legend table anywhere in the docs, so a reader has to grep three different paragraphs to build the full glyph-to-meaning list.
- Bad: no worked example shows the persona's exact ask ("install one artifact and update another in the same session") — the batch/multi-select mechanic is described generically (`space` marks rows, `i`/`u`/`d` act on marked rows), but there is no walk-through of, say, marking two rows in different states and pressing the two different keys.

For movement/keys I kept finding pieces in different places rather than one table:

- A dedicated Markdown table only for **tree mode**: `t`, `→`, `←`, `z`, `Enter` (on group vs. on leaf — different behavior!), `tab`/`shift-tab`, `space` on a group, `i`/`u`/`d` on a group.
- Much later, in a paragraph about the detail pane ("There is **no detail focus to enter or leave.**"): `↑`/`↓` move selection, `j`/`k` scroll the pane line by line, `pgup`/`pgdn` scroll a page, `tab` switches panel, `esc` quits on first press.
- Even later, in the Overwrite-dialog and pending-badge paragraphs: confirmation that `i` and `u` are real per-row keys (not just group keys), and that `r` forces a cache-clearing reload of a failed companion fetch.
- An active search is started with `/` (mentioned in passing near the end of the tree-view discussion).

So the full key set is recoverable, but only by reading the entire section top to bottom and keeping a running list — nothing on the page collects it into one table the way the tree-mode table does for its own subset.

For row states, I grepped `-n -i "legend\|not installed\|integrity-missing\|via bundle\|outdated\|status legend"` across `commands.md`. The base five-state vocabulary (`installed`, `outdated`, `locally modified`, `integrity-missing`, `not installed`) is actually defined on the **`grim status`** page (`## grim status {#status}`, line ~593): "Reports each declared artifact's state — installed, outdated, locally modified, integrity-missing, or not installed." The TUI page never redefines these; it just uses them and adds two more concepts specific to the TUI/lock model: `pending` and `via bundle` (member rows). I had to cross-reference both command sections to get the full vocabulary.

Badges: `↑` = some descendant outdated, `✱` = some descendant modified, `▣` = a group filled/fully marked — all three defined in one sentence each, in the tree-rollup paragraph, not as a table. The `↑ outdated` badge gets a second, more detailed paragraph later (about tracking the **declared** reference, not just the resolved one). The `+ pending` badge gets its own full paragraph, clearly the best-documented single badge on the page — ties `pending` directly to `grim status`'s `outputs_pending` JSON field and says explicitly it means "installed, but a client's outputs haven't been written yet" and that pressing `i` clears it.

For install-one/update-another from inside the TUI: the intro line "It supports multi-select with batch install, update, and delete" is the general claim. The precise semantics of `i`/`u`/`d` (which states each key applies to) are given only inside the tree-mode group-action table, phrased as "on a group" — e.g. "`i` acts on `not installed`, `pending` and `integrity-missing` leaves; `u`/`d` act on `installed`, `via bundle`, `outdated`, `modified`, `pending` and `integrity-missing` ones." Nothing states outright "in flat view, pressing `i` on a single not-installed row installs just that row, and pressing `u` on a different outdated row updates just that row" — I'm inferring this is how it works because `space` is described as marking rows for batch action and the group table's rules presumably carry over to individual leaves, but the doc never shows this as a two-row worked example the way the persona's task implies. Recording this as a guess, not a confirmed reading.
