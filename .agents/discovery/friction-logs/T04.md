# Friction log: T04 shared skills directory across Claude Code and Codex CLI

## Context

The persona has never used grim before and alternates daily between Claude
Code and OpenAI Codex CLI on the same machine, wanting an "adversarial
review" skill that either tool can run against the other tool's diff, kept
in one shared directory both tools read instead of two hand-copied files
that drift apart over time. Before starting, the persona had grim already
installed on PATH and no grim config anywhere under `$HOME`, only the two
coding-agent CLIs and a habit of copy-pasting prompt snippets between their
`.claude` and `.codex` folders. Written by a subagent with no repository
access, from the published docs pages and the grim binary only.

## Pros and cons

- Good: `concepts.md`, under "Clients", names the exact mechanism up front —
  a vendor-neutral `agents` client that installs into a shared
  `.agents/skills` pool "read by more clients than write to it" — so the
  right search term (`agents` pool) surfaced from the very first concept
  page, no guessing needed.
- Good: `clients.md`'s "Shared skills pool visibility" section states
  outright which clients read the pool (Cursor, Copilot, OpenCode, Warp,
  Kilo, OpenClaw) and which write it by default (Codex, Gemini, Zed, Amp,
  Goose, `agents`, project-scope Antigravity) — a complete two-list answer
  in one place, no cross-referencing needed to learn Claude Code is on
  neither list.
- Good: `vendor-metadata.md`'s global-scope skills table gives one line per
  client with the exact literal path and its env-var override, so
  `~/.claude/skills/<name>/` versus `$HOME/.agents/skills/<name>/` for
  Codex was a direct table lookup, not inference from prose.
- Bad: nowhere across the nine pages opened is there a worked example or
  even a sentence that names "Claude Code + Codex" together as a pairing
  someone might want to share a skill between. The Claude-Code-writes-only-
  its-own-directory fact and the Codex-always-uses-the-pool fact live in
  the same table on `vendor-metadata.md` but the reader has to notice their
  rows do not overlap — the page never states the negative ("Claude Code
  does not read this pool") next to the positive claim about Codex.
- Bad: `grim add` has no `--client` flag at all (documented, but only after
  reading well into the `## grim add` section), so the first natural
  attempt — one command with a client list — fails by design and a second
  command (`--no-install` then `grim install --client`) is required; a
  first-time user following `quickstart.md`'s single-command framing would
  hit this.
- Bad: the `grim install` result table printed only one row (target
  `~/.claude/skills/nox-review`) for a two-client `--client claude,codex`
  invocation that in fact wrote two directories on disk; nothing in
  `commands.md`'s `## grim install` section mentions the table can under-
  report fan-out across clients, so trusting the printed table alone would
  have left the Codex copy undiscovered.
- Bad: `grim status` afterward showed a single "installed" row for the
  skill with no mention of which client(s) or how many physical copies it
  materialized to — the only way to see two copies is `ls` on disk.

## Detailed stream of consciousness

`date +%T` at the very start: 21:32:52.

Opened `SUMMARY.md` first to get the sidebar order, then `introduction.md`
as the landing page — that page's "Where to next" list pointed at
`concepts.md` for "skills versus rules, scopes, locks, and clients," which
sounded like the right place for a scopes/sharing question, so I went there
next rather than straight to `clients.md`.

`concepts.md`'s "Clients" section paid off immediately:

> `[grim install](./commands.md#install)` writes to the targets listed in
> the `clients` option in your config; without one it targets every client
> it detects... When nothing is detected it targets the generic **`agents`**
> client — not a product, but the vendor-neutral pool at `.agents/skills`
> that several clients already read.

That is the shared-directory mechanism named in one sentence, on the very
first page I'd expect a newcomer to read past the landing page. Ran:

```
$ grep -n -i "agents/skills\|shared\|both.*read\|vendor-neutral\|generic" $DOCS/*.md
```

— a broad first grep, hit in `authentication.md` (irrelevant, "shared
machine"), `clients.md` (several hits, the real payload), pointing me at
`clients.md`'s "Shared skills pool visibility" section.

Read that section in full. It gives two lists: who *writes* the pool by
default (Codex, Gemini, Zed, Amp, Goose, the `agents` target, project-scope
Antigravity) and who *reads* it without grim writing there
(Cursor, Copilot, OpenCode, Warp fully; Kilo project-only; OpenClaw
global-only). I read this twice looking for Claude Code in either list and
did not find it in either — that's the first moment of doubt: is Claude
Code simply not part of this story at all, or did I miss a line?

Ran a second grep to be sure:

```
$ grep -n "Claude Code\|\[Claude\]\|Codex\b\|\.claude/skills\|\.codex" $DOCS/clients.md
```

Twelve hits, none of them putting Claude Code in either pool list — the
only Claude-adjacent lines were about MCP descriptor shape and an unrelated
Cline note ("its own docs list `.cline/skills/`, `.clinerules/skills/` and
`.claude/skills/`, and the pool appears nowhere" — that's Cline documenting
compatibility with Claude's directory, not Claude reading the pool). So by
this point the working hypothesis was: the pool exists, Codex is on it, but
Claude Code is out of the picture entirely and keeps its own directory.

Wanted to confirm the exact literal paths rather than trust prose, so:

```
$ grep -n -i "CODEX_HOME\|\.agents/skills\|skills/<name>\|skill directory\|skills directory" $DOCS/*.md
$ grep -n "~/.agents\|HOME/.agents\|~/.claude/skills\|CLAUDE_CONFIG_DIR" $DOCS/*.md
```

The second one landed on `vendor-metadata.md`'s global-scope table, which I
then read in full (lines ~380-430). This is the page that actually answers
the task's question, in a table row each:

- `[Claude Code]` → `~/.claude/skills/<name>/` (override `$CLAUDE_CONFIG_DIR`)
- `[Codex]` → `$HOME/.agents/skills/<name>/` (shared pool) — "`$CODEX_HOME`
  does not relocate skills; they are always keyed on `$HOME`"

So the two clients I care about resolve to two different physical
directories, always — Codex has no "own" skill directory at all, it *is* a
pool client unconditionally, while Claude Code is never a pool client.
There is no single directory both would read; the closest thing is
`grim install --client claude,codex` writing two synced copies from the
same locked artifact instead of one manually-copied file. That's a weaker
answer than "one shared directory" but grim does keep the two copies from
drifting since both come from the same lock entry.

Also checked `stability.md` and `upgrading.md` (they turned up in the
`.agents/skills` grep) for anything Claude-specific about the pool —
`stability.md`'s "shared-pool refcount" section and `upgrading.md`'s
Gemini/`$GEMINI_CLI_HOME` exception section — neither mentions Claude Code,
consistent with it simply not being a pool participant.

Checked `commands.md`'s `## grim add` and `## grim install` sections before
running anything, via:

```
$ grep -n "^## grim add\|^### " $DOCS/commands.md
```

Learned there: `grim add` has no `--client` flag; the pattern is `grim add
--global --no-install <ref>` then `grim install --global --client
<list>`. Confirmed `--global` is a shared flag via `grep -n -F -- "--global"
$DOCS/commands.md`.

Now the real run, `$S/proj` with `git init -q` already done. Search:

directory.
