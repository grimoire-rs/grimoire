# Friction log: T06 configure two registries with browse filters, verify with search

## Context

I am a platform engineer whose company runs its own package index and also uses
the public grim index; I has never used grim before today. I'm trying to
configure grim so that browsing and searching shows only my company's `acme/`
namespace from the company index but everything from the public index, and I
want to know what these include/exclude filters do and do not affect (does a
direct install by full reference bypass them, does a short id, does `grim
update`). Before starting I had `grim` installed and a fresh git repo, nothing
else. Written by a subagent with no repository access, from the published docs
pages and the grim binary only.

## Pros and cons

- Good: `configuration.md`'s "Multiple registries" section (around the
  `[[registries]]` field table) gives the exact TOML shape for declaring the
  same locator twice under two aliases with different filters, including a
  worked example (`grim`/`mine` aliases both on `index = "https://index.grimoire.rs"`)
  that is almost exactly my task.
- Good: `configuration.md`'s "Browse filters" section opens with the actual use
  case ("a platform team that only ever installs from `acme/platform` still
  pages past marketing's and data's packages") before it ever mentions the
  `include`/`exclude` keys — I did not have to infer the "why" myself.
- Good: `commands.md`'s "Registry lifecycle" section gave copy-pasteable
  `grim config registry add ... --include ... --exclude ...` commands, so I
  never had to hand-edit `grimoire.toml`.
- Good: the exact stderr warning text in `configuration.md` ("filter admitted 0
  of N repositories") appeared verbatim, word for word, when I ran the
  unqueried `grim search` — the docs did not oversell what would happen.
- Good: `configuration.md`'s "A browse filter is not access control" paragraph
  told me up front, before I even tried it, that `grim add` by full reference,
  `grim lock`, `grim install`, `grim fetch`, `grim release`, and `grim status
  --check` all ignore the filter — I did not have to discover this by trial and
  error, I only had to confirm it.
- Bad: `commands.md`'s `grim search` section, in the paragraph right after
  "Ranking replaces registry-declaration order whenever there is a query",
  states "every row still names the registry that served it in its source
  column" for the plain-table output — but four paragraphs later, in the same
  section, it states "Like `repository`, `source` is JSON-only; the plain
  table keeps its five columns." These two sentences contradict each other,
  and my own `grim search grim` run confirms the second one: the plain table
  header is `Kind Repo Summary Version Status`, five columns, no registry or
  source column anywhere.
- Bad: qualified alias references (`alias/repo`, documented in
  `configuration.md` under "Qualified references") are documented generically
  for any alias, but trying it against an `index`-type alias
  (`grim add company/skills/grim-usage`) produced a raw OCI-repository-grammar
  parse error instead of installing anything — the qualified-reference section
  gives only `oci`-type examples (`ghcr.io/acme`, `registry.corp.example/team`)
  and never says whether the same syntax is meant to work against an `index`
  alias.
- Bad: short-id resolution (`grim add grim-usage`) guessed
  `ghcr.io/grimoire-rs/grim-usage:latest`, dropping the `skills/` path segment
  the artifact actually lives under, and failed with a registry auth error
  rather than a "not found" — I could not find the page that explains how a
  short id is expanded against an index-backed default registry to know
  whether this was expected.

## Detailed stream of consciousness

`date +%T` at the start: `21:33:11`.

Opened `SUMMARY.md` first to see the sidebar order, then `introduction.md` as
the landing page. Introduction sold me on the pitch (versioned artifacts over
OCI, no bespoke server) and pointed me at Installation, Quick Start, Concepts,
Host Your Own Index, Command Reference. Since my task is entirely about
registries, I skipped straight to `configuration.md` rather than Quick Start.

Ran `grep -n -i "registr" $DOCS/configuration.md | head -60` — hit, lots of
matches, including line 190 `## Multiple registries {#multiple-registries}`
and line 327 `Two optional glob lists on a [[registries]] entry` (the
browse-filters section). Read `configuration.md` lines 190-480 in full.

The field table under "Multiple registries" told me `include`/`exclude` are
glob-pattern arrays, `exclude` wins on overlap, and — this is the part I
needed most — that the same locator can be declared twice under two aliases
as two independent "views": the doc's own example is almost my task
verbatim:

```
[[registries]]
alias = "grim"
index = "https://index.grimoire.rs"
exclude = ["michael-herwig"]
default = true

[[registries]]
alias = "mine"
index = "https://index.grimoire.rs"
include = ["michael-herwig"]
```

Then read the "Browse filters" section itself (line 327 onward). It leads
with the use case in prose — a platform team drowning in marketing's and
data's packages in one shared index — before the mechanics. It also has a
very direct paragraph, "A browse filter is not access control", that lists
exactly which commands ignore the filter: `grim add` by full reference,
`grim lock`, `grim install`, `grim fetch`, `grim release`, and `grim status
--check`. That answered half my task (what filters do NOT affect) before I
ran a single grim command.

Went to `commands.md` next, grepped `config registry` to find the CLI verbs:
`grim config registry add/set/use/show/rm/list/fields`. Read lines 105-260,
which document the dotted-key surface (`registry.<alias>.include` etc.) and
the lifecycle-verb examples with `--include`/`--exclude` flags.

Then I actually did the task:

```
$ export S=.../fl/T06; export HOME=$S/home; export PATH=.../scratchpad/bin:$PATH
$ cd $S/proj && git init -q
$ grim --version
grim 0.14.1
$ grim init --color never
Path                                    Scope    Status
.../fl/T06/proj/grimoire.toml           project  created
```

```
$ grim config registry add company --index https://index.grimoire.rs --include 'acme/**' --color never
Action          Key               Value                      Scope    Dry Run
registry-added  registry.company  https://index.grimoire.rs  project  false
$ grim config registry add public --index https://index.grimoire.rs --default --color never
Action          Key              Value                      Scope    Dry Run
registry-added  registry.public  https://index.grimoire.rs  project  false
$ grim config registry list --color never
Alias    Type   Source                     Default  Filters               Insecure
company  index  https://index.grimoire.rs  false    1 include, 0 exclude  false
public   index  https://index.grimoire.rs  true     —                     false
```

No warning fired on adding the second entry over the same locator — matches
the doc's claim that two views of one locator under different aliases is a
supported shape, not the "repeats an earlier entry" collapse case (which the
doc says only fires for a project entry repeating a *global* one under the
*same* alias).

I picked `acme/**` as the include pattern to stand in for "my company's
namespace", knowing the real content on the public index (my only reachable
index in this sandbox) does not actually have an `acme/` namespace — the two
real namespaces I can see are `grimoire-rs` and `michael-herwig`. That means
my "company" view is expected to come back empty against this stand-in data,
which is itself informative: it lets me watch the "filter admitted 0 of N"
warning fire for real, and confirms the "company" source is queried (not
silently skipped) even when it matches nothing.

```
$ grim search grim --color never | head -40
```
gave a 17-row plain table with a header of exactly `Kind Repo Summary Version
Status` — no column naming which of my two registries a row came from. I
went back to `commands.md`'s `grim search` section (line 869 on) to check
whether this was expected, and found the two sentences that disagree with
each other quoted in Pros and cons above.

Re-ran with `--format json | head -60` and this time each item does carry a
`"source": {"alias": "public", "locator": "https://index.grimoire.rs"}`
object, and the document ends with a `"sources"` array naming both `company`
and `public` with `"ok": true` each. I saved the full JSON to a scratch file
and grepped it: every one of the returned items has `"alias": "public"`
inside `items`; `"alias": "company"` appears exactly once, only in the
closing `sources` array, confirming company matched zero rows but was still
queried successfully. So: yes, you can tell which alias a result came from —
but only in `--format json`, never in the plain table, and the mechanism
(`source.alias`) is documented on a *different* page (`json-interface.md`,
not `commands.md`'s own `search` section, though `commands.md` does also
mention `source` in one late paragraph — the contradictory one noted above).

Ran the unqueried browse to see the mis-aimed-filter warning the docs
promised:

```
$ grim search --color never | head -10
 WARN grim::catalog::catalog_service: registry 'company': filter admitted 0 of 17 repositories; patterns match either the repository path or the fully-qualified reference, and anchor at the candidate's first segment — see https://grimoire.rs/configuration.html#browse-filters
Kind    Repo                                            Summary   ...
```
— fired on stderr, word for word matching the doc's sample warning text, and
the plain table beneath it still has five columns, confirming what I found
above.

Now the "what does the filter NOT affect" half, which the docs had already
told me the answer to; I wanted to confirm rather than take it on faith.

```
$ grim add ghcr.io/grimoire-rs/skills/grim-usage --color never
Kind   Name        Pinned                                                              Status
skill  grim-usage  ghcr.io/grimoire-rs/skills/grim-usage@sha256:f9746a9e...  added
```
Installed cleanly by full reference even though this repository is not under
`acme/**` and so would never show up when browsing through the `company`
alias. Confirms the "not access control" paragraph.

Then I tried the qualified-alias form documented under "Qualified references"
in `configuration.md`, expecting it to expand `company/` the same way the
doc's `acme/code-review:1.2` example expands against an `oci`-type alias:

```
$ grim add company/skills/grim-usage --color never
invalid identifier 'https://index.grimoire.rs/skills/grim-usage': repository must match the OCI name grammar: lowercase [a-z0-9] runs joined by '.', '_', '__', or '-', with no leading, trailing, or doubled separator
```
The alias expanded to the full index URL and that whole URL was then treated
as an OCI repository path, which of course fails the OCI name grammar. The
qualified-references section's own examples are both `oci`-type aliases; I
could not find anywhere in `configuration.md`, `package-index.md`, or
`commands.md` that says whether `alias/repo` is meant to work at all against
an `index`-type alias, or that it does not.

Tried the short-id form next:
```
$ grim add grim-usage --color never
ghcr.io/grimoire-rs/grim-usage:latest: registry authentication failed: Not authorized: url https://ghcr.io/v2/grimoire-rs/grim-usage/manifests/latest
```
This guessed a path that drops the `skills/` segment the artifact actually
lives under (`ghcr.io/grimoire-rs/skills/grim-usage`, per the successful full
reference above) and then hit ghcr.io directly rather than the index, ending
in an auth error rather than a clean "not found". I did not find the page
explaining short-id expansion against an index-backed default registry, so I
cannot say whether dropping `skills/` is the documented short-id shape or a
guess that happened to be wrong for this artifact's path depth.

Finished with the two commands the docs said ignore the filter entirely:
```
$ grim update --color never
Kind   Name        Old          New          Action
skill  grim-usage  sha256:f974  sha256:f974  unchanged
$ grim status --check --color never
Kind   Name        Source  Pinned                          State
skill  grim-usage  direct  ghcr.io/grimoire-rs/skills/grim-usage@sha256:f974...  installed
```
Both ran against the already-locked artifact with no reference to either
registry's filter, consistent with the "not access control" paragraph.
