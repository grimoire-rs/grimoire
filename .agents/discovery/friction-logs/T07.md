# Friction log: T07 install a skill for Claude Code only, add Cursor, drop Codex

## Context

The persona is a developer who uses Claude Code today, is planning to start using Cursor next week, and has never used grim before; they want to declare one skill for Claude Code only, then extend the same declaration to Cursor without re-running the install from scratch, then remove a client (Codex) they never actually use and see what happens to files already on disk. Before starting, the persona had `grim` installed and an empty project directory with no `grimoire.toml`, no lock file, and no client configuration of any kind. Written by a subagent with no repository access, from the published docs pages and the grim binary only.

## Pros and cons

- Good: quickstart.md's "3. Install into your AI client(s)" step gives the exact `--client claude,copilot` pattern, which transferred directly into `grim config set options.clients claude` to target Claude Code alone.
- Good: configuration.md's `grimoire.toml` section documents `options.clients` as a plain TOML array with the exact `grim config set options.clients claude,opencode` syntax; the identical command (with `cursor` appended) is all it took to add Cursor, and a later `grim install` alone materialized the skill there — no re-`add` needed.
- Good: commands.md's `grim update` section states plainly that "Pruning and client-reaping happen only on `update`. `grim install` materializes the current lock but never deletes." This matched exactly: after removing `codex` from `options.clients`, a plain `grim install` left the orphaned `.agents/skills/grim-usage` file untouched, and only `grim update` deleted it, reporting `"reaped_clients": ["codex"]`.
- Good: concepts.md's "Clients" section explains the vendor-neutral `agents` fallback (used when nothing is detected) before any command output could otherwise confuse the reader.
- Bad: quickstart.md's install step names the clients `grim install` detects "by default" as "Claude Code, opencode, GitHub Copilot, OpenAI Codex" — four names, with no hint that a dozen-plus more clients exist (Cursor among them). I only learned the full 17-client list, and that Cursor was even a valid `--client`/`options.clients` value, from concepts.md's "Clients" section, one page later.
- Bad: commands.md's `grim add` section states "`grim add` has no `--client` flag of its own" only deep inside the install-on-add paragraph — quickstart.md's step 2 shows `grim add ghcr.io/...` as the entire "declare and install" command with no forward pointer to that limitation, so the natural first move (add, then figure out narrowing later) does not compose with "Claude Code only" the way the quickstart's own flag vocabulary implies.
- Bad: `grim config set options.clients <list>` **replaces** the whole array rather than appending to it. commands.md's dotted-key table documents this as "An unordered set of unique values... input order is otherwise preserved on store," phrased as a serialization note, not a warning — nothing calls out that running `grim config set options.clients cursor` alone (forgetting to re-list `claude`) would silently drop Claude Code from the config.
- Bad: the plain-table report from `grim install` printed exactly one row ("Target: `.claude/skills/grim-usage`, Status: `updated`") for the run that added Cursor, even though the same run also materialized a brand-new `.cursor/skills/grim-usage` directory. Nothing in commands.md's `grim install` section says the report is one row per *artifact* rather than one row per *output*; I only found the new Cursor path by separately running `grim status --format json`.
- Bad: `grim status --format json`'s `outputs` array stopped listing `codex` the instant it was removed from `options.clients` — before any `install`/`update` ran, and while the file was still on disk and still present verbatim in `.grimoire/state.json`. json-interface.md describes `outputs` only as "read back from install state," with no mention that it is filtered against the currently configured client set; `clients_extra` was the only field that told me the file was still there.
- Bad: neither concepts.md nor clients.md states, in one place, what concretely counts as a "vendor directory or marker" for an ordinary client. concepts.md just says "vendor directory or marker present," and clients.md's per-client "Known gaps" notes only cover exceptions (Antigravity's opt-in-only detection, Kiro's legacy `.kilocode/`) rather than the base rule for Claude Code or Cursor.
- Bad: I never actually got to observe a *default-detected* client set, because after `grim init` (run in a repo with no client markers of any kind) the resulting `grimoire.toml` had no `[options]` table at all — nothing to read the "how are clients chosen by default" answer off of directly; I had to infer the fallback-to-`agents` behavior from concepts.md's prose rather than from any command output in this session.

## Detailed stream of consciousness

`date +%T` → `21:35:07`. Opened `introduction.md` first, per the sidebar order in `SUMMARY.md`. It links onward to Installation, Quick Start, Concepts, Host Your Own Index, Command Reference — I went to Quick Start next since the task is "install a skill."

`quickstart.md` step 3 ("Install into your AI client(s)") says: "By default it targets every AI client it detects in the workspace (Claude Code, opencode, GitHub Copilot, OpenAI Codex); pass `--client` to pick explicitly, with a comma-separated list to install into several at once." I took this at face value as "the" client list at first — it reads like an exhaustive enumeration, not an example set. I did not yet know Cursor was supported.

Ran the setup:
```
$ cd $S/proj && git init -q
```
exit=0.

```
$ grim --version
grim 0.14.1
exit=0
```

```
$ grim init --color never
Path                                                                    Scope    Status
.../proj/grimoire.toml                                                 project  created
exit=0
$ cat grimoire.toml
#:schema https://grimoire.rs/schemas/grimoire-config.schema.json

[skills]

[rules]
```
No `[options]` table was written at all. I went back to `configuration.md` and found the explanation only in the `grim init` writeup in `commands.md`: "`init` also seeds `[options].clients` with the clients it detects for the scope... Detecting nothing writes no `[options]` table at all — the scope stays on autodetect." So in this fresh sandbox project, with no `.claude`/`.cursor`/etc. directory yet inside `$S/proj` (the `~/.claude`/`~/.codex` under `$HOME` apparently do not count for project-scope detection — the docs never state this explicitly, I only infer it from the empty `[options]` table), nothing was detected. This meant I could not observe what "the default detected set" actually looks like in this session — I had to fall back to reading `concepts.md`'s prose about the `agents` fallback instead of seeing it happen.

To get "Claude Code only" for real (not just by accident of nothing else being installed), I searched `commands.md` for `grim add`'s flags and found: "`grim add` has no `--client` flag of its own; use `--no-install` when you mean to declare now and choose clients later." So instead I set the client list explicitly first, following the `options.clients` syntax from `configuration.md`:
```
$ grim config set options.clients claude --color never
Action  Key              Value   Scope    Dry Run
set     options.clients  claude  project  false
exit=0
```
Then declared and installed the skill from the quickstart example:
```
$ grim add ghcr.io/grimoire-rs/skills/grim-usage --color never
Kind   Name        Pinned                                                              Status
skill  grim-usage  ghcr.io/grimoire-rs/skills/grim-usage@sha256:f974...  added
exit=0
```
Verified:
```
$ find $S/proj -path $S/proj/.git -prune -o -print | sort
.../proj/.claude/skills/grim-usage/SKILL.md
.../proj/.claude/skills/grim-usage/references/...
.../proj/.grimoire/state.json
.../proj/grimoire.lock
.../proj/grimoire.toml
$ grim status --color never
Kind   Name        Source  Pinned  State
skill  grim-usage  direct  ...     installed
```
Only `.claude/` exists — good, Claude Code only, matching the goal.

Next: add Cursor "without redoing everything." I re-used the exact `grim config set options.clients <list>` shape from `configuration.md`, this time listing both names:
```
$ grim config set options.clients claude,cursor --color never
Action  Key              Value          Scope    Dry Run
set     options.clients  claude,cursor  project  false
```
I noticed the value is a full replacement, not an append — if I had typed just `cursor` here I would have silently dropped `claude`. Nothing in the docs I read flagged this as a footgun, it just reads as a syntax description.

Checked status before installing anything further:
```
$ grim status --format json --color never
...
"clients_missing": ["cursor"],
"outputs_pending": [{"client": "cursor", "path": ".../.cursor/skills/grim-usage"}]
```
This matched `commands.md`'s description of `outputs_pending` exactly — "a client that gained support since the last install... nothing was ever recorded for it," remediation `grim install`. Ran it:
```
$ grim install --color never
Kind   Name        Target                                   Status
skill  grim-usage  .../.claude/skills/grim-usage             updated
exit=0
```
This one line was confusing — it names the *Claude* path and says "updated," giving no visible sign that Cursor was touched at all. Only by re-running `find` and `grim status --format json` did I confirm `.cursor/skills/grim-usage` now exists and that `outputs` lists both `claude` and `cursor`. No `grim add` was re-run — the "without redoing everything" goal held, but the confirmation of *how* it held was not in the command's own output.

Now the Codex step. Codex was never in my client list up to this point (I had deliberately scoped to `claude` then `claude,cursor`), so to observe a real removal I first added it and installed it:
```
$ grim config set options.clients claude,cursor,codex --color never
$ grim install --color never
Kind   Name        Target                          Status
skill  grim-usage  .../.claude/skills/grim-usage   updated
```
`find` afterward showed a new `.agents/skills/grim-usage` directory — not `.codex/skills/`. I went looking in `clients.md` for why, and found the answer only in the "Known gaps" → "Shared skills pool visibility" subsection, several screens down: "grim installs skills into `.agents/skills` by default for Codex, Gemini, Zed, Amp, Goose, the vendor-neutral `agents` target..." That is a significant, non-obvious fact — the matrix table itself just shows a `✓` in Codex's Skill column with no indication of *where* the file lands.

Then removed Codex from the list and watched status before touching anything else:
```
$ grim config set options.clients claude,cursor --color never
$ grim status --format json --color never
"outputs": [{"client":"claude",...},{"client":"cursor",...}],
"clients_extra": ["codex"]
```
I expected `outputs` to still list `codex` (the file is still on disk, per `.grimoire/state.json` which I `cat`-ed directly and which still shows the codex entry verbatim) — but `outputs` silently dropped it, and only `clients_extra` surfaced that a `codex` output still existed somewhere. json-interface.md's description of `outputs` says nothing about this filtering.

```
$ grim install --color never
Kind   Name        Target                          Status
skill  grim-usage  .../.claude/skills/grim-usage   unchanged
$ ls .agents/skills
grim-usage        # still there — install never deletes, exactly as commands.md says
$ grim update --format json --color never
"reaped_clients": ["codex"], "action": "unchanged", "refused": false
$ ls -la .agents
skills   # now empty — file gone, empty directory left behind, nothing in docs promised this either way for a plain skill pool
```
`date +%T` → `21:37:55`. Final `grim status` showed one clean, installed skill row and a `grimoire.toml` with `clients = ["claude", "cursor"]` — task state matches intent.

Docs pages opened: `introduction.md`, `quickstart.md`, `clients.md`, `concepts.md`, `configuration.md`, `commands.md`, `json-interface.md`.
