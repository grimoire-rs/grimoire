# Friction log: T09 team + CI pin, stale-lock gate

## Context

The persona is a team lead setting up one repository for six developers plus
a CI job who has never used grim before, trying to make every developer and
CI install exactly the same artifact versions, know which files to commit,
and make CI fail when someone's lock is stale or someone edited the config
without relocking; before starting they had only a fresh empty repo and the
`grim` binary already installed. Written by a subagent with no repository
access, from the published docs pages and the grim binary only.

## Pros and cons

- Good: `introduction.md`'s "Where to next" list and `concepts.md`'s "The
  lock" section correctly primed the mental model (`grimoire.toml` +
  `grimoire.lock`, a stored "declaration hash" so drift is detectable)
  before I touched the CLI.
- Good: `configuration.md`'s "Data layout" section (around line 1002) answers
  the commit-vs-ignore question precisely: commit `grimoire.toml` and
  `grimoire.lock`, and `grim` itself drops a self-managed `.grimoire/.gitignore`
  (`*`) the first time `.grimoire/` (project install state) appears, so
  nothing has to be hand-added to a root `.gitignore`.
- Good: the actual CI gate works exactly as a team lead would want —
  `grim install` (with or without `--offline`) refuses at exit `65` with a
  clear message (`grimoire.lock is stale (declaration_hash … does not match
  current …); run \`grim lock\` before installing`) the moment `grimoire.toml`
  is hand-edited without relocking. `--format json` wraps the same message in
  a clean `{"error": {"code": "data", "exit": 65, "message": …}}` document.
- Bad: there is no page or section written for this job. `ci.md` is titled
  "Publishing from CI" but is entirely about `grim publish`/`grim publish
  --announce` from a maintainer's pipeline — nothing about a consumer/team CI
  job installing pinned artifacts. I had to assemble the workflow myself from
  `concepts.md` ("The lock"), `quickstart.md`, and `commands.md`'s scattered
  `grim install`/`grim lock`/`grim status` sections.
- Bad: the stale-lock refusal (exit `65`, `declaration_hash` mismatch) that
  is exactly the CI gate the task needed is not documented anywhere I could
  find under `commands.md`'s `## grim install` heading. I only found it by
  causing it experimentally; a `grep -n stale commands.md` turns up two
  unrelated hits (a catalog-cache staleness note and a bundle-removal
  staleness note), neither under `grim install`.
- Bad: `grim status --check` (which the task explicitly asked me to try as a
  possible CI check) does surface `state: stale` in its table, but
  `commands.md` states plainly ("`grim status` is a report, not a gate") that
  its exit code always stays `0` — confirmed empirically below. It cannot be
  used as the CI failure signal by itself; only `grim install`/`grim lock`
  give a non-zero exit.
- Bad: my first `grim install --offline` attempt (before ever running a
  non-offline install) failed with `offline mode blocked a required network
  operation` (exit `81`) even though I had already run `grim add`/`grim
  lock` for both artifacts. `concepts.md`'s "Online by default, offline on
  demand" section says to "warm the cache with a normal online `grim lock`",
  but locking alone did not warm the content cache needed for materialization
  — an online `grim install` was still required first. This cost a guess and
  a retry before I understood lock-resolution and content-fetch are two
  separate caches.

## Detailed stream of consciousness

`$ date +%T` → `21:33:24`. Set up sandbox exports, `mkdir -p`, `cd $S/proj &&
git init -q`, `grim --version` → `grim 0.14.1`, exit 0. Read
`$DOCS/SUMMARY.md` to get the sidebar order — `ci.md` is titled "Publishing
from CI", which already looked like a mismatch for "make CI fail on a stale
lock", but I opened it later anyway to confirm.

Opened `introduction.md` first, as a first-time user would. It pointed me at
Quick Start and Concepts. Opened `quickstart.md` — walks through `grim init`,
`grim add`, `grim install`, `grim status`, `grim update`, but never mentions
a CI-consumption or team-pin workflow explicitly; the closest is "Sharing
config across a team means publishing it" which is about *publishing* a
shared index, not about locking already-declared config for a team.

Opened `concepts.md` next, which is where the real substance for this task
lives: "The lock" section says verbatim: "The lock also stores a hash of the
declaration it was generated from, so Grimoire can tell when `grimoire.toml`
has drifted ahead of the lock." That is precisely the mechanism I need for
"CI fails when someone edited config without relocking" — but the page does
not say which command surfaces or enforces that drift, or what exit code
results. I made a mental note to test empirically.

Ran greps across all doc pages for the CI-gate vocabulary I expected from
other package managers (`cargo --locked`, `npm ci`): `grep -rn
"frozen\|--check\|--locked\|drift\|stale\|CI\b" commands.md` — 24 hits in
commands.md, none of them a `--frozen`/`--locked` flag on `install` or
`lock`. `grep -rn "frozen\|exit code\|exit-code" *.md` — nothing about a
lock-specific exit code either; only `grim rate`'s and `config`'s own exit
code tables exist, plus the general `stability.md` mention that exit codes
are frozen contracts. Checked `commands.md`'s `### grim lock {#lock}` section
directly (`sed -n '440,660p'`) — it is two sentences long: "Resolves the
floating tags... Run it after editing the config by hand; `grim add` already
locks what it declares." No mention of a check-only mode or of what happens
if you *don't* re-lock.

Read the full `## grim status {#status}` section — confirms `outputs_pending`
etc. but ends with "the exit code stays `0`: `grim status` is a report, not a
gate", which directly rules it out as the CI failure signal I need, before I
even ran it.

Read `configuration.md`'s `## grimoire.lock` section in full (`sed -n
'760,870p'`) — confirms lockfile is machine-owned, commit it alongside
`grimoire.toml`, shows the TOML shape including `declaration_hash` under
`[metadata]`. Then the "Data layout" section a bit further down settles the
commit-vs-ignore question: project install state lives in
`.grimoire/state.json`, and grim writes its own `.grimoire/.gitignore` (`*`)
the first time that directory is created, "so the state file is kept out of
version control without touching your root `.gitignore`."

Opened `ci.md` in full to check for a team/CI-consumption angle — it is
entirely about `grim publish` from GitHub Actions / GitLab CI (credentials,
`--announce`, tokens). Nothing about consuming/installing pinned artifacts in
CI. Confirmed this page does not cover the job I was asked to do.

At this point (~10 minutes in) I stopped searching and started doing the
task, since no dedicated page existed and I had already gathered the
scattered pieces (`grim init` → `grim add` (locks automatically) → commit
both files → `grim install` in each consumer, `grim lock` after any hand
edit).

I used `--no-install` here deliberately, on the theory that the team lead
would want to *declare and lock* the shared set before any developer's
client-detection kicks in, rather than installing into whatever client
happens to be autodetected on the lead's own machine. `grimoire.toml` ended
up with `:latest` references, because I passed a bare reference with no tag —
`quickstart.md` warned floating tags like `:1` are what makes `grim update`
meaningful, so I noted this as a first-time trap: it's easy to `add` without
a tag and get `:latest` rather than a tracked major.

Now the CI-style command. Since nothing in the docs names one directly, I
tried the most CI-idiomatic thing `concepts.md` described — cache-only,
reproducible install:

```
$ grim install --offline --color never
ghcr.io/grimoire-rs/skills/ai-config-authoring@sha256:f89a210d77918758f5fbc6b18eb11dbc5d7a5018e8531be0cb6665e6a9568a68: offline mode blocked a required network operation

```

This surprised me — I had already run `grim add` (which locks) for both
artifacts, and `concepts.md` says to "warm the cache with a normal online
`grim lock`... before going offline." Locking apparently only resolves and
caches the *digest*, not the artifact content layer itself; `--no-install`
never pulled the blob. Ran a normal online install to warm it:

Now the stale scenario: hand-appended a third declaration
(`grim-authoring`) straight into `grimoire.toml` without running `grim add`

```

21:36:35
$ grim install --offline --color never

```

This is exactly the CI gate the task asked for — but I found it by guessing
and testing, not by reading a documented behavior. I double-checked it was
not an `--offline`-only side effect by running plain `grim install` (online)
against the same stale config:

```
$ grim install --color never
grimoire.lock is stale (declaration_hash sha256:1f21d931174e4d75c3a8cb11dd189a8aacdfa001e18a53cef940187ccdcf5a00 does not match current sha256:dc661e7a4dfa108823d3c246738e2fa97d1f8222e22e870203016a4c007ec218); run `grim lock` before installing
exit=65
```

Same refusal either way — the drift check runs before the offline/online
distinction even matters. `--format json` wraps it cleanly:

```
$ grim install --offline --format json --color never
{
  "error": {
    "code": "data",
    "exit": 65,
    "message": "grimoire.lock is stale (declaration_hash sha256:1f21d931174e4d75c3a8cb11dd189a8aacdfa001e18a53cef940187ccdcf5a00 does not match current sha256:dc661e7a4dfa108823d3c246738e2fa97d1f8222e22e870203016a4c007ec218); run `grim lock` before installing"

Also re-ran `grim status` on the stale config to see the state word the

`grim status --check` on the same stale config gave the identical table,
same `exit=0` — confirming, as `commands.md` states, that `status` never
gates on drift; only `grim lock`/`grim install` do.

Fixed it the documented way and confirmed recovery:

```
$ grim lock --color never
Kind   Name                 Pinned                                             Action
skill  ai-config-authoring  ghcr.io/.../ai-config-authoring@sha256:f89a2...    unchanged

exit=0

$ grim install --offline --color never    # new artifact's blob not cached yet
