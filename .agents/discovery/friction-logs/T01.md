# Friction log: T01 install grim and confirm it runs

## Context
The persona is a TypeScript developer on Ubuntu who has never installed `grim` or heard of OCI registries; a colleague sent only the link https://grimoire.rs, so the only starting point was the landing page itself. The goal was to get the `grim` binary onto the machine and confirm it runs, using nothing but the published docs. Before starting, the only things in place were a shell, Claude Code and OpenAI Codex CLI already installed, and an empty project directory — no `grim`, no familiarity with OCI, ocx, or any Grimoire-specific vocabulary. Written by a subagent with no repository access, from the published docs pages and the grim binary only.

## Pros and cons
- Good: `introduction.md` is short and ends with a clearly labeled "Where to next" list, so the very first click (Installation) is unambiguous.
- Good: `installation.md` puts one option under a heading literally titled "Recommended: install with ocx" — no doubt about which path is favored.
- Good: `installation.md` ends with a dedicated "Verify" section giving exactly one command (`grim --version`) and says in plain words what success looks like ("If the command prints a version string, you are ready for the Quick Start").
- Good: the Verify section directly links to Quick Start, so "what do I do after installing" has an unambiguous, one-click answer.
- Bad: the "recommended" path is not actually installing `grim` — it's installing a second, unfamiliar package manager (`ocx`) first, then using that to install `grim`. For someone who has "never heard of OCI registries," the recommended route adds an extra unfamiliar tool and one more curl-pipe-to-shell step before you even reach the `grim` install command (`ocx --global add grimoire/cli`).
- Bad: "OCI registry" appears in the second paragraph of `introduction.md` with only an external hyperlink (to the OCI distribution-spec repo) as explanation — no inline plain-English gloss for a reader who has never heard the term, which is exactly the persona's stated starting knowledge.
- Bad: the install script requested by policy (`curl -fsSL https://setup.ocx.sh/sh | sh`) is a raw curl-pipe-to-shell command with no visible way to inspect the script first (no "view the script" link, no checksum mentioned for this path specifically — the checksum guarantee is only mentioned for the non-ocx install script and the pre-built binaries).

## Detailed stream of consciousness

Started the clock: `date +%T` → `21:32:42`.

Opened `SUMMARY.md` first to get the sidebar shape, since that's what a sidebar-driven doc site would show as a nav: Introduction, then Installation, Quick Start, Concepts, Client Compatibility, Command Reference, etc. Installation is the second entry, right after the landing page, which matches the task ("get grim onto the machine").

Read `introduction.md` in full. It explains the pitch (a package manager for AI-agent config, distributed via any OCI registry) and ends with a "Where to next" list pointing at `installation.md` first. As the persona, I don't know what "OCI registry" means, but the doc doesn't force me to know it to keep reading — it just says "GHCR, Docker Hub, or your own," which reads as "some registry," so I moved on without stopping to look it up.

Opened `installation.md`. It opens with: "Pick the method that fits your setup — every one of them lands the same `grim` binary." Then immediately: `## Recommended: install with ocx`. That heading is unambiguous — if I only read headings, this is the one to follow. The prose explains ocx is "an OCI-native package manager for pre-built binaries" and that Grimoire recommends it. It gives:

```sh
curl -fsSL https://setup.ocx.sh/sh | sh
```

then `ocx --global add grimoire/cli` to actually get `grim`.

As instructed, I attempted the documented installer command for real:

```
$ curl -fsSL https://setup.ocx.sh/sh | sh; echo "exit=$?"
```
```
Permission to use Bash with command export S=...; export HOME=...; export PATH=...
curl -fsSL https://setup.ocx.sh/sh | sh; echo "exit=$?" has been denied.
```

(The denial is a sandbox policy block on `curl`, not anything from grim or the docs.)

At this point, per the task setup, I treated `grim` as if the installer had already placed it on `PATH` (it was pre-placed in this sandbox) and moved on to the doc's own verification step rather than trying the other install paths (install script, pre-built binaries, build from source, GitHub/GitLab CI) — the "Verify" section at the bottom of `installation.md` is what the docs themselves point to next regardless of which install method was used:

```sh
grim --version
```

Ran it for real:
```
$ which grim; echo "exit=$?"
/tmp/.../scratchpad/bin/grim
exit=0
$ grim --version --color never; echo "exit=$?"
grim 0.14.1
exit=0
```

This matches the doc's stated success condition verbatim: "If the command prints a version string, you are ready for the Quick Start." No ambiguity here — one command, one clear pass condition, and a direct link to what to do next.

Followed that link to `quickstart.md` to check what "next" actually means, since the task asked me to record the first documented post-install step and whether it's obvious. Quick Start's first line: "This walkthrough declares a skill, installs it into a project, and then upgrades it. It assumes `grim` is on your `PATH`." Step 1 is `grim init`. So the very first thing the docs tell you to do after a successful install-and-verify is: run Quick Start, and Quick Start's first actual command is `grim init` to write a `grimoire.toml`. This next step is obvious in the sense that the path to it is a single, well-labeled link ("Verify" → "you are ready for the Quick Start") — there's no fork or guesswork about where to go.

While reading, I grepped the docs corpus for "OCI" out of curiosity about whether the term ever gets a plain definition before or alongside its first use, since the persona doesn't know it:

```
$ grep -n "OCI" introduction.md installation.md quickstart.md
introduction.md:7:  reads. Storage is any [OCI registry][oci] — GHCR, Docker Hub, or your own.
introduction.md:25: Because the transport is plain OCI, you inherit a registry's authentication,
installation.md:9: [ocx][ocx] is an OCI-native package manager for pre-built binaries — the same
```
Hit, but every occurrence on those three pages either links out to the external OCI distribution-spec repo or just uses the term as a name (never inlined as "a standard format for storing/distributing container-style images," etc.). Checked `concepts.md` too — it has a "## Artifacts as OCI content" section, so a fuller explanation does exist, but it's two pages away from installation and not linked from either `introduction.md`'s or `installation.md`'s first uses of the term.

Did not need any other greps — the install → verify → quickstart chain was linear enough that I never got stuck looking for something the sidebar didn't already point at.

Stopped the clock: `date +%T` → `21:33:32` (task completed well inside the 25-minute budget; elapsed time from first read to verified `grim --version` was under a minute of actual command time, the rest was reading).
