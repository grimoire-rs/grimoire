# Friction log: T08 re-render/re-materialize after a hand-edit

## Context

The persona has never used grim before; they have Claude Code and OpenAI
Codex CLI installed and want to understand what `grim status`, `grim
update`, and `grim install` do to a skill file they hand-edited after
installing it, and how to deliberately keep or discard that edit. Before
starting they had only a fresh git repo and the published documentation
site. Written by a subagent with no repository access, from the published
docs pages and the grim binary only.

## Pros and cons

- Good: `quickstart.md` steps 1-2 (`grim init`, `grim add
  ghcr.io/grimoire-rs/skills/grim-usage`) worked verbatim on the first try,
  no flags guessed.
- Bad: quickstart's step 2 promised the artifact would materialize "into the
  clients it detects," but with no client marker in the fresh project it
  silently rendered into the generic `.agents/skills/` pool instead of
  `.claude/skills/` — the fallback behavior is documented on `clients.md`
  ("What grim will and will not do about a gap") and in `commands.md`'s
  `grim install` section, but not flagged at the point in `quickstart.md`
  where a first-timer would hit it.
- Good: `commands.md`'s `grim update` section states the exact refusal
  behavior for a locally-modified artifact (exit 65, hash comparison,
  `--force` to override) before I ran anything, so the refusal I got was not
  a surprise.
- Bad: three different pages give three different word-lists for the same
  `grim status` state concept: `quickstart.md` says "installed, outdated,
  locally modified, or missing"; `commands.md`'s `grim status` section says
  "installed, outdated, locally modified, integrity-missing, or not
  installed"; `json-interface.md`'s status table gives the actual enum as
  `installed, stale, modified, missing, outdated`. None of the three lists
  matches another exactly.
- Bad: the JSON `state` enum value `stale` (`json-interface.md` status row)
  is never defined anywhere in the docs set — it only appears as a bare word
  in that one enum list. I never saw it fire in my own run.
- Good: `upgrading.md` ("A refused update over a locally-modified artifact")
  directly answers "how do I keep an edit" — `grim remove` undeclares the
  artifact and explicitly leaves the file on disk — and "how do I discard
  it" — `--force` or the TUI Overwrite dialog.
- Bad: `commands.md`'s bundle-row section (around the `grim tui` tree
  rollup) uses a third, non-overlapping vocabulary for what is conceptually
  the same health state: `integrity-missing`, `pending`, `not installed`,
  layered with precedence over `modified`/`outdated`/`installed`. `pending`
  and this `not installed` never appear in the `grim status` JSON enum at
  all.
- Good: the JSON output for `grim update`'s refusal matched
  `json-interface.md`'s promise exactly — table still printed
  (`action: unchanged`), exit code 65, no error document — I did not have to
  guess whether the refusal suppressed the report.

Ran `grim update` on the modified file:

```
$ grim update
```

My edit survived (`diff` against the pre-edit copy still showed only my one
sentence changed). This matches `commands.md`'s claim exactly: "A refusal
does not suppress the report" — the table still prints beside the error, and
`action: unchanged` even though the command exited 65. This is, per
`upgrading.md`, also the answer to "how do I keep the edit across an
update": do nothing special, just don't pass `--force`; grim's own integrity
hash comparison is the mechanism, not a flag or config setting I had to set.

Ran `grim install` on the still-modified file:

```
$ grim install

exit=65
```

Same refusal message as `update`, but no table at all this time — `update`
printed a table next to its error, plain `install` printed only the error
line. Edit still intact after.

To get back to the published version, grepped `commands.md` and
`upgrading.md` for `--force` usage against this exact scenario, then ran:

```
$ grim install --force
Kind   Name        Target                                                                                                                             Status
skill  grim-usage  .../proj/.claude/skills/grim-usage  updated
exit=0
```

`diff` against the pre-edit copy now returned exit 0 (no difference) — the
published sentence was back verbatim, and `grim status` read `installed`
again. That confirms `--force` on `grim install` is what "get back to the
published version" means in practice.

Grepped for `re-render` and `re-materiali[sz]e` across the whole doc set to
pin down what those two words mean, since the task asked. `re-materialize`
is the general term used everywhere for "write the artifact's pinned content
to a client's directory" (`commands.md`, `quickstart.md`, `stability.md`,
`upgrading.md` all use it that way, for both `install` and `update`).
`re-render`, by contrast, shows up in two unrelated senses on different
pages: (1) on `vendor-metadata.md`, re-rendering a rule for Claude Code means
transforming its content because it carries vendor-namespaced metadata keys
(a content transform, not just a copy); (2) on `hosting-an-index.md` and
`ratings.md`, "re-render" means regenerating the *index repository's own CI
pipeline* after editing its config block — a completely different subsystem
(package-index hosting, not artifact installation) that happens to reuse the
same verb.

For "does install and update differ in what they rewrite": `commands.md`'s
`grim update` section states it directly — "Pruning and client-reaping
happen only on update. grim install materializes the current lock but never
deletes — like grim remove, it leaves files on disk." I did not need to
reproduce pruning/reaping myself to find this; it is stated once, plainly,
in the `grim update` section rather than the `grim install` one, so I would
not have found it by reading only the `install` section.

Also noticed, while grepping for "not installed" (used in the `grim status`
prose), a third vocabulary in `commands.md`'s bundle-row / tree-rollup
passage: "the row shows the worst member state, at the same precedence the
tree rollup uses: `integrity-missing` over `modified` over `outdated` over
`pending` over `installed`." `pending` and this particular `not installed`
never appear in the `grim status --format json` enum I actually got back
(`installed, stale, modified, missing, outdated`), so a reader relying on
the JSON contract page alone would not learn these words exist, and a reader
relying on the bundle/tree passage would not learn `stale` or `missing`
exist.
