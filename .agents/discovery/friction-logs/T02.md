# Friction log: T02 install one skill for Claude Code in a new project

## Context

I am a Python developer who uses Claude Code every day and has never used
grim before; `grim` is already on my PATH. I am starting a brand-new,
empty project (just ran `git init`) and want exactly one useful skill from
the public catalog working inside Claude Code, then I want to be certain
Claude Code will actually see it, and know which of the files grim creates
belong in git. Before starting I had nothing but an empty repo and the
published docs site. Written by a subagent with no repository access, from
the published docs pages and the grim binary only.

## Pros and cons

- Good: `introduction.md` points straight at "Quick Start — install your
  first skill in five commands," so there was no doubt where to start.
- Good: every quickstart command (`grim init`, `grim add
  ghcr.io/grimoire-rs/skills/grim-usage`, `grim status`) ran verbatim,
  first try, no flags needed beyond the `--color never` I added myself for
  clean output.
- Good: `grim status --format json` (documented in `json-interface.md`,
  not in the quickstart) names the exact client and path for every
  installed output, which is the only command output that actually proves
  Claude Code got a copy.
- Good: `configuration.md`'s Data Layout section states plainly that grim
  writes `.grimoire/.gitignore` (contents `*`) the first time it creates
  `.grimoire/`, so that directory is unambiguously "don't commit."
- Bad: `grim add ghcr.io/grimoire-rs/skills/grim-usage`, run exactly as the
  quickstart shows, in a fresh project with no `.claude/` directory yet,
  installed into `.agents/skills/grim-usage/` — the vendor-neutral pool —
  not `.claude/skills/`. Nothing in the command's own output said this;
  I only found the reason by reading `clients.md`'s "no client marker
  present" fallback paragraph and `concepts.md`'s matching paragraph.
- Bad: `grim add` has no `--client` flag (`commands.md` states this
  explicitly), so the fix for "I want this in Claude Code" is a second
  command, `grim install --client claude`, that the quickstart never
  mentions as something you might need on a new project.
- Bad: the task's own verification command, plain `ls -R`, shows nothing
  at all in a fresh project — both `.agents/` and `.claude/` are
  dot-directories `ls -R` hides by default, so it reports only
  `grimoire.lock` and `grimoire.toml` even after a successful install.
- Bad: plain-table `grim status` (the form the quickstart shows) never
  names a client or a path — it says `installed` whether or not Claude
  Code is one of the targets, so it cannot by itself answer "will Claude
  Code see this."
- Bad: no page states, in one place, "commit `grimoire.toml` and
  `grimoire.lock`, do not commit the installed skill directories or
  `.grimoire/`." I had to assemble this from three different sentences on
  two pages (see stream of consciousness).
- Bad: no page says whether Claude Code needs a restart or reload to
  notice a new skill directory; the only assurance the docs give is
  structural (file is at the documented native path with the documented
  frontmatter shape).

## Detailed stream of consciousness

```
$ date +%T
21:32:42
```

Started at `introduction.md` since that's the landing page. It has a
"Where to next" list; "Quick Start — install your first skill in five
commands" is the obvious first link for someone who has never touched this
tool, so I went there next rather than "Installation" (grim is already
installed per the task, so I skipped that page entirely).

`quickstart.md` step 1 is `grim init`. Ran it in `$S/proj` after `git init
-q`:

```
$ grim init --color never
Path                                    Scope    Status
.../proj/grimoire.toml                  project  created
```

Worked first try. `cat grimoire.toml` afterwards showed just empty
`[skills]` / `[rules]` tables — no `[options]` block, which I didn't think
about yet but turned out to matter later.

Step 2 is `grim add`. The doc's own worked example is
`ghcr.io/grimoire-rs/skills/grim-usage`, so I used exactly that instead of
searching for something Python-specific — the instructions said to follow
the quickstart, and this is the one artifact the docs themselves already
vouch for as "useful":

```
$ date +%T
21:33:08
$ grim add ghcr.io/grimoire-rs/skills/grim-usage --color never
Kind   Name        Pinned                                    Status
skill  grim-usage  ghcr.io/grimoire-rs/skills/grim-usage@sha256:f97...  added
```

No errors, no warnings printed anywhere in this output.

Now the task's verification step. Ran `ls -R` exactly as instructed:

```
$ ls -R
grimoire.lock
grimoire.toml
```

That's it — no sign the skill materialized anywhere. I re-ran with `-a` to
see if it was hiding in a dotdir, since `grim add`'s own table had said
`added`, and `grim status` (below) also said `installed`, so I assumed the
files existed somewhere:

```
$ ls -Ra
.  ..  .agents  .git  .grimoire  grimoire.lock  grimoire.toml
```

`.agents/skills/grim-usage/` is where the files actually are — not
`.claude/skills/`, which is what I expected as a daily Claude Code user
(and which `vendor-metadata.md` later confirmed is Claude Code's real,
documented directory: `.claude/skills/<name>/`). This is the first real
confusion point. I went back to `clients.md` to find out why.

`clients.md` (searched for "marker" after finding nothing under the
support matrix itself):

> It is also what grim falls back to when *nothing* is detected: rather
> than writing a directory for every client it knows about, an install
> with no `--client`, no `[options].clients`, and no client marker present
> targets `agents` alone.

and `concepts.md` says the same thing in almost the same words. My
project is brand new — no `.claude/` directory existed before I ran
`grim add`, so there was no "Claude Code marker" for grim to detect, and
it silently fell back to the generic vendor-neutral pool. Nothing in the
`grim add` output signaled that a fallback had happened; you only learn it
by reading these two pages.

Checked whether Claude Code reads that pool anyway. `clients.md`'s
"Shared skills pool visibility" section lists who *writes* to
`.agents/skills` by default (Codex, Gemini, Zed, Amp, Goose, the
vendor-neutral `agents` target, and project-scope Antigravity) and who
*reads* it without writing (Cursor, Copilot, OpenCode, Warp). Claude is in
neither list. So the quickstart's own example command, run verbatim in a
fresh project, does not put anything where Claude Code looks.

Grepped `commands.md` for how to fix this and found, under `grim add`:

> `grim add` has no `--client` flag of its own; use `--no-install` when
> you mean to declare now and choose clients later.

So the fix is a second command:

```
$ date +%T
21:34:56
$ grim install --client claude --color never
Kind   Name        Target                                    Status
skill  grim-usage  .../proj/.claude/skills/grim-usage         updated
```

That worked. Re-checked with `ls -Ra .claude` and the skill and its
`references/` directory were there, matching the file layout
`vendor-metadata.md` documents for Claude Code.

Re-ran the task's literal `ls -R` again out of curiosity — still just
`grimoire.lock` and `grimoire.toml`, even with the skill correctly
installed in `.claude/skills/`. The instructed verification command does
not actually verify anything in a project this fresh, because the only
output locations grim ever uses (`.claude/`, `.agents/`, `.grimoire/`) are
all dot-directories.

Ran `grim status` per the task:

```
$ grim status --color never
Kind   Name        Source  Pinned              State
skill  grim-usage  direct  ghcr.io/...@sha256  installed
```

`installed` — but no client name, no path. This does not tell me Claude
Code specifically has it; the old `.agents/skills/grim-usage` copy from my
first, mis-targeted `add` is still sitting on disk too, and this table
doesn't distinguish "installed for Claude" from "installed for the
fallback pool." Grepped `commands.md` and `json-interface.md` for a way to
see per-client output and found `--format json`, which is not mentioned in
the quickstart at all:

```
$ grim status --format json --color never
...
"outputs": [
  {"client": "agents", "path": ".../.agents/skills/grim-usage"},
  {"client": "claude", "path": ".../.claude/skills/grim-usage"}
],
...
```

This is the only command output in the whole exercise that actually names
"claude" next to a path. That's the closest thing to proof I found that
Claude Code will see the skill: the file sits at the path
`vendor-metadata.md` documents as Claude Code's own skills directory, in
the standard frontmatter shape (checked `.claude/skills/grim-usage/SKILL.md`
directly — it has `name:` and `description:` frontmatter keys). No page
anywhere states whether Claude Code needs restarting or reloading to pick
up a skill added while it might be running; the docs give no runtime
confirmation step at all, only this structural argument.

For the git question I grepped for "gitignore" and "commit" across every
page. `configuration.md`'s Data Layout section is explicit about one
thing only:

> Grim writes a self-managed `.grimoire/.gitignore` (contents: `*`) the
> first time it creates the `.grimoire/` directory, so the state file is
> kept out of version control without touching your root `.gitignore`.

Confirmed on disk — `git status --porcelain --ignored` shows `.grimoire/`
as `!!` (ignored) and everything else (`grimoire.toml`, `grimoire.lock`,
`.agents/`, `.claude/`) as `??` (untracked, not ignored). So `.grimoire/`
is a clear "never commit."

For `grimoire.toml`, `configuration.md`'s glob-escaping paragraph says in
passing: "`grimoire.toml` is a file teams commit and share, so one pattern
has to mean one thing on every checkout" — that's the only sentence
anywhere that states outright that this file is meant to be committed.

For `grimoire.lock` I found no equivalent explicit sentence. `concepts.md`
describes it as what makes "an install... byte-for-byte reproducible until
you deliberately upgrade" and frames it the way a lockfile is usually
framed, but never says "commit this" the way it says so for
`grimoire.toml`.

For the installed skill directories themselves (`.claude/skills/
grim-usage/`, and the leftover `.agents/skills/grim-usage/`), I found no
statement anywhere — not in `configuration.md`, not in `concepts.md`, not
in `clients.md` — saying whether these generated, re-creatable files
belong in git or should be left for each teammate's own `grim install` to
regenerate. The only signal is the negative one: grim did not write a
`.gitignore` into `.claude/` or `.agents/` the way it did for `.grimoire/`,
and `git status --ignored` does not mark them ignored either.

```
$ date +%T
21:36:50
```

Stopped here — task's two questions are answered as far as the docs go,
and the skill is verifiably installed for Claude Code.
