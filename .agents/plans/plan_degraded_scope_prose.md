# Plan: Render a dropped `paths:` scope as prose for Degraded-scoping clients

## Status

- **Plan:** degraded_scope_prose
- **Active phase:** implementation (complete)
- **Step:** verified
- **Last update:** 2026-08-25 (`task --force verify` green — 2855 unit + 1065 acceptance)
- **Tracking:** [grimoire-rs/grimoire#103](https://github.com/grimoire-rs/grimoire/issues/103)

---

## Context

A client whose rule scoping is `KindSupport::Degraded` installs a scoped rule
with its `paths:` **discarded**. The author saw a `tracing::warn!` at install
time; the consumer got a rule authored for `**/*.rs` that silently claimed to
apply to everything, with nothing in the rendered document saying otherwise.

The warning was honest, the artifact was not.

## Decision

Restate the dropped scope in the rule body as one blockquote line, ahead of the
author's text:

```markdown
<!-- generated by grim from …; edits will be overwritten -->
> Applies only when working on files matching `**/*.rs`.

# Rust Style
…
```

A **class-2 compensating render** per
[`adr_vendor_support_tiers.md`](../adr/adr_vendor_support_tiers.md), which
classifies this issue by name. Deterministic body text, no runtime, removed with
the artifact. It does not recover the token cost — it stops the rule being
*misapplied*.

### Which clients

- **OpenCode** and **Junie** — the two `Degraded` clients: `paths:` has no
  native target and is dropped.
- **Kiro is out of scope.** The issue's premise was wrong: Kiro is `Native`,
  writes correct `inclusion: fileMatch` + `fileMatchPattern`, and its warning is
  about upstream bug [kirodotdev/Kiro#9176](https://github.com/kirodotdev/Kiro/issues/9176)
  making *global* steering inert. That file self-heals when the bug closes.
  `docs/src/clients.md` states grim deliberately ships the deterministic scoping
  rather than a fuzzy always-on fallback, and prose would be exactly that.

### Tier carve-out (ADR amendment)

Class-2 renders were gated to Tier 1, and Junie is Tier 2. The gate exists to
bound *re-verification* cost. This render is derived solely from the artifact's
own frontmatter — no upstream key, surface or version behind it — so there is
nothing to re-verify and nothing the tier buys. Amended in
`adr_vendor_support_tiers.md` §2 and mirrored in the watchlist: **a
frontmatter-only class-2 render is not tier-gated; one that tracks a vendor
surface still is.**

The author-side warning is deliberately **kept**: prose is weaker than a native
scoping key, and only the author can decide whether that is enough.

## Backwards compatibility

Vendor render layout is outside the 1.0 contract
([`adr_render_layout_stability.md`](../adr/adr_render_layout_stability.md)
Decision 1). No schema, no layout, no path move ⇒ no migration, no reaper, no
upgrade fixture.

`status` is unaffected for existing installs: `footprint`
(`src/command/status.rs`) compares the file on disk against the hash recorded
**at install time**, so a rule rendered by the old renderer still reports
`Intact`. The next `grim install` / `grim update` rewrites file and hash
together. Re-rendering the same artifact twice is byte-identical — self-heal
holds (`rule_index_is_deterministic`, `scope_notice_is_deterministic`).
